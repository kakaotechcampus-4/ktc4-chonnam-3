# 0052 Director 문제 재현 평가와 조건부 질문 개선

상태: Accepted for local development and evaluation, 2026-11-11.

사용자가 합의한 Luna 전용·현재 설정 유지·Codex 주평가 방식으로 Director를 개선하는
로컬 구현 범위를 채택한다. 운영 품질 인증, 사람 검수, 도메인 전문가 승인 또는
공개 채점 기준의 타당성 승인을 뜻하지 않는다. 실행 결과·구현 상태는
[구현 기록](../implementation.md) 한 곳에서 관리한다.

## 맥락

실사용에서 관찰한 응답 대기와 질문 연결·표현 문제를 재현하고 원인별로 개선해야 한다.
문제 해결 관점은 Director 자체의 입력·판단·질문·복구 문제를 해결한다는 뜻이며,
면접을 지원자의 `problem_solving` 항목만 평가하는 방식으로 바꾸지 않는다.

기존 단일 Director, 질문 계약, 실제 원문, 별도 Plan/Review, Controller의 저장·종료 책임을
유지한다. [0040](0040-director-single-copy-source-input.md)의 원문 중복 제거,
[0043](0043-director-turn-state-and-reference-constraints.md)의 턴 상태·실제 ID 제약,
[0050](0050-review-work-lifetime-and-scoped-recovery.md)의 작업 수명·복구 경계를 이어간다.

## 결정

1. 서비스 생성과 제한된 보조 Judge에는 Luna만 사용한다. Sol은 이번 비교·개선에 포함하지 않는다.
   현재 `.env`의 추론 강도·출력 상한을 유지하고 실제 요청 모델·설정·버전을 실행에 결합한다.
   설정을 낮춘 효과와 입력·정책 개선 효과를 섞지 않는다.
2. 기존 평가 실행기·검토 자료·저장 판정과 공통 호출 장부·집계를 재사용한다.
   레포 분석 전용 수집·분석 실행기를 Director에 복사하거나 자율 레포 Agent를 추가하지 않는다.
   별도 레포 평가 작업의 공통 저장 판정 결정 0051과 코드는 미병합 선행 범위로 구분하며,
   이 결정으로 해당 원본을 재작성하거나 승인·게시·검증 완료로 간주하지 않는다.
3. 코드가 형식·참조·호출·저장·종료 등 결정적으로 확인 가능한 조건을 검사한다.
   Codex가 실제 원문·질문 계약·출력·기준을 읽고 기준별 이유를 남기는 주평가를 맡는다.
   Luna Judge는 사전에 정한 표본·제어 사례의 보조 대조이며 전수 추가 호출을 기본으로 하지 않는다.
   입력·출력·기준의 지문이 맞지 않는 판정, 기준 누락·중복·상충한 종합 판정은 거절한다.
   이 평가는 보존한 서비스 출력의 오프라인 판정이며 서비스의 Plan/Review와 구분한다.
   Codex를 실제 면접 턴의 새 런타임 Agent나 필수 외부 API로 연결하지 않는다.
4. Codex도 LLM 평가자이며 구현 참여자의 평가다. 사람 또는 독립 전문가 검수로 기록하지 않는다.
   완료한 자동 검사·판정은 `자동 검증 완료`로 표시하고 사람 검수 상태는 별도로 보존한다.
   기존 pending·미검수 사례를 사람 승인 정답으로 승격하지 않는다. 평가자의 오류와 모호함도
   제어 사례·실패 이유로 남기며, 다른 평가자보다 정확하다는 전제로 통과시키지 않는다.
5. 질문할 기회와 답변 충분성을 분리한다. 확정 질문의 평가 키를 모은
   `presented_evaluation_keys`는 점수·역량 확보가 아니다. 기존 main 배정을 유지하면서
   직전 실제 답변·당시 계약에 재검증한 분석에서 보완·명확화 선택지를 제한적으로 계산한다.
   남은 Persona 슬롯으로 적용 가능한 미질문 영역을 확보할 수 있을 때만 선택지를 제공한다.
   partial·모름을 무조건 후속 질문으로 연결하거나 충분히 답할 때까지 반복하지 않는다.
6. v9는 저장 Context와 모델 표시용 입력을 분리한다. 현재 턴의 질문·답변·계약·분석 중복과
   불필요한 공고 수집 메타데이터를 제거한다. 원문·정정·위치·SHA·과거 복원 registry는 유지하고,
   모델이 실제로 본 자료와 참조 허용 범위를 일치시킨다. Plan과 Review의 원문 범위는 같으며
   생성자의 정당화·복구 피드백을 Review의 승인 근거로 넣지 않는다.
7. 질문 계약의 목적·필수 확인내용과 실제 질문 문장을 일치시킨다. 한 중심 목적의 말하기 쉬운
   질문을 만들되 이해에 필요한 가정·조건을 숨기지 않는다. 묻지 않은 내용을 이후 감점하지 않고,
   허용 대안 중 하나를 선택하는 기준을 모든 대안을 수행해야 하는 의무로 해석하지 않는다.
   v10은 v9의 입력·후속 정책을 유지하면서 `company_job_fit`의 의미를 명시한다. 실제 질문과
   필수 확인내용 모두 프로젝트 경험·이해·제안한 방식을 JD 업무에 연결하도록 해야 한다.
   공고의 기술명이나 장애 상황만 붙인 일반 기술 질문을 직무 연결의 평가 기회로 기록하지 않는다.
8. 별도 Review·실제 ID 제한·유한 복구·중복 확정 방지를 유지한다. 새 프롬프트의 턴 상태,
   스키마 제약, 복구 피드백과 자동 복구 허용 여부를 같은 capability 기준으로 연결한다.
   속도를 위해 검토를 제거하거나 재시도·질문 수·종료 권한을 늘리지 않는다.
9. v9에서 원문 항목이 없는 `not_found/tool_error/insufficient_analysis` 결과는 최초 유효 T3와
   실제 Tool 상태를 재사용할 수 있다. claim·분석을 덮어쓰거나 미확인을 검증 완료·감점으로
   바꾸지 않는다. 원문 항목이 있으면 기존 보강 T3와 공유 예산을 유지한다. 최적화를 허용한
   활성 PromptSpec을 고정하고 다음 질문 생성 시 동일성을 검사한다. 불일치는 호출 전
   폐기 기록으로 남기며 재전송에서도 같은 결과를 보존한다. 마지막 답변도 정책·한계를 기록한다.
10. 같은 사례·자료·모델·설정에서 변경 전후를 비교한다. 서비스 시간과 Judge 시간을 분리하고,
    물리 HTTP 시도·실패·취소·미확인 사용량을 기록한다. 장부를 원본으로 두고 Langfuse 전송은
    별도로 수행한다. 캐시·추론 토큰을 총량에 중복 합산하지 않으며 미계측 비용을 0으로 만들지 않는다.

## 자료와 기준의 근거

`기술면접 특강 자료.pdf`, 「기술면접, 그리고 AI 시대는 어떤 사람을 원할까」의 원칙을 다음 범위로 적용한다.

| 원문 위치 | 적용하는 원칙 | 적용하지 않는 해석 |
| --- | --- | --- |
| 8~15쪽 | 실제 답변에 연결하고 필요한 깊이를 단계적으로 확인 | 모든 답변에 정의·원리·장단점·대안·경험을 전부 요구 |
| 26~29쪽 | 선택 이유·조건·대안·본인 역할을 확인 | 레포·기술명만 보고 개인 기여나 이해도를 확정 |
| 30~44쪽 | 새 조건을 명시하고 실패·검증 방법을 구체화, 모름과 접근을 구분 | 강의 예시의 기술·해법만 정답으로 채택하거나 어려움 자체를 금지 |
| 41쪽 | 개인 담당과 팀의 역할·정정 내용을 구분 | 협업·AI 사용을 역량 부족으로 단정 |
| 60~66쪽 | 문제 정의와 AI 결과 검증을 관련 질문에 반영 | 특정 도구·자율 Agent·기술 목록을 모든 지원자의 필수 역량으로 고정 |

이 강의는 실무 질문 설계 참고자료다. 심리측정 타당성, 품질 점수 가중치, 지연 SLO,
비용 상한 또는 표본 수의 정량 근거로 사용하지 않는다.

[#110](https://github.com/kakaotechcampus-4/ktc4-chonnam-3/issues/110)의 허용 질문·반복·미관찰,
평가자 false accept/false reject, 필수 오류, 수치 수용 기준과 연결한다. 공개 rubric 환산,
도메인 검수자 승인, 시드 활성화의 전체 합의를 이 결정으로 대신하지 않는다. 수치 목표·가중치·
합격선을 임의로 만들지 않고 대표 사례의 측정과 제품 목표를 근거로 최종 검증 전에 고정한다.

## 평가 자료와 해석 범위

- 개발·최종 검증 자료는 레포·공고·대화의 source group 단위로 분리한다. 같은 자료의 변형,
  반복 실행, 면접의 여러 턴을 독립 사용자 표본으로 계산하지 않는다.
- 합성 원문·지원자 답변·상황은 재현 가능한 진단 자료다. split을 분리해도 실제 대규모 레포,
  실제 지원자·채용 면접·사람 정답을 대표한다는 보장은 없다. 실제 자료 검증과 결과를 구분한다.
- 최종 검증 결과를 보고 수정했다면 그 자료는 이후 회귀 자료이며 새 독립 검증으로 재명명하지 않는다.
- 평가 기준·코드·출력·원문 버전을 결합하고 적용 조건·허용 대안을 명시한다. 판단 불가,
  미실행·누락·예산 소진은 통과에 포함하지 않는다. 필수 안전 오류를 평균 품질로 상쇄하지 않는다.
- 작은 표본의 평균·p95·품질 비율에는 사례·source group 수와 관측 범위를 함께 표시한다.
  입력 바이트나 모의 HTTP 호출 감소만으로 실제 사용자 대기·청구액 감소를 확정하지 않는다.

## 추가 방법을 선택하는 기준

사용자의 2026-11-11 추가 지시에 따라 아키텍처·RAG·임베딩·Lang 계열도 해결 후보로 둔다.
도입 자체를 목표나 구현 지시로 해석하지 않는다. 실제 실패 원인과 해결 가설을 먼저 고정하고,
동일 자료·Luna 설정에서 기존 방법과 비교해 채택 여부를 결정한다.

| 후보 | 적합한 문제 | 비교 조건 |
| --- | --- | --- |
| 책임·상태 경계 개선 | 중복 호출·정책 변경 후 잘못된 재사용·중단 복구·저장 충돌 | 재개·중복 전송·취소 테스트, 물리 호출 수, 총지연과 상태 일관성 |
| 필요한 근거를 검색해 제공하는 RAG | 자료가 커서 필요한 근거를 놓치거나 무관한 원문을 과다 전달 | 근거 검색 Recall@k, 무관 자료 비율, 질문 근거 정확성, 검색 포함 총시간·토큰 |
| 임베딩과 키워드·식별자 검색의 결합 | 자연어 표현이 달라 정확한 근거를 찾지 못함 | 같은 사실표의 표현 변형·어려운 반례·다국어 검색, 색인·변경 갱신 비용과 지연 |
| LangChain의 연결 추상화 | 여러 모델·수집기·Tool의 연결 유지보수가 실제 병목 | 기존 gateway의 스키마 검증·실제 사용량·유한 예산·취소 의미 보존과 유지보수 절감 |
| LangGraph의 상태 실행 | 분기·재개·checkpoint 관리가 직접 구현에서 반복 오류를 만듦 | 기존 DB 잠금·ARQ·WS 수명과의 책임 일치, 중단 후 중복 과금·중복 저장 방지, 전환 비용 |

검색 결과는 후보 근거이며 임베딩 유사도는 사실·개인 기여·역량 점수가 아니다. 레포·SHA·문서
버전·접근 범위를 먼저 제한하고 원문 구간·주변 문맥·출처·미확인 범위를 유지한다. 작은 고정
문맥에 있는 질문 계약 오류를 검색 도입으로 해결한다고 가정하지 않는다. 임베딩만으로 검색하거나
모든 턴에 검색을 강제하지 않으며, 단일 Director가 필요한 Tool을 요청하는 책임을 유지한다.

새 검색/색인 모델을 비교하려면 공급자·모델·차원·입력 분할·색인 버전과 비용도 별도로 결합한다.
검색의 이득과 프롬프트·모델 변경의 이득을 섞지 않는다. source group별 개발/최종 자료를 분리하고,
같은 평가 자료에 맞춘 뒤 독립 검증 완료로 재명명하지 않는다. Langfuse는 관측 역할이며 검색·
임베딩·상태 실행 프레임워크의 도입 조건이 아니다.

기술 역할 구분은 [공식 Retrieval 설명](https://docs.langchain.com/oss/python/deepagents/retrieval)과
[LangGraph 설명](https://docs.langchain.com/oss/python/langgraph/overview),
[상태 보존 설명](https://docs.langchain.com/oss/python/langgraph/persistence)을 참고한다.
라이브러리의 기능 설명은 이 서비스에서의 성능·정확성 향상을 입증하는 자료로 사용하지 않는다.

## 영향

현행 내부 필드·검증 의미는 [내부 계약](../contracts.md)의 v9 범위를 따른다. 공개 REST·WS 필드,
DB 컬럼, 고정 면접 배분과 공개 채점 산식은 이 결정의 변경 대상이 아니다. 기존 버전의 원문·입력과
평가 이력은 보존한다. 필요한 실제 변경·미실행·실측 결과는 구현 기록에서 따로 확인한다.
