# 면접 WebSocket Mock 방식 결정

- 상태: Proposed
- 작성일: 2026-09-21
- 관련 브랜치: `feature/msw-failure-and-ws`
- 참조 명세: `frontend/docs/api-spec.md` #18, `spec/backend/features/interview.md`,
  `spec/shared/contracts/migration.md`(WS 식별자·`questionEnd`는 `PENDING_FE`)
- 검토자: FE·BE 리드 미확정

## 결정

**msw 2.15의 `ws.link()`를 쓴다.** REST 목과 같은 핸들러 배열에 얹고 별도 서버를 띄우지 않는다.

```ts
export const interviewSocket = ws.link(path('/ws/interviews/:sessionId'));
```

## 배경

`InterviewPrepare`·`InterviewScreen`은 아직 스텁이다. 이전 설계 문서는 "소비처가 없으니 화면 작업과 함께"로
미뤘다. 그 판단을 바꾼 이유는 두 가지다.

- WS는 화면 상태머신 자체를 결정한다. 준비 체크리스트, 입력창 잠금, 배너 해제 시점이 전부 메시지 순서에 달려 있다.
  목이 없으면 화면 작업이 계약 문서를 눈으로 읽어 옮기는 일이 되고, 어긋나도 실서버가 나올 때까지 드러나지 않는다.
- msw에 WS 지원이 들어오면서 비용이 크게 떨어졌다. 별도 서버·별도 설정·별도 종료 절차가 없다.

## 비교한 안

| 안 | 장점 | 단점 | 판정 |
| --- | --- | --- | --- |
| **msw `ws.link()`** | REST 목과 같은 배열·같은 장애 주입 저장소. 추가 프로세스 없음. `npm run dev` 하나로 끝 | 핸드셰이크 단계(HTTP 401·409)에 끼어들 수 없음 | **채택** |
| 로컬 `ws` 서버 (별도 프로세스) | 핸드셰이크 상태코드까지 재현. 실제 네트워크 경로 | 프로세스·포트·종료 관리가 늘고, 목 상태가 REST 목과 분리돼 두 벌이 됨 | 기각 |
| `WebSocket` 클래스 직접 교체 | 의존성 0 | 프로덕션 코드에 목 분기가 남고, 실제 연결 경로를 타지 않아 검증 가치가 낮음 | 기각 |

두 번째 안의 결정적인 문제는 **상태가 둘로 갈라진다**는 점이다. 면접 턴은 `GET /interviews/{id}`와 WS가
같은 값을 보여야 하는데(계약의 재연결 절차가 조회로 `turns`를 다시 받는 것이다), 별도 프로세스면 목 저장소를
공유할 수 없다. 한쪽만 고치는 순간 화면이 조용히 틀어진다.

## 구현 구조

```
src/mocks/ws/
├─ interview.ts   ws.link + connection 핸들러 (분기만)
├─ prepare.ts     준비 단계 스트리밍·실패 재생·prepareRetry
├─ turns.ts       질문 출제·답변 수신·종료
└─ protocol.ts    send/parse/오류 생성, 상수
```

### 상태는 목 저장소에 둔다

턴 진행을 연결 클로저가 아니라 `InterviewRecord.liveTurns`에 둔다.
계약상 재연결 절차가 `GET /interviews/{id}`로 `turns`를 다시 받는 것이라(#18),
클로저에 들고 있으면 새로고침 후 조회 응답과 어긋난다.

준비 단계도 `createdAt` 기준 경과 시간에서 파생한다. 늦게 접속한 연결은 이미 지난 단계를
`completed`로만 채우고 남은 단계부터 흘려보낸다. REST 목이 SSE·폴링을 같은 시계로 맞추는 것과 같은 규칙이다.

### 실패는 REST와 같은 저장소를 쓰되 경로로 격리한다

`msw.fault({ path: '/ws/interviews/*', reason, code, step, recoverable })`로 건다.
경로를 `/ws/` 로 명시한 규칙만 WS 에 적용한다. HTTP 전역 규칙(`path: '*'`)까지 걸리면
규칙이 WS 에서 소비돼 정작 HTTP 요청에는 안 걸리고, `code` 없는 규칙이 계약에 없는
오류를 WS 로 내보낸다(PR #46 리뷰).

준비 단계 오류는 `step` 을 싣는다. 이 값이 없으면 `error.step` 이 항상 `null` 이 되어
화면이 체크리스트의 어느 칸을 ✕로 칠지 알 수 없다. `step` 이 있으면 `error` 앞에
`prepareStep`(completed/failed/pending)을 먼저 보내고, 같은 오류를 레코드에도 남겨
새로고침 후 REST 스냅샷으로 배너를 복원할 수 있게 한다.
시나리오 프리셋 `ws-question-failed`(복구 가능), `ws-repo-unreachable`(복구 불가·연결 종료)도 같은 규칙을 쓴다.
`recoverable: false`일 때는 오류 전송 후 `CLOSE_GRACE_MS`만큼 기다렸다 닫는다.
같은 틱에 닫으면 클라이언트가 `error`를 받기 전에 연결이 끊긴다(구현 중 실제로 재현했다).

## 한계

| 항목 | 내용 |
| --- | --- |
| 핸드셰이크 실패 | 계약의 401·409는 HTTP 상태코드다. WS 목은 그 단계에 끼어들 수 없어 `1008`로 닫고 사유를 `reason`에 담는다. 화면은 `onclose`의 `code`·`reason`으로만 구분할 수 있다 |
| 인증 | 핸드셰이크 쿠키 검증을 재현하지 않는다. CORS·쿠키와 마찬가지로 실서버에서 처음 검증된다 |
| 동시 접속 | `already_connected`(기존 연결 종료 후 신규 허용)를 재현하지 않는다. 목은 연결 수를 세지 않는다 |
| 메시지 순서 보장 | `send`는 즉시 전달된다. 실서버의 네트워크 지연·재정렬은 재현하지 않는다 |

## 검증

테스트 러너가 없으므로 수동 시나리오로 확인했다. 재현 절차는 `frontend/docs/msw-smoke-check.js`.

| 시나리오 | 결과 |
| --- | --- |
| 연결 → 준비 4단계 → `prepareCompleted` → 1턴 질문 | 통과 |
| 답변 → `answerReceived` → `thinking` → `evidenceCheck` → 다음 질문 | 통과 |
| 9턴 완주 → `interviewEnd`, `GET /interviews/{id}`가 `completed`·9턴·전부 답변 | 통과 |
| 끊고 재연결 → 준비 재생 없이 `prepareCompleted` + 미답변 질문 재전송 | 통과 |
| 2000자 초과 답변 → `answer_too_long`, 답변 미저장 | 통과 |
| 준비 실패 seed 연결 → 체크리스트(completed·failed) + `error` | 통과 |
| `prepareRetry` → 성공 단계 건너뛰고 실패 단계부터 재실행 | 통과 |
| `ws-question-failed` → `recoverable: true`, 연결 유지 | 통과 |
| `ws-repo-unreachable` → `error` 수신 후 `1008` 종료 | 통과 |
| 없는 세션 / 종료된 세션 | `1008/not_found`, `1008/already_ended` |

미실행: 자동화 테스트, 핸드셰이크 인증, 동시 접속, 실서버 연동.
