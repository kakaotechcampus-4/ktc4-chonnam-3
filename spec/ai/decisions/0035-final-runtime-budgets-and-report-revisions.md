# 0035 최종 실행 예산·근거 참조·리포트 재평가 경계

- 상태: Proposed — 사용자 승인 범위의 로컬 구현 기준. 신규 공유 API와 운영 기준의 팀 검토는 별도다.
- 날짜: 2026-11-07
- 관련 결정: [0031](0031-final-service-runtime-boundaries.md), [0034](0034-local-llm-xhigh-output-limit.md)
- 관련 이슈: #110, #195, #196
- 구현·실행 결과: [단일 구현 기록](../implementation.md)

## 맥락

최종 기능을 실제 공급자에 연결하려면 모델 선택, 작업별 대기 시간, 원문과 해석의 참조,
중단·재시도와 리포트 변경의 책임을 명시해야 한다. 실행 성공과 평가 기준의 타당성 승인은 별개다.

## 결정

### 모델과 예산

1. 사용자 지정 서비스 모델은 기존 설정의 세 번째 연결 `gpt-6.1-sol`이다.
   `LLM_CONNECTION_SLOT`으로 모델과 프록시 주소를 한 쌍으로 선택한다.
   불완전한 연결은 실패 처리하며 다른 슬롯으로 조용히 전환하지 않는다.
   STT·Vision은 각자의 기존 설정 경로를 유지한다.
2. `xhigh`, Responses 스트리밍, 모델 출력 상한 128000을 사용하되 실제 작업에는 유한한 시간·바이트 상한을 둔다.
   출력 상한은 항상 그만큼 생성한다는 뜻이 아니다. 스트리밍은 전송 방식이며 검증되지 않은 토큰을 발행하지 않는다.
3. 작업별 시간 상한은 `LLM_TASK_TIMEOUTS`에 명시한다. 초기 로컬 값은 `repo_deep`,
   `answer_analysis`, `director` 각각 120초다. 9턴 전체를 처리하는 `report_score`·`report`는
   각각 180초, 나머지는 공통 50초다.
   이는 제한된 기능 검증을 위한 시작값이며 사용자 응답 시간의 목표나 운영 최적값은 아니다.
4. 면접 준비 worker는 1800초, 내부 전체 deadline은 1770초로 분리한다.
   수집·문서 추출·선정/분석·주장 대조·질문 생성/검토의 최대 계획을 먼저 검사한다.
   개별 호출의 대기 시간을 늘려도 전체 작업과 WS 실행권이 먼저 만료되지 않도록 함께 조정한다.
5. STT의 파일 상한과 별도로 전체 업로드·응답 수신 시간을 제한하고 응답 바이트 상한을 둔다.
   청크가 계속 도착한다는 이유로 무한 대기하지 않는다.

### 입력·원문·참조

1. L1의 `tech_stack`은 기술명 목록이다. 여러 기술을 설명문 하나로 합치지 않는다.
   근거와 확인 한계는 `basis`·`limitations`에 둔다. 공고와의 매칭에서 부분 문자열을 임의로 추측하지 않는다.
2. 답변 분석의 `technical_assessment.evidence_refs`와 `claim_checks.evidence_refs`는
   입력에 등록된 코드 Evidence의 ID만 참조한다. 문서 Claim·시각 해석·주장 대조·외부 참고 자료의
   `source_id`를 코드 Evidence ID로 바꾸지 않는다. 해당 자료는 별도 종류와 한계를 유지한다.
   출력 스키마와 의미 검증 양쪽에서 실제 허용 ID를 검사한다.
   일반 설계·개념 판단은 `technical_assessment`에 두고 코드 사실 판정과 구분한다.
   사실 판정에는 직접적인 등록 근거를, 미확인 주장에는 구체적인 한계를 요구한다.
3. 같은 파일의 다른 구간을 캐시에서 읽을 때 원본 SHA·본문 해시·확보 범위를 확인한다.
   앞부분만 읽은 결과를 전체 파일로 재사용하지 않는다.
4. 이미지 공고는 제한된 Wanted 출처의 본문 이미지만 수집하고 기존 Vision 경로로 전사한다.
   추출한 구조화 항목은 실제 전사 문장·위치를 참조해야 한다. 이미지와 구조화 원문의 충돌은 보존한다.
5. 문서 주장 대조 결과는 문서의 주장 버전과 코드 Evidence에 연결하는 별도 해석이다.
   개인 역할·성과를 코드 존재로 확인하지 않는다. 새 실행이 과거 질문의 참조를 덮어쓰지 않는다.

### 답변 분석의 생성 표현

1. `answer_analysis_v6`는 모델 전용 표현과 저장용 `AnswerAnalysis`를 분리한다.
   충분성·충족 항목·부족 항목·판단 상태·한계를 하나의 구조로 생성해 서로 모순되는 조합을 제한한다.
   필수 항목은 실제 질문의 고정 key만 사용한다. 보류한 항목을 부족으로 자동 바꾸지 않는다.
2. 서버는 현재 답변을 정확한 문자 위치의 원문 구간으로 나누고 ID를 부여한다.
   모델이 선택한 ID를 해당 원문으로 복원하며 문장을 고치거나 실제 답변에 없는 인용을 만들지 않는다.
   구간은 최대 128개이고 마지막 구간에는 남은 원문 전체를 유지한다. 전체 입력 상한도 계속 적용한다.
3. 기여를 모른다는 사유는 모델이 명시한 문장을 그대로 한계에 전달한다.
   조회 필요 flag는 실제 요청 배열의 유무에서 정한다. 표현을 변환하면서 판정값·요청·원문을 교정하지 않는다.
4. 생성 표현 복원 뒤 기존 의미 검증을 그대로 적용한다. 의미 실패는 재호출하지 않는다.
   모델의 감사용 raw 출력은 변형하지 않고, 과거 분석을 다시 읽을 때 당시 prompt 버전과 답변·질문으로 복원한다.
5. 생성 스키마는 [Structured Outputs의 지원 범위](https://developers.openai.com/api/docs/guides/structured-outputs)를
   참고하되 실제 Elice 연결의 호환성을 별도로 확인한다. 공급자에 보장되지 않은 조건은 서버 검증으로 유지한다.
   API 수신 성공을 원문의 사실성·평가 기준 타당성의 승인으로 해석하지 않는다.

### 면접 종료와 복구

1. 진행 중 또는 준비 실패 면접의 중단은 기존 API 계약을 따른다.
   DB 행 잠금으로 상태·중단 당시 턴을 확정하고 WS 실행권을 철회한다.
   늦게 도착한 답변·모델 결과가 중단 상태를 되돌리지 못하게 한다.
2. 실패한 의미 검증을 무시하거나 같은 질문에 모델을 반복 호출해 성공 결과만 고르지 않는다.
   중단·새 면접 재도전은 별도 사용자 행동이며 이전 실패 기록을 보존한다.
3. 마지막 답변 뒤에는 새로운 외부 검색이나 추가 질문을 시작하지 않는다.
   미실행 검색 요청은 명시적인 상태·한계로 남기고 종료·리포트에 전달한다.

### 리포트 이의 제기와 재평가

1. 리포트 생성 요청의 실행권은 PostgreSQL에서 관리하고 Redis 전달과 분리한다.
   전달 실패·취소를 기록하되 이미 실행 중인 worker의 권한을 다른 정리 작업이 빼앗지 않는다.
   실패한 최초 생성의 명시적 재시도와 성공 리포트의 재평가를 구분한다.
2. 리포트는 `revision`을 가지며 재평가 전후의 점수·피드백·근거·모델/프롬프트·입력 지문을 보존한다.
   새 결과는 기대 revision과 입력 상태가 일치할 때만 현재 결과를 바꾼다.
3. 이의 제기는 작성 당시 revision에 연결한다. 운영자는 검토자·사유·시각을 남기고,
   별도의 명시적 재평가 명령으로 새 생성 요청을 만든다. 기본 CLI 동작은 dry run이다.
4. 이의 내용이나 운영자의 검토 사유를 채점 정답으로 자동 주입하지 않는다.
   종료된 원문·답변 분석과 현재 rubric·prompt로 재평가한다. 이전과 같은 결과도 정상이다.
5. 프로필 요약은 입력 지문을 확인해 새로운 답변·프롬프트에 뒤처진 결과를 재사용하지 않는다.
   모델 실행 중 입력이 바뀌면 이전 결과를 덮어쓰지 않는다.

### 평가와 TTS의 완료 조건

1. 평가 실행기는 서비스 호출 예산과 Judge 호출 예산을 분리한다.
   Judge에는 허용·금지 기준과 단일 출력만 전달하고 control 정답 종류·검수 메타데이터를 숨긴다.
2. 승인된 기존 control만으로 Judge를 교정할 수 있지만, 서비스 입력이 없는 사례를 실행한 것처럼 기록하지 않는다.
   미검수 사례는 품질 분모에서 제외하고 사람 기준·교정·운영 임계값 승인 전 release gate는 미확정으로 둔다.
3. TTS는 Google Cloud Chirp 3 HD와 Persona별 음성 설정을 유지한다.
   실제 TTS 호출·음질·결제 검증은 사용자의 명시적 요청에 따라 후속 작업으로 남긴다.
   로컬 예산 제한을 공급자의 영구 무료 보장으로 설명하지 않는다.

## 영향과 대체 관계

이 제안은 원문·기여 추정 금지, 단일 Director, 의미 실패 비재시도와 초기 설계 보존 원칙을 유지한다.
모델·프롬프트 변경에는 새 immutable 버전을 사용하며 이전 저장 행을 일괄 재작성하지 않는다.
BE의 리포트·프로필 영구 모델과 API 응답, FE의 이의 제기·재시도 화면에 영향이 있다.
게시할 때 공통 구현·공유 계약·계약 대응 구현을 나누어 검토한다. 이 문서는 병합·배포 승인을 뜻하지 않는다.
