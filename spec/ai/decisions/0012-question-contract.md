## 결정과 이유

질문의 목적과 답변에서 확인할 내용을 담는 Question Contract는 **해당 질문의 `interview_turns` 행에 JSONB로 함께 보관**한다. 별도 평가 기준 테이블은 만들지 않는다. JSON 저장 형식은 기존 [DB 규약](../../../backend/docs/db-schema.md)을 따른다.

질문과 당시 기준을 한곳에서 조회할 수 있고, 별도 테이블·연결·독립 관리 절차가 필요하지 않아 현재 요구사항에 적합하다. 대안인 별도 테이블 방식은 기준을 독립적으로 관리해야 할 때 유용하지만, 현재는 그런 요구가 없다.

기존 원칙대로 질문·기준·Persona는 사용자에게 질문을 전달하기 전에 함께 확정한다. 답변을 본 뒤 평가 목적이나 필수 확인내용을 소급 변경하지 않는다. 리포트와 답변 분석은 해당 질문에 확정된 기준을 참조한다.

## 추가 결정: 다섯 내용 항목 유지

2026-09-21 사용자 선택에 따라 기존 제안의 다섯 항목을 구분해서 보관한다.

| 항목 | 필드 | 의미 |
| --- | --- | --- |
| 질문 목적 | `purpose` | 무엇을 확인하려는 질문인지 |
| 필수 확인내용 | `required_points` | 실제 질문에서 설명을 요청한 사항 |
| 가정 | `assumptions` | 질문에 명시한 조건; 관찰된 사실과 구분 |
| 근거 | `basis_refs` | 질문의 전제를 뒷받침하는 코드·자료 참조 |
| 평가 범위 | `evaluation_scope` | 확인내용 중 평가할 범위와 제외할 내용 |

가정과 평가 범위를 확인내용에 합치는 세 항목 방식도 검토했으나, 구분해서 기록하면 가정을 관찰 사실처럼 사용했는지와 질문에 없는 기준을 적용했는지 확인하기 쉽다. 이 구성은 별도 테이블이나 추가 모델 호출을 요구하지 않는다.

`evaluation_scope`는 실제 질문에서 요청한 내용 안에서 평가 범위를 명확히 한다. 질문에 없는 요구를 추가하는 용도로 사용하지 않는다. 가정은 코드 근거를 대신하지 않으며, 근거 참조만으로 확인하지 않은 사실을 확정하지 않는다. 다섯 항목을 둔다는 이유로 없는 가정·근거를 만들어 채우지 않는다.

## 추가 결정: 근거는 연결 정보만 저장

2026-09-21 사용자 선택에 따라 Question Contract의 `basis_refs`에는 출처 종류와 저장된 자료 ID 등 연결 정보만 둔다. 근거 본문이나 인용문을 질문 기록에 중복 복사하지 않고, 필요한 내용은 연결된 자료에서 읽는다. 코드 근거·공고 자료·이전 답변처럼 출처를 구분하며, 모든 출처를 코드 Evidence ID로 취급하지 않는다.

연결 대상은 질문에 사용한 면접 당시 자료 버전을 가리켜야 한다. 같은 URL의 공고가 갱신되거나 저장소에 새 commit이 생겨도 이미 확정한 질문의 근거를 최신 자료로 바꾸지 않는다. 코드 근거는 기존 Evidence의 고정 ref와 보존 원문을 이용한다. 이 결정은 기존 Evidence의 원문 보존을 없애는 것이 아니다.

연결 정보와 인용문을 함께 저장하는 대안보다 본문 중복과 관리 지점을 줄일 수 있어 이 방식을 선택했다. 자료 ID가 당시 내용을 계속 가리키는지 실제 저장 경계에서 검증한다. 이 선택 당시 남아 있던 공고 갱신의 보존 방식은 아래 후속 결정으로 정했다.

출처 종류와 ID 형식은 아래 최종 저장 형식에서 후속 확정했다. 공고 갱신의 세부 저장 제약은 AI-L02에서 AI-L03·AI-L12와 함께 정한다. 자료 보존기간·삭제와 분석·리포트에 미치는 영향은 AI-L18에서 정하며, 이번 결정을 무기한 원문 보관이나 새 이력 테이블 승인으로 해석하지 않는다.

## 추가 결정: 공고 내용이 바뀌면 새 자료 ID 부여

2026-09-21 사용자 선택에 따라, 같은 URL의 공고라도 재조회한 내용이 달라지면 **새 `job_postings` 자료 ID로 저장**한다. 내용이 같으면 기존 자료를 재사용한다. 연결 정보에 공고 ID와 별도의 자료 버전번호를 함께 요구하는 방식은 채택하지 않는다.

- 이전 공고와 그 `jd_requirements`를 갱신본으로 덮어쓰거나 삭제 후 재삽입하지 않는다. 변경된 공고의 요구사항은 새 공고 자료에 연결된 별도 ID로 저장한다.
- 이미 생성된 면접과 그 질문·리포트는 당시 공고·요구사항 ID를 계속 참조한다. 새 면접도 해당 분석 run에 확정된 자료를 사용하며, 기존 run의 참조를 최신 공고로 소급 변경하지 않는다.
- 새 분석 run은 normalized Wanted URL로 재사용 가능한 현재 자료를 찾는다. 기존의 성공본·`fetched_at` 기준 24시간 TTL은 유지하며, 재조회 시 동일 내용 재사용 또는 변경 내용의 새 ID 생성을 적용한다.
- 이 방식은 자료 ID 자체가 당시 내용을 식별하므로 질문의 근거 연결을 단순하게 유지한다. 별도 이력 테이블이나 질문별 공고 본문 복사본은 추가하지 않는다.
- 내용 동일성의 비교 필드·정규화, 재확인 시각의 저장·갱신 방식, 동시 수집의 중복 방지 제약은 AI-L02·AI-L03·AI-L12에 남는다. 기록 형식의 `schema_version`은 자료 ID와 별개의 개념이다.

이 결정은 공고 갱신과 그 요구사항 연결에 적용한다. 코드 Evidence의 고정 ref·원문 보존과 확정 답변 원문 보존은 기존 정책을 유지하며, 자료 삭제·보존기간은 AI-L18에서 정한다.

## 추가 결정: 최종 저장 형식 v1

2026-09-21 사용자 승인에 따라 `interview_turns.question_contract` JSONB에 다음 형식으로 보관한다. 다섯 내용 항목에 형식 버전만 추가하며, 아래 모든 필드는 항상 존재하고 `null`을 허용하지 않는다.

| 필드 | 형식과 조건 |
| --- | --- |
| `schema_version` | 정수 `1`; 자료·prompt 버전과 별개인 기록 형식 버전 |
| `purpose` | 비어 있지 않은 문자열 |
| `required_points` | `{key, description}` 객체 목록. 최소 1개이며 두 값은 비어 있지 않은 문자열, `key`는 질문 안에서 고유 |
| `assumptions` | 비어 있지 않은 문자열의 목록. 명시한 가정이 없으면 `[]` |
| `basis_refs` | `{kind, id}` 객체 목록. `kind`는 아래 네 종류, `id`는 저장된 자료의 UUID 문자열. 같은 `(kind, id)` 중복 금지 |
| `evaluation_scope` | 비어 있지 않은 문자열 |

빈 문자열에는 공백만 있는 값도 포함한다. 필수 필드 누락·`null`·타입 불일치·알 수 없는 필드는 형식 오류로 처리하며, 임의 기본값으로 보충하지 않는다. `key`, `description`, `kind`, `id`도 각각의 객체에 필수다.

| 근거 종류 `kind` | 참조 대상과 유효 범위 |
| --- | --- |
| `evidence` | 저장된 Evidence. 현재 선택 repo·고정 ref·권한과 일치하는 코드 또는 허용 자료 |
| `jd_requirement` | 해당 run·면접에 확정된 공고 자료의 요구사항 |
| `job_posting` | 해당 run·면접에 확정된 공고 자료 자체 |
| `answer_turn` | 같은 면접의 이전 Turn에 제출·저장된 답변. 이후 답변·현재 질문의 미제출 답변은 제외 |

`basis_refs: []`는 일반 HR 질문 등 기존 정책상 사실 근거 없이 성립하는 질문에만 허용한다. 조회 실패·자료 유실·필수 근거 누락을 빈 목록으로 숨기지 않는다. 자료 ID의 존재·소유권·허용 범위는 BE가 검증하며, Tool의 임시 참조는 실제 저장 ID로 바꾼 뒤 최종 기록을 확정한다. 전달 후 확인항목의 `key`를 바꾸지 않고 평가·리포트에서 같은 항목을 참조한다.

이 형식은 최종 저장본에 적용한다. 모델 원시 출력·Question 전체·ToolResult·공개 API의 형식을 일괄 승인하지 않는다. 문자열 길이·목록 개수 등 운영 상한은 AI-L04에서 정하며, 상한 미정이 무제한 실행을 허용하는 것은 아니다.

## 영향과 남은 결정

- Question Contract의 최종 저장 형식 v1과 공고 변경 시 새 자료 ID 부여를 확정한다. 나머지 AI 객체의 계약, 공고 갱신의 세부 저장 제약과 공개 변환은 AI-L02에서 계속 검토하며 운영 상한은 AI-L04에 남는다.
- AnswerAnalysis, DirectorDecision, Evidence/ToolResult, feedback의 상세 저장 계약과 공개 변환은 이번 결정에 포함하지 않는다.
- AI 계약·면접·Context·리포트 명세와 BE DB 안내에 같은 저장 위치를 반영한다. 실제 DB migration·타입·서비스 코드는 구현하지 않았다.
- 향후 구현 검증에서는 질문과 기준이 함께 저장되는지, 다섯 항목이 구분되는지, 가정과 관찰 사실이 섞이지 않는지, 평가 범위가 질문의 요구를 넘지 않는지, 전달 후 기준이 바뀌지 않는지 확인한다. 답변 분석과 리포트는 같은 확정 기준을 참조해야 한다. 이번 문서 기록은 팀 검수나 구현 검증 완료를 대신하지 않는다.
- 근거 연결은 현재 권한·면접 범위와 자료 버전을 검증한다. 원본이 갱신되어도 당시 자료를 조회하는지, 자료 유실을 빈 근거나 최신 자료로 숨기지 않는지, 질문 기록에 근거 본문을 중복 저장하지 않는지도 확인한다.
- 공고 재조회 검증에서는 동일 내용의 ID 재사용, 변경 내용의 새 ID, 이전 공고·요구사항·면접·run 참조 보존을 확인한다. 기존 `jd_fetch.py`의 7일 TTL·요구사항 삭제 후 재삽입 주석은 현재 구현 기준으로 사용하지 않는다.
- 저장 형식 검증에서는 필수 필드·버전·타입·빈 값, 확인항목의 고유 key, 근거 종류·ID·중복·권한·범위와 임시 참조 변환을 확인한다. 근거가 필요 없는 질문의 빈 목록과 근거 조회 실패를 구분한다.

## 대체 관계

기존 AI-L02와 내부 계약의 Question Contract 저장 위치 보류를 해소한 뒤, 같은 날 후속 선택으로 다섯 내용 항목·근거 연결 정보만 저장·공고 변경 시 새 자료 ID 부여·최종 저장 형식 v1을 채택했다. 질문 내용과 평가 기준을 함께 확정한다는 기존 정책을 유지하며, 나머지 Proposed 계약의 승인을 뜻하지 않는다.
