# 0031 최종 AI 서비스의 원문·실행·외부 공급자 경계

- 상태: Proposed — 사용자 요청에 따른 로컬 통합 기준. 공유 계약·운영 조건의 팀 합의는 별도 검토한다.
- 날짜: 2026-11-07
- 관련 PR: 이번 신규 변경은 미게시. 선행 PR의 승인 범위를 이번 확장의 승인으로 해석하지 않는다.
- 관련 이슈: [#110](https://github.com/kakaotechcampus-4/ktc4-chonnam-3/issues/110), [#195](https://github.com/kakaotechcampus-4/ktc4-chonnam-3/issues/195)
- 검토자: BE·FE·AI 공유 계약과 운영 담당자 확인 대기
- 구현·검증 현황: [단일 구현 기록](../implementation.md)

## 맥락

최종 서비스에서는 레포·공고·선택 문서·면접 답변을 연결하고, 필요한 경우 외부 자료와 음성을 사용한다.
파일명이 익숙하다는 이유로 특정 레포 구조를 가정하거나, 문서에 적힌 주장을 실제 기여로 확정하면
근거를 추적할 수 없다. 반대로 선택 공급자의 장애가 이미 확보한 원문까지 무효화해서도 안 된다.

기존 독립 AI 모듈의 계약은 실제 수집·권한·저장·재시도·음성 재생까지 보장하지 않는다.
따라서 원문과 해석, 현재 모델 입력과 과거 참조, 내부 실행 정책과 공유 API 변경을 구분한다.

## 결정

### 1. 실제 구조를 입력하고 읽은 범위를 보존한다

- 레포의 실제 트리·기본 분석에서 읽을 파일을 선정하고, 서버가 허용 경로·버전·예산을 검사해 원문을 수집한다.
  특정 프로젝트의 파일명이나 디렉터리를 보편적인 정답으로 고정하지 않는다.
- 지원 범위의 텍스트를 공통 입력으로 사용한다. 전체 파일의 Python·JSON·TOML에는 정적 구조 해석을 보조하고,
  전용 해석기가 없거나 부분 구간만 확보한 자료는 원문 구간과 해당 한계를 전달한다.
  구문 해석은 실행 결과·설정 효과·동적 호출 관계의 검증을 뜻하지 않는다.
- 큰 파일과 여러 모듈은 호출·바이트·시간 상한 안에서 나누어 읽는다. 파일 버전과 원래 줄 번호를 유지하고,
  미수집·부분 수집 범위를 결과에 남긴다. 추가 수집도 서버가 정한 보완 절차와 예산을 따른다.
- 레포 분석·재조회는 단일 Director의 Tool로 연결한다. 별도의 자율 레포 분석 Agent는 추가하지 않는다.

### 2. 선택 문서의 원문·주장·시각 해석을 분리한다

- 화면용 preview와 근거용 추출 원문을 분리한다. 근거용 snapshot에는 원본 파일 해시, 보존 텍스트 해시,
  추출 방식, 페이지·줄·가능한 좌표, 축약·누락 한계를 결합한다. 파일 바이너리 보관과 동일시하지 않는다.
- Native 추출을 먼저 사용하고, 설정된 Vision 경로에서 텍스트가 없는 영역과 혼합 PDF의 표·이미지를 보완한다.
  같은 페이지에 native 문장이 있다는 이유로 다른 영역의 전사를 버리지 않는다.
  공급자 실패 시 확보한 native 결과와 실패 한계를 보존한다.
- OCR 전사는 원문 후보이며, VLM의 생성 설명은 별도의 시각 해석이다. 생성 설명을 전사·개인 기여·성과로
  승격하지 않는다. 읽지 못한 영역과 위치 불명확성을 모델 입력에서도 유지한다.
- Claim은 선택한 문서의 저장 텍스트 버전에서 추출한 **미검증 주장**이다. 원문 구간에 연결하되 진위를 확정하지 않는다.
  답변의 `claim_checks`는 계속 현재 답변을 검증한다. 문서 문장을 답변 인용으로 바꾸어 넣지 않는다.
- 재사용은 원문 버전과 추출 prompt 버전을 확인한다. 현재 Claim 집합과 과거 질문에서 참조한 집합을 구분하며,
  재추출 때 과거 근거를 삭제하거나 현재 분석 결과인 것처럼 섞지 않는다.
- 문서 추출의 실패·진행 중·정상 빈 결과를 구분한다. 실패한 추출이나 미확인 영역을 지원자의 감점 근거로 쓰지 않는다.

### 3. 자소서와 포트폴리오를 각각 명시적으로 선택한다

- `POST /documents/preview`에 선택 필드 `docType`을 제안한다.
  값은 `portfolio` 또는 `cover_letter`, 생략 시 기존 동작인 `portfolio`다.
- `POST /analysis-runs`의 기존 `documentId`는 포트폴리오로 유지하고,
  선택 필드 `coverLetterDocumentId`로 자소서를 따로 전달한다.
- BE는 두 ID의 소유자·문서 종류·추출 상태를 각각 검사한다. 최근 업로드 문서를 임의로 선택하지 않는다.
  자소서 ID가 달라지면 분석 입력의 중복 판정도 달라져야 한다.
- 자소서와 포트폴리오는 면접 Claim의 입력이 될 수 있다. 레포 추천의 `portfolio_mentioned` 힌트는
  기존 포트폴리오 경로를 유지해 자소서에 있는 URL이 같은 신호로 섞이지 않게 한다.
- 이는 로컬에서 함께 검토할 신규 공유 계약이다. 사용자 구현 요청을 FE·BE 팀의 계약 합의 완료로 기록하지 않는다.
  이미지·슬라이드 형식의 API 지원과 화면의 공식 업로드 형식 확대도 구분한다.

### 4. 외부 자료는 검증 Tool의 제한된 입력으로 사용한다

- LLM 내장 지식을 실시간 검색 결과로 취급하지 않는다. 검증된 T3의 검색 요청을 서버 Tool이 받아
  Tavily Search·Extract로 공식 출처 범위의 자료를 확인한다.
- 검색 요약과 수집 원문을 구분하고 URL·위치·본문 해시·수집 시점·공개 시점의 유무·검색 상태·한계를 전달한다.
  검색 성공 자체를 답변의 정답 판정이나 개인 성과의 증명으로 사용하지 않는다.
- 검색 질의는 필요한 개념으로 제한한다. URL 원문·코드·비밀값·이메일 등 금지 패턴은 전송 전에 거절한다.
  패턴 검사가 모든 개인정보를 탐지한다는 보장은 없으므로 문서·답변 원문을 통째로 질의로 전달하지 않는다.
- 작업별 호출·credit 상한과 면접 전체 상한을 따로 적용하고 DB에서 예약한다.
  캐시 적중은 외부 호출 예산을 다시 쓰지 않으며, 같은 본문을 재확인한 사실과 질의별 캐시 연결을 구분한다.
  TTL은 검색 재확인 정책이며 출처 내용의 정확성·최신성을 보증하지 않는다.
- 저장된 전체 근거를 매번 모델에 보내지 않는다. 문서별·외부 자료별로 유한한 입력 예산을 배분하고,
  과거 질문의 근거 복원용 전체 조회는 현재 모델 Context와 분리한다.

### 5. 확정 질문·답변·평가 기회를 구분한다

- 질문 후보 생성·검토가 끝나 저장한 계약만 실제 면접 이력에 반영한다.
  모델 출력·Tool 결과는 현재 턴·준비 작업의 소유권을 다시 확인한 뒤 저장하며, 외부 호출 동안 DB 잠금을 유지하지 않는다.
- `evaluation_keys`는 그 질문에서 제공할 평가 기회다. 확정 질문의 선언으로 다음 질문을 배정하되,
  질문했다는 사실을 답변 관찰·평가 가능·점수 획득으로 바꾸지 않는다.
- 이 배정 규칙은 내부 실행 정책이다. 각 질문이 해당 역량을 타당하게 측정한다는 연구·품질 검증이나
  [#110](https://github.com/kakaotechcampus-4/ktc4-chonnam-3/issues/110)의 평가 체계 전체 완료를 뜻하지 않는다.
- 리포트는 관찰·미관찰·평가 불가를 구분하고 근거가 없는 평가를 생성하지 않는다.
  [#195](https://github.com/kakaotechcampus-4/ktc4-chonnam-3/issues/195)의 공개 점수 필드 nullable 확대는
  별도 공유 계약 합의 대상이다. 이 ADR로 `NA`를 임의의 0점이나 확정 점수로 바꾸는 정책을 승인하지 않는다.

### 6. 음성 공급자와 무료 예산을 명시한다

- STT와 문서 Vision은 사용 가능한 Elice MLAPI 공급자를 우선 연결하고,
  주소·키·모델·요청 형식·실제 응답을 환경별로 확인한다. 설정만으로 실서비스 호환성을 판정하지 않는다.
- TTS는 사용자가 선택한 Google Cloud 한국어 Chirp 3 HD를 대상으로 한다.
  `tech_lead`·`domain_lead`·`hr_manager` 각각의 음성 ID를 명시 설정할 수 있게 하고,
  음성 누락·지원 밖 조합을 다른 목소리로 조용히 대체하지 않는다.
- 확정 질문·persona·음성·언어·형식이 같은 재생은 캐시를 재사용하고 동시 생성을 제한한다.
  TTS 장애 시 질문 텍스트를 보존하며, 음성의 부재를 답변 평가로 전파하지 않는다.
- 무료 한도 내 사용을 위해 프로젝트·월별 문자 예산을 서버가 먼저 예약한다.
  Redis 초기화·재시작·월 전환을 새로운 무료량의 증명으로 보지 않고,
  운영자가 실제 Cloud 잔여량을 확인해 명시적으로 초기화한다.
  과금 여부가 불명확한 호출을 자동 환급하거나 유료 음성·다른 공급자로 자동 전환하지 않는다.
- 이 예산은 같은 Cloud 프로젝트의 다른 앱 사용량까지 관측하지 못한다.
  사용자 OAuth 요청에는 [공식 quota 프로젝트 헤더](https://docs.cloud.google.com/docs/quotas/set-quota-project)를
  명시해 예산 대상 프로젝트와 맞춘다. API 키의 소속 프로젝트도 운영자가 확인한다.
  Cloud 권한·결제·실제 무료 조건 확인과 음질 검수는 별도 운영 조건이다. 영구 무료나 실제 비용 0원을 보증하지 않는다.
- 명시적인 질문 재청취 요청은 답변 저장·턴 진행과 분리한다. 정상적인 “모르겠습니다”는 답변으로 남기며,
  지원 문법 밖의 모든 자유 발화를 이해한다고 가정하지 않는다.

### 7. 평가 실행 가능성과 평가 타당성의 승인을 구분한다

- 평가 입력·모델 출력·정답/금지 조건·검수 상태를 분리한다. 실행기는 정답을 모델 입력에 섞지 않는다.
  prompt·model·입출력 해시·시도·실패 단계·token·지연을 실행 결과에 남긴다.
- 검수 전 사례와 invalid 사례를 승인된 품질 평가의 분모로 합산하지 않는다.
  채점기 control 결과, 서비스 출력의 판정, 리포트의 결정적 검사를 구분한다.
- 비용표가 없으면 비용을 0달러로 기록하지 않고 미설정으로 남긴다.
  실행 성공만으로 release gate를 통과시키지 않는다.
- LLM-as-a-Judge를 도입하려면 독립 기준의 근거, 사람 검수 정답, 오수락·오거절 측정과 교정이 필요하다.
  이 실행 경계가 #110의 전체 기준 확정·데이터셋 검수·운영 품질 승인을 대신하지 않는다.

### 8. 모델 전송과 환경별 활성화를 명시한다

- 실행 task의 본문·버전은 `ai/prompts/runtime-prompts.json`에서 선택하고 모델·호출 상한은
  환경 설정으로 결합한다. manifest 생성과 DB 등록·활성화(`--apply`)를 구분하며,
  같은 task/version의 모델·본문 변경은 충돌로 거절한다. 모델·본문을 바꾸면 새 버전을 사용한다.
- 선택한 공급자가 지원할 때 `LLM_STREAM`과 `LLM_REASONING_EFFORT`를 명시한다.
  [Responses SSE 계약](https://developers.openai.com/api/docs/guides/streaming-responses)에 따라
  전체 이벤트를 수신해 유일한 완료 이벤트와 상태를 확인하고 기존 schema·의미 검증을 적용한다.
  델타·끊긴 프레임·실패 이벤트를 성공 후보로 발행하지 않는다.
- 스트리밍에서도 동일한 총 응답 바이트·시간·시도 예산을 적용한다. 전송 방식 변경을 FE 토큰 스트림,
  추가 Agent, 모델 출력의 무검증 저장으로 확대하지 않는다.
- 프롬프트 파일을 배포 이미지에 포함한다. 명시적 활성화와 실제 API 연결 성공은 사람 검수·품질 승인과 별개다.

## 이유와 영향

기존 수집·AI 계약·Director·저장 계층을 재사용하면 중복 Agent나 추출기를 만들지 않고 실제 서비스 경로를 연결할 수 있다.
원문과 생성 해석을 분리하면 안전한 재질문과 과거 근거 복원이 가능하지만, 검증된 내용만 입력하므로 일부 자료는
미확인·부분 분석으로 남는다. 유한한 공급자 예산은 호출 실패를 만들 수 있으며 그 상태도 사용자 평가와 구분해야 한다.

BE에는 문서·외부 근거의 버전 및 선택 ID 저장, 마이그레이션, 작업 소유권과 취소 처리가 영향을 준다.
AI에는 근거 종류·범위·평가 기회의 내부 계약이, FE에는 문서 선택과 음성 실패 시 표시가 영향을 준다.
공유 API 계약은 관련 팀의 검토 후 채택하며, 게시 시 명세 변경과 대응 구현을 분리한다.

운영 활성화 전에는 실제 공급자 인증·예산·prompt 등록·최종 서비스 통합을 검증한다.
되돌릴 때는 추가 선택 입력·공급자를 비활성화하되 이미 확정한 질문과 그 근거를 파괴하는 삭제·재계산을 하지 않는다.

## 대체 관계
