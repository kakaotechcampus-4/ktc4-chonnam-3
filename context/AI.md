# DEVON 통합 기준서 · 개정 2
## 서비스 기획 · 아키텍처 설계 · 평가기준 · 평가 데이터셋

**문서 목적:** 팀이 같은 서비스 범위, 처리 규칙, 결과물, 검증 기준으로 개발하도록 정리한다. 구현 완료나 성능 검증을 보고하는 문서는 아니다.

**이번 개정의 핵심:** 음성면접을 핵심단계에서 후속단계로 이동한다. 세 면접관, 답변에 따른 다음 행동, 자료 조회, 문답 기록, 종합·면접관별 피드백은 핵심단계에 유지한다.

**핵심단계의 입출력에 대한 적용안:** 화면에 질문을 표시하고 사용자가 텍스트 답변을 제출하는 방식으로 전체 면접을 먼저 완성한다. 사용자가 이번에 확정한 것은 ‘음성의 후속단계 이동’이며, 텍스트 문답은 그 변경을 실제 개발 흐름으로 연결하기 위해 본 문서에서 제시하는 적용안이다. 이하 핵심단계 설명은 이 적용안을 전제로 한다.

# 0. 이번 개정에서 달라지는 것

| 구분 | 기존 통합 문서 | 이번 개정안 |
|---|---|---|
| 핵심 면접의 입출력 | 질문 음성 재생·음성 답변·STT를 필수로 연결 | 질문 표시·텍스트 답변 제출로 면접 완주 |
| 음성 기능 | 핵심단계의 완료 조건 | 후속단계에서 녹음·STT·TTS·목소리 연결 추가 |
| 세 면접관 | 역할·화면·음성·기록·피드백 연결 | 역할·화면·기록·피드백은 핵심, 음성 연결은 후속 |
| 시작 조건 | 자료 준비와 마이크·재생 점검 | 핵심은 자료 준비·입력 가능 여부, 음성 이용 시 장치 점검 추가 |
| 답변 기록 | 음성에서 확정한 전사문 중심 | 제출된 답변 본문을 공통 기준으로 관리하고 입력 출처 구분 |
| 평가·데이터셋 | 음성 전체 경로를 핵심 검증에 포함 | 공통 의미·진행 검증을 먼저 하고 음성 검증을 후속에 추가 |

**면접 자체를 뒤로 미루는 것이 아니라, 면접의 음성 입출력을 뒤로 미룬다.** 핵심단계에서도 질문에 답하고, 그 답변에 따라 다음 질문이 달라지며, 종료 후 피드백을 확인할 수 있어야 한다.

이 적용안을 채택하면 기존의 ‘텍스트 문답은 시험에만 사용하고 서비스에는 제공하지 않는다’는 문구도 수정해야 한다. 다만 이는 **면접 답변 입력**의 변경이지, 제거한 **JD 본문 직접 입력**을 다시 추가하는 결정은 아니다. 전체·기술집중 등 면접 진행 모드 선택도 추가하지 않는다.

후속단계에서 텍스트와 음성을 동시에 제공할지, 면접 도중 전환할지는 별도 화면·운영 결정이다. 이번 문서에서 자동으로 확정하지 않는다. 기존 자료의 음성 필수 표현은 이번 요청으로 변경하고, 나머지 합의는 최신 Persona·Domain 보완안에 따라 유지한다. [자료 1] [자료 2] [자료 9] [자료 10]

# 1. 서비스 기획

## 1-1. 무엇을 만드는가?

**DEVON은 GitHub 프로젝트와 지원 공고를 바탕으로 세 명의 AI 면접관이 면접을 진행하고, 사용자의 답변에 따라 질문을 조정하며, 실제 문답과 근거에 연결된 피드백을 제공하는 개발자 면접 연습 서비스다.**

핵심단계에서는 자신의 경험과 판단을 글로 정리하여 설명하는 흐름을 제공한다. 후속단계에서는 동일한 면접 구조에 음성 입출력을 연결하여 말로 답하는 연습까지 확장한다.

목적은 예상 질문을 많이 생성하는 것이 아니다. 사용자가 본인 기여, 기술 선택, 문제 해결을 어디까지 설명했는지 확인하고, 설명이 부족한 부분을 다시 연습하게 하는 것이다. 핵심단계의 텍스트 평가 결과만으로 실제 발화 능력이 향상됐다고 주장하지 않는다.

취업 합격, 지원자 간 순위, 경력의 진위, 전체 개발 역량을 보장하는 서비스로 정의하지 않는다. 평가의 범위는 이번 면접에서 질문하고 관찰한 내용이다. 이러한 연습 목적과 자료·답변 중심 흐름은 기존 기획을 유지한다. [자료 1]

## 1-2. 무엇을 어느 단계에서 제공하는가?

| 영역 | 핵심단계 | 후속단계 |
|---|---|---|
| 계정·레포 | GitHub 로그인, Public 레포 일괄 연동·갱신, 기본 분석 | 기존 기능 유지 |
| 공고·면접 준비 | 공고 URL의 텍스트 본문 수집, 추천·선택, 선택 레포 정밀 분석 | 이미지에 있는 공고 내용 판독 추가 |
| 면접 진행 | 세 면접관의 텍스트 문답, 답변 평가, 근거 조회, 후속 질문·전환·종료 | 동일한 흐름에 음성 녹음·STT·TTS 추가 |
| 추가 경험·지식 | 레포·JD·현재 문답·확인된 본인 역할 사용 | 선택 문서의 Claim과 검수된 도메인 자료 연결 |
| 결과 | 질문·제출 답변 기록, 종합·면접관별 피드백 | 음성에서 확정한 답변과 추가 자료의 출처 연결 |
| 검증 | 자료·질문·답변·전략·상태·기록·리포트 검증 | 음성 오류·재생·판독·추가 자료 경로 검증 |

음성, 이미지 공고, 선택 문서, 도메인은 서로 다른 확장 기능이다. 하나가 준비되지 않았다는 이유로 나머지 기능까지 자동으로 준비 완료로 처리하지 않는다.

**현재 범위 밖:** 공고 자동 탐색·자동 지원, JD 본문 직접 입력, 공고 없이 진행, 면접 진행 모드 선택, 이력서·자소서 작성·첨삭, Private 레포, 기업 홈페이지 전체 조사, 레포 Snapshot·복원 기능. 음성 원본 장기 보관·다시 듣기는 별도 결정사항으로 남긴다. [자료 1] [자료 10]

## 1-3. 핵심단계의 이용 흐름

```text
GitHub 소셜로그인
→ ‘레포 연동하기’로 Public 레포 일괄 등록·갱신
→ 레포별 기본 분석
→ 공고 상세페이지 URL 입력
→ 공고 본문·직무 요구사항 확인
→ 관련 레포 추천
→ 사용자가 면접 대상 확정
→ 선택 레포 정밀 분석 또는 유효한 분석 재사용
→ 자료·본인 역할·준비상태 확인
→ 세 면접관의 질문 표시와 사용자 텍스트 답변 제출
→ 답변 평가·필요한 자료 조회·다음 행동 선택 반복
→ 면접 종료
→ 문답 기록과 종합·면접관별 피드백
```

후속단계의 선택 문서는 면접 준비정보에 추가하고, 도메인은 필요한 판단에서 조회한다. 음성은 질문을 전달하고 답변을 받는 입출력 부분에 연결한다. 이 때문에 후속 기능을 추가해도 면접의 평가·전략·기록을 처음부터 다시 만들 필요가 없도록 설계한다.

## 1-4. GitHub 로그인과 레포 일괄 연동

사용자는 GitHub 소셜로그인으로 서비스 계정을 연결한다. 로그인 자체와 레포 연동 요청은 구분하고, ‘레포 연동하기’를 누르면 허용된 범위의 레포를 일괄 등록한다.

연동 대상은 로그인 사용자의 소유·협업·조직 접근 관계가 있고 앱의 권한으로 조회 가능한 Public 레포다. GitHub 전체의 공개 레포를 수집하는 기능이 아니다. 조직의 레포에 접근할 수 있다는 사실도 개인 기여를 증명하지 않는다.

다시 연동하면 신규·변경사항을 반영한다. 반복 요청으로 같은 레포를 중복 등록하지 않고, 일시적인 조회 실패만으로 기존 면접 기록을 삭제하지 않는다. 레포별 분석 대기·진행·완료·실패 상태를 표시한다.

이 과정의 결과는 **사용자가 면접 대상으로 선택할 레포 목록과 추천에 사용할 기본 분석**이다. 등록 목록과 이번 면접에 사용할 프로젝트 선택을 구분하는 이유는 사용자가 매번 다른 직무와 경험을 중심으로 준비할 수 있기 때문이다. [자료 1]

## 1-5. 기본 분석과 정밀 분석

| 구분 | 기본 분석 | 정밀 분석 |
|---|---|---|
| 시작 시점 | 레포 연동·필요한 갱신 후 | 면접 대상 선택 후 |
| 목적 | JD와 비교할 추천 자료 준비 | 실제 구현 질문과 근거 준비 |
| 읽는 범위 | 설명·README·언어·의존성·상위 구조 | 지원 범위의 관련 코드·함수·설정·테스트 |
| 반환할 정보 | 프로젝트 목적·주요 기능·기술 관련성·확인 수준 | 구현 관찰·원문 위치·질문 관련 자료·분석 한계 |
| 사용처 | 레포 추천 | 면접 Context·Evidence 검색 |

기본 분석에서 원문에 언급된 내용과 실제 코드에서 확인한 내용을 구분한다. 정밀 분석도 지원 범위에서 읽은 코드에 대한 분석이며, 실제 배포 동작·성능·개인 작성자까지 자동 검증한 것이 아니다.

분석 결과는 저장하고, 분석한 코드와 분석 기준이 유효하면 재사용한다. 새 JD에서는 기존 분석 중 관련된 부분을 다시 선택한다. 필요한 내용이 부족하면 그 범위를 추가 확인하되, 공고가 달라졌다는 이유만으로 전체 정밀 분석을 반복하지 않는다.

선택 레포의 필수 분석이 끝나지 않았다면 준비 중 상태를 보여준다. 준비 미완료를 숨기고 일반 질문으로 대체하지 않으며, 분석 대기시간을 면접시간에 포함하지 않는다. 분석 재사용에 필요한 코드 식별정보와 분석 버전은 보관하되 별도의 전체 레포 Snapshot 서비스는 만들지 않는다. [자료 1]

## 1-6. 공고 분석과 프로젝트 추천

공고 수집기는 입력 URL에서 해당 공고의 본문을 확보한다. JD 분석기는 확보한 본문에서 담당업무·필수·우대·경력조건·기술·업무 분야를 구분하고 원문 위치나 구절을 연결한다.

페이지에 접속했다는 것과 공고의 핵심 내용을 확보했다는 것을 구분한다. 본문이 부족하면 정상 JD를 생성하지 않는다. 모든 사이트를 지원한다고 가정하지 않고, 수집을 검증한 페이지 유형부터 지원한다.

추천 기능은 JD와 기본 분석을 비교해 후보·관련성·추천 이유를 반환한다. 설명에는 실제로 확인한 정보만 사용하며, 분석이 끝나지 않은 레포를 관련성이 낮다고 판정하지 않는다. 사용자는 추천 이유를 확인한 뒤 다른 연동 레포를 선택할 수도 있다.

핵심단계에서는 텍스트로 핵심 본문을 확보할 수 있는 공고를 처리한다. 후속단계의 이미지 판독은 동일 URL 수집 경로를 확장한다. 읽지 못한 요건이나 해결되지 않은 핵심 충돌을 추측으로 채우지 않는다. **면접 답변을 텍스트로 받는 적용안과 JD를 텍스트로 직접 입력받는 기능은 별개다.** [자료 1] [자료 10]

## 1-7. 선택 문서와 Claim 활용 — 후속단계

문서 처리는 두 단계로 구분한다. 공통 추출기는 원문 텍스트·문서·페이지 또는 구획 위치·추출 상태를 반환한다. Claim 추출기는 그 원문에서 경험·기여·성과 주장, 주장 주체, 연결된 출처를 구조화한다.

**문장 내용은 어떤 주장이 적혔는지 파악하는 입력이며, 위치는 그 주장의 원문을 다시 확인하는 정보다.** 문단의 맥락을 잃지 않게 유지하고, 존재하지 않는 페이지나 문장을 만들어내지 않는다.

추출된 내용은 사용자가 확인·수정·제외한 뒤 면접에 반영한다. 이 확인은 추출 결과와 자료 사용 의사를 확인하는 것이지, 주장 자체가 객관적으로 입증됐다는 뜻은 아니다.

선택 문서가 없거나 처리에 실패한 경우 자료를 제외하고 핵심 면접을 진행할 수 있다. 이력서·자소서·포트폴리오를 새로 쓰거나 첨삭하는 기능으로 확대하지 않는다. [자료 1] [자료 7] [자료 8]

## 1-8. 세 면접관의 역할과 공유 정보

| 면접관 | 질문 책임 | 피드백의 중심 |
|---|---|---|
| **Manager** | 자기소개·지원동기·직무 연결·협업·의사소통 | 경험과 직무를 어떻게 연결하고 전달했는가 |
| **Senior Developer** | 직접 구현·디버깅·테스트·구체적인 문제 해결 | 실제 수행 내용을 얼마나 구체적으로 설명했는가 |
| **Tech Lead** | 기술 선택·대안·설계·성능·정합성·확장성 | 선택 이유와 한계를 어떤 조건에서 판단했는가 |

세 Persona는 독립된 면접 지휘자나 세 개의 상충하는 채점 체계가 아니다. 단일 Director가 다음 질문의 목적과 담당 면접관을 선택하고, 각 역할 설정을 질문 표현에 적용한다.

핵심단계부터 화면에 세 역할을 표시하고 현재 질문자를 구분한다. 확정한 면접관 식별정보를 질문·문답 기록·피드백에 연결한다. 후속단계에서 같은 식별정보에 고정된 TTS 목소리를 연결한다.

면접관 전환 후에도 이전 문답·기여 정정·확인한 내용·반복 횟수를 공유한다. 정상 면접 계획에는 세 관점을 반영하되 동일 발언 수나 고정 교대 순서를 강제하지 않는다. 사용자 종료나 상한에 도달하면 미관찰 영역을 남기고 종료한다. [자료 9]

## 1-9. 도메인 지식 활용 — 후속단계

도메인은 해당 직무의 업무 분야와 상황에 대한 참고지식이다. 공고의 담당업무를 근거로 관련 분야를 확인하고, 출처·버전·적용 조건을 검수한 자료에서 필요한 부분을 조회한다.

반환 결과에는 관련 내용뿐 아니라 어디에서 가져왔고 어떤 조건에 적용되는지를 포함한다. 자료가 없거나 업무 분야가 불명확하면 미지원·미확인으로 남긴다. 회사 업종만으로 특정 업무 질문을 강제하지 않는다.

자료는 질문의 상황을 구성하거나 기술적 판단을 검토할 때 사용한다. 질문에 적용한 가정은 사용자에게 제시하고 평가에도 동일하게 사용한다. 특정 제품의 방식을 모든 환경의 정답으로 일반화하지 않는다.

**외부 도메인 자료는 사용자 경험이나 지원 기업의 실제 구현을 증명하지 않는다.** 도메인 질문을 하지 않은 영역은 미평가로 남기며, 도메인 자료를 조회하지 않았다는 사실 자체를 사용자 점수에 반영하지 않는다. [자료 10]

## 1-10. 음성면접의 제공 범위 — 후속단계

음성면접은 핵심 문답 처리 앞뒤에 연결하는 입출력 기능으로 구현한다. 사용자는 검증된 질문을 해당 면접관의 목소리로 듣고, 답변 완료로 발화를 확정한다. STT가 음성을 문자로 변환하고, 확정한 전사문을 공통 답변 처리에 전달한다.

첫 음성면접 전에는 마이크 권한·음성 입력·질문 재생을 점검한다. TTS 생성이나 재생에 실패했다고 사용자 무응답으로 처리하지 않는다. 재시도에서는 질문·Persona를 유지하고 음성 처리만 다시 수행한다.

음성 데이터는 질문·녹음 시도·확정 답변과 연결한다. 이전 녹음의 결과가 늦게 도착해 현재 답변을 덮어쓰지 않아야 한다. 인식 오류가 확인되면 확인·정정 절차를 먼저 거친다.

목소리·억양·감정을 새로운 역량점수로 사용하지 않는다. 후속단계의 목표는 말하기 방식으로 같은 면접을 이용할 수 있게 하는 것이며, 음성 품질과 실제 연습 효과는 별도로 검증한다. 원음 장기 보관·다시 듣기와 텍스트 병행·전환 UI는 별도 결정한다. [자료 1] [자료 9]

## 1-11. 왜 Agent AI인가?

DEVON에서 적응적인 판단이 필요한 곳은 다음 면접 전략이다. 사용자 답변, 근거 조회 결과, 이미 확인한 내용, 남은 시간에 따라 보완·심화·조회·전환·종료 중 선택이 달라진다.

반면 파일 수집, 상태 저장, 권한 확인처럼 정해진 절차가 있는 일을 모두 자율 Agent로 만들 필요는 없다. 다음 전략은 Director가 선택하고, 허용 범위와 실행 순서는 코드로 제한한다.

따라서 음성을 뒤로 미루어도 Agent의 핵심은 유지된다. **Agent인 이유는 말로 대화하기 때문이 아니라, 문답과 도구 결과를 반영해 다음 행동을 다시 선택하기 때문이다.** 단순 예상 질문 생성과의 차별성도 준비·적응형 진행·근거 연결·복습을 하나의 서비스로 제공하는 데 있다. [자료 1] [자료 2]

# 2. 아키텍처 설계

## 2-1. 용어와 역할

| 용어 | 의미와 사용 목적 |
|---|---|
| **Analysis** | 면접 전 기본·정밀 분석. 추천과 질문 준비에 재사용한다. |
| **Evidence** | 면접 중 실제로 채택한 근거. 원문·출처·사용 목적을 연결한다. |
| **Context** | 현재 판단에 필요한 자료와 상태를 선별한 입력 묶음이다. |
| **Question Contract** | 해당 질문의 목적·필수 확인내용·필요한 가정이다. 답변 전에 확정한다. |
| **Turn / Session** | 질문 하나와 답변·판단이 Turn, 전체 면접이 Session이다. 미답변 질문도 기록할 수 있어야 한다. |
| **Agent** | 현재 상황과 도구 결과를 보고 다음 행동을 선택한다. DEVON의 중심은 Director다. |
| **Tool** | 요청받은 범위의 조회를 실행하고 결과·출처·상태를 반환한다. |
| **Pipeline** | 정해진 순서로 자료를 처리해 분석·리포트 등 결과를 만든다. |
| **Worker / 작업 큐** | Worker는 작업을 실행하는 프로그램이고, 큐는 실행할 작업을 전달·대기시키는 통로다. |
| **Adapter / Model Gateway** | 외부 API의 차이를 내부 형식으로 연결하고, 모델 호출의 버전·시간 제한·사용량을 관리하는 모듈이다. |

LLM을 호출한다는 이유만으로 모든 모듈을 Agent라고 부르지 않는다. 논리적인 책임을 구분하는 것이며, 각 항목을 별도 서버나 독립 LLM 호출로 구현해야 한다는 뜻은 아니다. [자료 2]

## 2-2. 웹 관점: 입력·요청·작업·결과를 연결한다

기존 통합 문서의 React·FastAPI·ARQ·Redis·PostgreSQL 구성을 유지한다. PostgreSQL 직접 운영과 Supabase PostgreSQL 중 실제 운영방식은 별도 선택한다. 이번 요청에서 프론트엔드 프레임워크나 DB 제품을 새로 변경하지 않는다. [자료 2]

```text
React 웹
질문·면접관 표시 / 텍스트 답변 제출 / 진행상태·기록·리포트
                 ↕ HTTPS API / SSE 알림
FastAPI
GitHub 로그인·권한 검사 / 요청 접수 / 상태·결과 조회
                 ↓ 작업 식별자 등록
Redis + ARQ
       ├─ 준비 Worker: 레포·공고 분석, 추천, 리포트
       └─ 면접 Worker: 답변 평가, Director, Tool, 질문 생성·검증
                 ↕
PostgreSQL: 확정 상태·문답·분석·근거·리포트
비공개 파일 저장소: 필요한 원문과 자료

후속 연결
준비 Worker: 선택 문서·이미지 공고 처리 추가
면접 입출력: 음성 업로드·STT·TTS·재생 상태 추가
도메인: 검수된 자료와 조회 기능 연결
```

React는 입력·표시와 사용자 조작을 담당한다. FastAPI는 사용자와 자료의 접근권한을 확인하고, 요청을 받아 작업으로 등록하며, 확정된 결과를 조회해 제공한다. 핵심단계에는 마이크 권한이나 음성 파일이 없어도 면접이 진행되어야 한다.

SSE는 서버에서 브라우저로 보내는 단방향 알림이다. 따라서 답변 제출은 HTTPS API로, 진행상태와 결과 알림은 SSE로 나눈다. 후속 음성 업로드도 SSE가 아니라 별도 요청으로 전달한다. [외부 2]

일시적인 알림 끊김이 발생하면 서버에 확정된 질문·상태를 다시 조회하는 방향으로 구성한다. 이를 장기 중단 면접 재개 기능까지 지원한다는 의미로 확대하지 않는다. 재연결·이벤트 중복 처리는 현재 질문 식별정보와 맞춰 확인한다.

## 2-3. ARQ와 저장소의 책임

ARQ는 Redis에 등록한 비동기 작업을 Worker에서 실행한다. 공식 문서는 작업이 다시 실행될 수 있다고 명시한다. 따라서 같은 작업을 두 번 받아도 사용자에게 같은 결과가 중복 확정되지 않는 성질인 **멱등성**을 서비스에서 확보해야 한다. [외부 1]

작업에는 원본 전체나 DB 연결 객체 대신 작업·세션·답변 식별자를 전달한다. Worker가 해당 자료를 조회하고, 처리한 결과를 저장한 뒤 작업을 끝낸다. 사용자가 읽고 생각하고 답하는 시간을 Worker가 계속 대기하는 구조로 만들지 않는다.

준비 Worker와 면접 Worker는 실행 자원을 나누어 대량 분석이 현재 면접 처리를 모두 점유하지 않게 한다. 다만 같은 외부 API 한도와 서버 자원을 공유할 수 있으므로 호출량과 동시 처리 제한도 측정해 조정한다. 긴 동기 파일 처리는 비동기 이벤트 루프를 막지 않는 실행 경계로 분리한다. [자료 2] [외부 3]

| 저장소 | 저장 책임 | 단독으로 맡기지 않을 것 |
|---|---|---|
| **PostgreSQL** | 확정된 분석·세션 상태·질문·답변·판정·근거·리포트 | 실제 스키마와 제약 검증 없이 모든 정합성이 확보됐다고 가정하지 않음 |
| **Redis** | 작업 전달·상태 캐시·검색 캐시·중복 실행 완화용 잠금 | 면접 장기 기록과 최종 상태의 유일한 저장소 |
| **비공개 파일 저장소** | 필요한 원문, 후속 문서·이미지·음성 | 접근권한 없는 공개 원문 저장 |

ARQ 공식 저장소는 유지보수 전용 상태를 안내한다. 기존 채택은 유지하되 검증한 버전을 고정하고, 큐 연결 코드와 실제 분석·면접 로직을 분리하여 변경 영향 범위를 줄인다. [외부 4]

## 2-4. 에이전트 관점: 각 기능의 입력과 결과

| 구성 | 받는 정보 | 반환하거나 수행하는 결과 |
|---|---|---|
| **Analysis Pipeline** | 레포와 읽기 범위 | 기본·정밀 분석, 원문 위치, 분석 상태·한계 |
| **JD·문서 Pipeline** | 확보한 공고 본문·문서 원문 | 원문에 연결된 요구사항·Claim·확인 상태 |
| **Context Builder** | 사용자·선택 자료·현재 상태·질문 목적 | 현재 판단에 필요한 자료만 선별한 묶음 |
| **Answer Evaluator** | 실제 질문·Contract·확정 답변·적용 조건 | 평가 가능 여부, 세 판단, 확인·부족 항목, 불확실성 |
| **Interview Director** | 답변 평가·진행상태·자료 조회 결과 | 행동·목표·Persona·도구 요청·판단 이유 |
| **Question Generator** | 질문 목적·Contract 초안·Persona·관련 자료 | 사용자에게 제시할 질문 후보 |
| **Question Validator** | 질문 후보·Contract·현재 자료와 상태 | 사용·재작성·재계획·차단과 이유 |
| **Report Pipeline** | 확정 문답·평가·사용 근거·종료 상태 | 근거가 연결된 종합·면접관별 피드백 |

현재 질문의 평가결과와 전체 면접 상태를 Director가 함께 받는 이유는, 설명이 부족하더라도 시간과 미평가 영역에 따라 보완보다 전환이 필요할 수 있기 때문이다. Persona를 함께 반환하는 이유는 같은 질문자 정보를 생성·표시·기록에 연결하기 위해서다.

도구 요청에는 확인할 목적과 허용된 대상이 있어야 한다. 검색 결과를 받은 뒤 목적·전제·다음 행동을 다시 판단한다. 반환 형식이 올바르다는 사실만으로 의미적으로 적절한 결정이라고 보지는 않는다. [자료 2] [자료 9]

## 2-5. 세 Tool의 반환 범위

**Evidence Retriever**는 선택 레포의 기존 Analysis와 허용된 원문에서 관련 코드·설정·테스트를 찾는다. 결과에는 원문, 파일, 함수 또는 구획, 위치, 검색 상태를 포함한다. 함수가 없는 파일에 함수명을 만들지 않으며, 원문과 요약은 구분한다.

**문서 Claim 조회 도구**는 사용자 확인을 거친 Claim과 해당 문서의 원문·위치를 찾는다. 문서에 없는 주장을 생성하거나 제외된 문서를 다시 사용하지 않는다. 후속단계에 활성화한다.

**Domain Knowledge 조회 도구**는 질문 목적에 맞는 검수된 자료와 적용 조건을 반환한다. 결과를 사용자 개인 경험의 증거로 취급하지 않는다. 후속단계에 활성화한다.

검색 결과는 관련 자료 발견, 정상적인 검색 범위 내 미발견, 확인된 분석 부족, 도구 장애를 구분한다. **도구의 실행 상태와 해당 주장이 얼마나 뒷받침되는지는 별개**다. 관련 자료를 찾았어도 주장 일부만 지원할 수 있다. 특정 파일 힌트나 확인된 누락 범위는 제한적으로 추가 조회하고, 미발견마다 전체 레포를 다시 분석하지 않는다. [자료 2]

## 2-6. 첫 질문과 답변 이후 처리

첫 질문은 공고·선택 레포·필요 분석·사용자 시작 의사를 확인한 뒤 준비한다. Manager의 자기소개 확인으로 시작하되, 질문 내용은 준비된 직무 맥락에 맞춘다.

질문을 만들 때 목적과 필수내용의 초안을 먼저 정하고, 생성된 질문이 이를 실제로 요구하는지 검사한다. 불일치하면 전달 전에 표현을 고치거나 목적부터 다시 계획한다. **사용자에게 전달하는 시점에는 질문 문장·Contract·Persona가 함께 확정되어야 한다.**

핵심단계의 답변 후 처리는 다음과 같다.

```text
텍스트 답변 제출
→ 사용자·현재 질문·제출 상태 확인
→ 확정 답변 저장
→ 답변 평가
→ Director의 다음 행동·질문 목적·면접관 선택
→ 필요할 때 Tool 실행·결과 반영
→ 다음 질문과 Contract 정합성 검사
→ 질문·Contract·Persona 저장
→ 화면에 다음 질문 전달
```

음성 기능은 다음과 같이 같은 처리에 연결한다.

```text
음성 제출 → STT → 전사문 확인·확정
                         ↓
                 공통 답변 처리 흐름
                         ↓
                 승인된 질문·Persona
                         ↓
               해당 면접관의 TTS·재생
```

핵심 문답 로직은 마이크·음성 파일·TTS 성공을 필수 입력으로 요구하지 않는다. 후속단계의 녹음 실패·재시도는 입출력 계층에서 구분하고, 새 질문이나 사용자 역량 부족으로 자동 변환하지 않는다. [자료 2; 이번 개정의 입출력 적용안]

## 2-7. Controller가 지켜야 하는 규칙

Controller는 모델이 직접 바꾸면 안 되는 조건을 검사한다. 사용자 권한, 현재 질문·답변의 일치, 세션 종료 여부, 준비 입력의 변경 여부, 반복·도구 호출 상한을 확인한 뒤 작업을 실행한다.

외부 호출이 끝난 뒤 저장하기 전에도 현재 상태를 다시 확인한다. 처음 시작할 때 유효했던 작업이 완료 시점에는 종료되거나 오래된 입력에 대한 결과가 될 수 있기 때문이다. 이미 확정된 결과는 재사용하며 새 결과를 중복 추가하지 않는다.

DB에 작업을 기록했지만 큐 전달에 실패한 경우의 복구를 둔다. 이미 질문을 저장하고 알림만 실패했다면 기존 질문을 전달하는 방향으로 복구한다. 사용자 종료 후에는 늦게 완료된 질문을 현재 면접에 적용하지 않으며, 후속 음성도 추가로 재생하지 않게 연결한다.

이 규칙은 텍스트·음성 공통이다. 모델이 ‘종료했다’고 답한 것만으로 종료를 인정하지 않고 실제 상태와 전달 결과로 확인한다. [자료 2]

# 3. 기록·데이터·접근 원칙

## 3-1. 저장해야 하는 연결

기존 데이터 모델을 우선 활용하되 다음 연결을 최신 스키마와 대조한다. 이 문서는 새로운 테이블 전체 설계를 확정하거나 기존 제약을 검증한 보고서는 아니다.

| 연결 | 보존해야 하는 정보와 이유 |
|---|---|
| **사용자 → 자료** | 누구의 레포·공고·문서인지 구분하여 접근 범위를 제한 |
| **원문 → Analysis·Claim** | 어떤 원문에서 어떤 내용이 추출됐는지 검수·정정 가능하게 연결 |
| **질문 → Contract·Persona** | 실제 물은 내용, 평가 범위, 질문자를 함께 기록 |
| **질문 → 확정 답변** | 어느 질문에 제출한 어떤 내용을 평가했는지 구분 |
| **Turn → Evidence·판정** | 사용한 자료와 확인 범위를 추적 |
| **리포트 → 문답·평가** | 피드백의 판단 근거와 이후 보완을 확인 |

핵심단계의 답변 원문은 사용자가 제출한 텍스트다. 후속 음성에서는 음성에서 확정한 전사문이 답변 본문이며, 입력 출처·녹음 시도·음성 처리상태를 구분한다. **핵심단계의 질문·답변에 음성 파일을 필수로 요구하지 않는다.**

정정이 생겨도 원래 제출·제시한 내용을 모범답안으로 덮어쓰지 않는다. 적용한 답변·자료 버전과 정정 이유를 구분해 최종 피드백이 오래된 판정에만 의존하지 않게 한다. 정정 허용 시점, 재평가 범위, 리포트 갱신 방식과 물리적 저장형식은 별도 확정할 세부 명세다. [자료 2] [자료 10]

## 3-2. 리포트 작성과 문답 보존

리포트는 현재 확인된 문답·판정·근거를 모아 강점, 설명이 부족했던 부분, 기술적으로 확인할 부분, 다음 연습사항을 정리한다. 후속 질문에서 보완한 내용과 확인된 정정을 반영한다.

종합 피드백과 세 면접관 관점의 피드백은 공통 기록을 사용한다. 독립 전문가 세 명이 검증한 것처럼 표현하거나 서로 다른 점수를 단순 평균하지 않는다. 근거가 부족한 관점은 미평가·관찰 부족으로 남긴다.

다른 관점의 피드백에서 특정 답변을 참고할 수는 있지만 실제 질문자까지 바꾸어 기록하지 않는다. 사용자 답변의 부족함을 설명할 때는 해당 문답을, 구현 사실을 설명할 때는 해당 원문을 근거로 연결한다.

핵심단계는 제출 텍스트를, 후속 음성은 확정 전사문을 문답 기록으로 보여준다. 리포트를 재생성해도 원문은 바꾸지 않는다. **질문·답변 기록과 음성 원본 다시 듣기는 서로 다른 기능**이다. [자료 1] [자료 9]

## 3-3. 접근·개인정보·자료 보존

로그인 여부만 확인하지 않고 요청한 자료와 세션을 사용할 권한을 서버에서 검사한다. Tool도 허용된 사용자·선택 레포·승인 자료 범위에서만 실행한다. 외부 원문에 적힌 지시가 시스템의 접근 규칙을 바꾸지 못하게 한다.

공고·이미지 URL은 지원 목적지와 수집 범위 안에서 요청한다. 내부 주소, 위험한 리다이렉트, 과도한 파일·응답을 제한하는 구현을 포함한다. 사용자 코드와 문서는 면접 자료로 읽고, 임의 실행·수정을 핵심 기능에 포함하지 않는다.

비밀키·개인 문서·문답 원문을 공개 저장소나 불필요한 로그에 남기지 않는다. 실제 사용자 자료를 평가·학습에 재사용하려면 서비스 이용 목적과 구분해 정한 동의·접근·보존 절차를 적용한다.

자료 삭제와 분석·리포트 보존의 관계, 음성 원본 보관기간과 재생 제공 여부는 실제 자료 수집 전에 정해야 한다. 이 문서만으로 특정 법규 준수나 개인정보 보호가 이미 검증됐다고 보지 않는다. [자료 1] [자료 2]

# 4. 평가·진행 기준

## 4-1. 무엇을 평가하는지 먼저 구분한다

**사용자 답변 평가**는 해당 질문에서 설명한 내용과 기술·기여·근거의 관계를 판단한다. **서비스 품질 검증**은 질문·자료·입력·판정·진행·기록이 올바르게 처리됐는지 확인한다.

전송·질문·검색 오류를 사용자 역량 부족으로 바꾸지 않는다. 핵심단계에서는 텍스트 내용과 진행을 평가하고, 후속단계에서 음성 처리 품질을 별도로 검증한다. 음성 기능이 아직 없는 핵심 버전을 음성 검증 실패로 보고하지 않으며, 동시에 음성까지 검증됐다고 표시하지도 않는다. [자료 3; 이번 단계 변경 적용]

## 4-2. 시작 조건

공통 시작 조건은 사용자와 자료의 접근권한, 공고 본문·요구사항 확보, 면접 대상 선택, 필요한 정밀 분석의 사용 가능 상태, 현재 입력과 준비 결과의 일치, 사용자의 시작 요청이다.

핵심단계는 질문 표시와 답변 제출이 가능한 상태에서 시작한다. 사용자의 작성 중인 초안은 확정 답변이 아니다. 후속 문서를 사용한다면 확인됐거나 제외된 상태여야 한다. 도메인 미지원은 그 자체로 모든 면접을 막는 조건이 아니다.

음성으로 시작할 때만 마이크·입력·재생을 추가 점검한다. **핵심단계에서 마이크 권한·음성 준비를 시작 조건에 남기지 않는다.** 면접 준비시간과 실제 면접 진행시간도 구분한다.

## 4-3. 질문 검증: 세 기준 유지

| 기준 | 확인할 내용 | 처리 이유 |
|---|---|---|
| **전제 타당성** | 자료·기여·업무 조건을 근거 없이 사실로 가정하지 않는가 | 잘못된 전제 때문에 답하지 못한 것을 역량 부족으로 오인하지 않기 위해 |
| **현재 맥락 적합성** | 직전 답변·이미 확인한 내용·JD 중요도·남은 시간·Persona에 맞는가 | 필요한 관찰에 질문 기회를 사용하기 위해 |
| **표현 적합성** | 중심 목적이 명확하고 과도한 복합 질문·모호함·정답 유도가 없는가 | 사용자가 요구사항을 이해하고 평가범위와 일치하게 답하도록 하기 위해 |

자기소개나 명시적 가정형 질문에 반드시 GitHub 코드가 있어야 하는 것은 아니다. 특정 구현·개인 기여를 사실로 전제하는 경우 그 근거와 확인 범위가 필요하다.

검증 결과는 사용, 표현 수정, 전략 재결정, 전달 차단으로 구분한다. 심각한 전제·권한 문제를 말투만 바꿔 전달하지 않는다. 질문의 난이도·반복·필요성은 이 기준 안에서 확인하고 새 평가축으로 늘리지 않는다. [자료 3] [자료 4]

## 4-4. 답변 평가의 사전조건

먼저 현재 질문에 대한 확정 입력이며 핵심 의미를 해석할 수 있는지 확인한다. 제출되지 않은 초안, 전송 실패, 불명확한 입력, 잘못된 질문 전제는 정상 역량평가와 구분한다.

정상적으로 제출된 모름·설명 부족은 입력 오류가 아니다. 반대로 후속 음성에서 확인된 인식 오류나 질문 재생 실패를 무응답·불충분으로 확정하지 않는다.

평가 불가·확인 필요 상태에서는 무엇을 복구하거나 다시 물어야 하는지 기록한다. 원래 질문을 잘못 설계했다면 사용자의 답변에 맞춰 평가 목적을 사후에 바꾸지 않고 질문 문제를 정정한다. [자료 3]

## 4-5. 답변의 세 판단

### 충분성: 실제로 물은 내용을 설명했는가?

질문 전에 확정한 Contract와 실제 질문 문장을 기준으로 확인한다. 필수내용을 설명하면 충분, 일부만 설명하면 부분, 핵심을 거의 확인할 수 없으면 불충분으로 구분한다.

반환 결과에는 판정뿐 아니라 확인한 내용·부족한 항목·그 판단에 사용한 답변 구절을 포함한다. 답변을 길게 썼는지, 전문용어를 많이 사용했는지로 대체하지 않는다. 질문에서 요구하지 않은 내용을 말하지 않았다고 누락으로 처리하지 않는다.

세 단계는 순위를 세밀하게 나누려는 것이 아니라, 이미 설명한 부분을 인정하면서 필요한 후속 확인을 선택하기 위한 것이다.

### 기술적 정확성: 제시한 설명이 해당 조건에서 타당한가?

충분성과 별도로 현재 요구조건·구현·기술 문서·적용 버전을 확인한다. 모델이 선호하는 기술과 다르다는 이유로 오류라고 하지 않는다. 타당한 대안은 조건과 한계를 함께 검토한다.

검토 범위에서 오류 미발견, 경미한 오류, 핵심 판단에 영향을 주는 중대한 오류, 주어진 조건에서 중대한 위험을 만드는 치명적인 오류를 구분할 수 있다. 자료나 조건이 부족하면 판단을 보류한다. 이 수준의 수치화·가중치는 별도 확정 대상이다.

충분성은 필요한 설명이 제시됐는지이고 정확성은 그 설명이 맞는지다. 둘을 합치면 실제로 필요한 보완 질문과 오류 확인을 구분하기 어렵다.

### 기여·근거 정합성: 누구의 경험이고 어디까지 확인됐는가?

직접·공동·팀원 담당·미확인 등 기여 범위를 구분하고, 자료가 주장을 지원·일부 지원·확인하지 못하는 범위를 별도로 정리한다. 구현의 존재가 개인 작성과 성과까지 입증하지는 않는다.

자료 간 차이가 있어도 환경·버전·원문 해석·분석 오류의 가능성을 함께 확인한다. 검색 미발견이나 도구 장애를 거짓의 증거로 사용하지 않는다. 당사자가 담당 범위를 정정하면 이후 질문의 전제에 반영한다.

**동일 질문·답변·조건에서 면접관 이름이나 텍스트·음성의 출처만으로 임의 가점을 주지 않는다.** 다만 두 입력 방식의 실제 성능과 시간 기준이 동일하다고 가정하지 않으며, 음성 연결의 효과는 별도로 검증한다. [자료 3] [자료 9]

## 4-6. 다음 행동: 평가결과와 진행상태를 함께 본다

| 행동 | 선택하는 목적 |
|---|---|
| **ASK_FOLLOWUP** | 현재 질문의 부족한 설명을 보완 |
| **ASK_DEEPER** | 현재 답변 이후 중요한 새로운 판단을 확인 |
| **VERIFY** | 자료 조회가 다음 판단을 바꿀 수 있을 때 확인 |
| **SWITCH_TOPIC** | 더 중요하거나 경험에 적합한 주제로 이동 |
| **END_TOPIC** | 필요한 관찰을 했거나 주제 상한에 도달하여 마무리 |
| **END_INTERVIEW** | 전체 목적과 진행상태에 따라 정상 종료를 제안 |

부분 답변이라고 항상 더 묻지 않고 충분한 답변이라고 항상 심화하지 않는다. 현재 남은 핵심 영역, 주제의 중요성, 반복 횟수, 시간, 자료 확인의 가치까지 함께 본다.

검증할 것은 행동 이름 하나가 아니다. 목표·Persona·도구 필요성·질문의 전제까지 적절해야 한다. 여러 행동이 타당한 상황에서는 허용 범위를 정하되 권한·종료·반복 제한은 공통으로 강제한다.

`VERIFY`나 `END_TOPIC` 자체는 새로운 질문·답변 Turn이 아니다. 내부 처리 뒤 사용자에게 질문을 제공하거나 면접 상태를 변경하며, 도구나 재계획이 무한 반복되지 않도록 상한을 둔다. [자료 4]

## 4-7. 종료와 미평가 처리

**정상 종료**는 필요한 영역에서 관찰을 확보했고 중요한 추가 질문의 가치가 낮아진 상태다. 질문 횟수를 채웠다는 이유만으로 자동 인정하지 않고 실제 답변을 얻었는지 확인한다.

**제한 종료**는 시간·질문·반복 제한에 도달한 상태다. 부족한 답변을 완벽하게 고칠 때까지 질문하지 않으며, 확보한 관찰만 평가한다. 묻지 못한 영역은 낮은 점수가 아니라 미평가로 남긴다.

**사용자 종료**는 계획보다 우선한다. 세 면접관의 참여나 도메인 질문을 채우기 위해 계속 질문하지 않는다. 복구 불가능한 시스템 중단은 정상 평가 완료와 구분한다.

Director는 정상 종료를 제안하고 Controller가 실제 상태를 확정한다. 구체적인 시간·질문·반복 상한은 아직 별도 운영값이며, 텍스트와 음성에 같은 시간 기준이 자동으로 적합하다고 가정하지 않는다. [자료 4]

## 4-8. 서비스 품질과 리포트 검증

| 검증 대상 | 확인할 결과 |
|---|---|
| **자료·검색** | 실제 원문과 결과의 일치, 중요 누락·오선택·과장 여부 |
| **질문** | 세 질문 기준과 Contract의 일치 |
| **답변 평가** | 사람 검수와 판정·이유의 일치, 충분·부분·불충분별 오류와 보류 |
| **전략·Persona** | 행동·목표·면접관의 적합성, 전환 후 정보 유지 |
| **실행 상태** | 시작·반복·종료·중복·권한 규칙 준수 |
| **기록·피드백** | 원래 문답 보존, 실제 근거 연결, 후속 보완 반영, 미평가 인정 |

이것은 새로운 사용자 역량 점수표가 아니라 서비스가 제 역할을 하는지 확인하는 범위다. 질문·판정의 일치율을 제시할 때 평가한 건수·조건·유형·보류를 함께 기록하고, 일부 쉬운 유형만 잘 맞혀 전체가 좋아 보이지 않게 한다.

후속 음성에서는 원음과 전사의 핵심 의미 일치, 질문 음성 내용·Persona 일치, 재녹음·재생 실패 복구를 추가 검증한다. 음성 오류율·응답지연·비용은 운영 품질이며 사용자 점수로 합치지 않는다.

다른 사용자 자료 사용, 존재하지 않는 근거, 타인 기여 단정, 시스템 오류의 사용자 감점 전가, 종료 무시, 중복 질문 확정, 기록 변형은 필수 안전검사로 구분한다. 발견되면 수정·재검증하고 평균 품질로 상쇄하지 않는다. 테스트에서 0건이라고 운영 오류 가능성까지 0으로 주장하지 않는다. [자료 3]

# 5. 평가 데이터셋 설계

## 5-1. 무엇을 만드는가?

평가 데이터셋은 **주어진 자료·질문·답변·면접 상태에서 어떤 판정과 행동이 허용되는지 사람이 검수한 시험 사례집**이다. 모델 학습이 선행돼야 한다는 뜻도, 질문과 모범답안의 문장 일치를 검사한다는 뜻도 아니다.

원문 자료와 평가 사례를 구분한다. 레포·공고·필요한 문서·기술 및 도메인 자료는 출처와 버전을 관리하고, 사례가 필요한 부분을 참조한다. 실제 코드 사실, 문서에 적힌 주장, 시험을 위한 가상 역할 설정은 다른 성격의 정보로 관리한다.

원문을 공유하는 구조는 유지하되, 모든 평가를 한 프로젝트나 같은 표현에만 편중하지 않는다. 사용 가능한 자료와 검수 가능한 범위에서 서로 다른 판단 상황을 확보한다. [자료 5] [자료 6]

## 5-2. 네 종류는 그대로 유지한다

| 사례 종류 | 핵심단계에서 확인할 것 | 후속단계에서 추가할 것 |
|---|---|---|
| **자료·근거** | 기본·정밀 분석, 텍스트 공고 추출, 추천·코드 검색 | 문서 Claim, 이미지 판독, 도메인 관련성·적용 조건 |
| **Turn** | 텍스트 질문·답변 평가, 행동·목표·Persona, 질문 검증 | 음성에서 확정된 답변과 도메인·문서 조건의 적용 |
| **Session** | 시작·전환·반복·종료, 제출·중복·화면·기록 | 녹음·전사·음성 재시도, 질문자·음성 일치, 추가 자료 상태 |
| **Report** | 종합·개별 피드백, 실제 문답·근거, 미평가 | 음성 정정과 추가 자료의 출처, 가정과 경험의 구분 |

Persona·도메인·위험 여부는 필요한 사례의 조건이나 태그로 넣는다. 음성만을 이유로 다섯 번째 대형 데이터셋을 만들거나 모든 사례를 면접관 수만큼 복제하지 않는다.

이번 적용안에서는 핵심단계의 문자 입력이 실제 서비스 입력이다. 기존 문서의 ‘문자 시험은 서비스와 다른 시험 방식일 뿐’이라는 설명은 이 단계에는 적용하지 않는다. 음성 추가 후에는 공통 의미 판단 시험과 실제 음성 전체 경로 시험을 구분한다. [자료 5; 이번 단계 변경 적용]

## 5-3. 사례 한 건에 담을 정보

| 항목 | 작성할 내용 |
|---|---|
| **대상·적용 조건** | 시험할 기능, 핵심·후속 단계, 활성 기능·정책 버전 |
| **실행 입력** | 실제로 해당 기능이 받는 자료·질문·Contract·답변·상태 |
| **기대 결과** | 판정, 허용 행동·목표·Persona, 필요한 상태 변화 |
| **금지 결과** | 근거 없는 단정, 잘못된 접근·기록 변경·종료 위반 |
| **판정 근거** | 기준과 원문·답변의 연결, 적용 조건, 검수 이유 |
| **관리정보** | 사례·자료 버전, 작성·검수 상태, 개발용·Holdout 구분 |

실행 모델은 실제 운영에서 받을 정보만 읽는다. 기대 평가나 정답 메모는 프롬프트·검색·파일 접근 범위에서 제외한다. 반면 Question Contract처럼 운영에서도 사용하는 입력까지 숨겨 시험을 어렵게 만들지는 않는다.

질문의 표현은 달라도 목적과 전제가 맞으면 인정할 수 있다. 행동 이름만 맞고 목표가 다르면 통과시키지 않는다. 자료의 실제 존재와 접근권한, 확정 기록은 표현의 다양성과 별개로 엄격히 확인한다. [자료 5] [자료 6]

## 5-4. 어떤 차이를 시험할 것인가?

충분·부분·불충분뿐 아니라 기술 오류, 기여 정정, 자료 미발견, 분석 부족, 도구 실패, 반복 상한, 사용자 종료를 구분하는 사례를 구성한다. 모두 성공하는 입력만 모으지 않는다.

한 조건만 바꾼 대조 사례로 같은 판정이 유지돼야 하는지, 다음 행동은 달라져야 하는지 확인한다. 검색에는 관련 자료와 함께 **비슷하지만 무관한 자료인 Hard Negative**를 포함한다. 도구를 사용해야 하는 경우와 사용하지 않아야 하는 경우도 함께 구성한다.

전체 면접 자동 재생에서는 실제 질문 목적에 맞는 범위의 답변만 제공한다. 시스템이 기록한 목표와 실제 질문 문장이 다르면 이를 숨기고 이상적인 답변을 주지 않는다. 준비하지 않은 정당한 질문이 나오면 시험 시나리오의 한계로 구분해 보완한다. [자료 5] [자료 8]

## 5-5. 핵심·후속 기능의 검증 결과를 섞지 않는다

사례마다 적용 단계와 필요한 기능을 지정한다. 핵심단계에 제공하지 않는 음성·이미지 판독의 정확도를 핵심 버전의 실패로 합산하지 않는다. 미지원 상태를 올바르게 안내하는지는 별도 기대 결과로 검증한다.

후속단계에서는 음성·이미지·문서·도메인 기능을 활성화한 조건으로 검증한다. 읽을 수 있는 지원 범위에서 정확히 처리하는지와, 읽지 못한 내용을 추측하지 않는지를 함께 확인한다.

기대 결과는 기능 범위·정책을 먼저 정한 뒤 작성한다. 모델 출력이 달라졌다는 이유로 정답을 맞춰 바꾸지 않는다. **핵심단계 통과는 음성면접 통과를 뜻하지 않고, 후속 기능의 성공이 기존 핵심 오류를 상쇄하지도 않는다.**

# 6. 데이터셋 구축·실행 절차

## 6-1. 원문 확보와 사람 사실 확인

팀이 사용할 수 있고 직접 검수할 수 있는 자료부터 확보한다. 출처·확보 시점·코드 또는 문서 버전·읽은 범위를 기록한다. 공고는 추출문만이 아니라 수집 대상 원문도 있어야 수집기의 누락을 확인할 수 있다.

사람이 원문에서 확인한 사실과 한계를 별도로 작성한다. 평가할 모델의 분석 결과를 그대로 정답으로 복사하지 않는다. 사용자가 제공한 개인 자료의 평가 재사용과 공개 여부는 서비스 이용 목적과 별도로 관리한다. [자료 7] [자료 8]

## 6-2. 질문·상태·기대 결과 작성

질문과 필수내용을 먼저 정하고, 그 목적을 충족하거나 일부 설명하지 않은 답변과 다른 상태 조건을 구성한다. 기술 오류 사례에는 해당 조건에서 왜 틀린지 확인할 근거가 있어야 한다.

정답은 완성된 질문 문장 하나보다 판정·허용 행동과 목표·금지 결과·판정 근거로 작성한다. 정상 흐름뿐 아니라 입력·도구·상태의 실패 처리도 포함한다. 핵심단계는 텍스트 제출 문답부터 실제 실행하고, 후속 기능의 자료는 해당 연결을 검증할 준비가 되었을 때 추가한다. [자료 7]

## 6-3. 교차 검수와 채점기 확인

작성자 외의 검수자가 원문·질문·답변·상태를 보고 독립적으로 판정한다. 불일치가 있으면 질문이 모호한지, 조건이 부족한지, 여러 행동이 타당한지 확인한다. 합의할 근거가 부족한 사례는 수정하거나 보류한다.

LLM은 후보 작성과 반복 검토를 도울 수 있지만 정답을 자동 승인하지 않는다. 채점기에도 적절한 출력과 의도적으로 잘못된 출력을 넣어 구분하는지 확인한다. 형식·식별자·개수 같은 조건 검사와 의미 판정을 구분한다.

LLM Judge 연구는 순서·답변 길이·자기 선호 등의 편향과 추론 한계를 다룬다. 따라서 다른 모델이 채점했거나 높은 점수를 줬다는 사실만으로 객관성을 확정하지 않고 사람 검수와 비교한다. [외부 5]

## 6-4. 개발용·Holdout·회귀검사의 구분

개발용은 프롬프트·검색·정책 개선에 사용한다. Holdout은 그러한 수정에 사용하지 않은 최종검증용으로 남긴다. 같은 프로젝트의 질문·답변 변형과 나중에 녹음한 음성도 같은 그룹으로 관리하여 분리 양쪽에 섞이지 않게 한다.

Holdout을 보고 수정하면 이후 같은 사례의 통과는 회귀검사, 즉 수정 후 기능이 유지되는지 확인하는 결과로 해석한다. 새로운 상황의 대응력은 사용하지 않은 사례로 확인한다. 외부 모델의 사전학습에 공개 자료가 포함됐는지는 이 분리만으로 보장하지 못한다.

초기 시범 15~20건은 구축·검수·실행 절차를 확인하는 제안 규모다. 최종 사례 수나 서비스 성능을 입증하는 충분한 표본이라고 단정하지 않는다. 실제 지원 범위와 실패 유형에 맞춰 확장한다. [자료 6] [자료 7]

## 6-5. 기능별 시험과 전체 시험

기능별 시험에는 검수된 앞 단계 입력을 사용할 수 있다. 어느 모듈에서 오류가 발생했는지 분리하기 위한 시험이다. 전체 시험에서는 실제 수집·분석·답변 처리 결과를 이어서 사용한다. 중간 오류를 사람이 정답으로 교체한 실행을 전체 성공으로 보고하지 않는다.

핵심단계 전체 시험은 실제 웹의 질문 표시·텍스트 제출부터 평가·후속 질문·종료·리포트까지 연결한다. 후속단계는 실제 음성 입력·STT·확정 답변·TTS·재생과 추가 자료 경로를 연결한다.

매 실행은 이전 면접 상태와 결과가 섞이지 않게 격리하고, 코드·모델·프롬프트·정책·자료 버전·출력·도구 기록·최종 상태를 남긴다. 반복 실행의 실패·보류도 기록하고 성공한 시도만 선택하지 않는다. 이는 Agent의 최종 출력과 도구 실행·최종 상태를 함께 검토한다는 평가 원칙을 적용한 것이다. [자료 8] [외부 6]

## 6-6. 음성 데이터 추가 — 후속단계

동의받은 테스트 음성, 사람이 확인한 실제 발화 전사문, STT 결과를 연결한다. 대본 녹음과 자유 발화를 구분하고, 실제 발화가 대본과 달라지면 실제 발화를 기준으로 기대 판정을 확인한다.

인식 정확성은 원음과 비교하되, 에이전트의 복구 능력은 실제로 전달된 오류 신호나 사용자 정정으로 시험한다. 채점자만 아는 원음을 에이전트도 반드시 알았어야 한다고 요구하지 않는다.

승인된 질문이 해당 Persona의 음성으로 전달되는지, 재시도·종료 뒤에도 연결이 유지되는지 확인한다. 기존 텍스트 의미평가 사례를 재사용할 수 있지만, 그것만으로 음성 전체 경로의 정확성과 사용성이 검증되지는 않는다. [자료 5] [자료 8]

## 6-7. 구축 완료의 의미

원문과 판정 근거가 연결되어 있고, 입력과 정답이 분리되어 있으며, 검수한 사례를 실제 기능에 실행해 기대 결과와 비교할 수 있어야 한다. 결과가 틀리면 서비스·자료·정답·채점기·실행환경 중 원인을 구분할 수 있어야 한다.

양식과 기대 출력만 작성한 단계, 형식 검사만 통과한 단계, 실제 모델을 실행한 단계, 전체 서비스를 실행한 단계를 구분해 기록한다. 미실행 기능을 성공으로 집계하지 않는다. **구축 결과물은 많은 질문 문장이 아니라, 다시 실행하고 판단 근거를 확인할 수 있는 평가체계다.** [자료 7] [자료 8]

# 7. 단계별 완료조건과 남은 결정

## 7-1. 핵심단계 완료조건

텍스트 문답 적용안을 채택한 핵심단계는 실제 공고·레포 입력으로 추천·선택·정밀 분석을 거쳐 세 면접관의 질문·답변·후속 행동·종료·종합 및 개별 피드백까지 연결되어야 한다.

화면·질문·기록의 Persona가 일치하고, 실제 제출한 답변을 평가하며, 근거와 미확인 범위를 구분해야 한다. 반복·중복·권한·종료 오류도 검사한다. **마이크·녹음·STT·TTS·역할별 음성 파일은 핵심 완료의 필수조건에서 제외한다.**

텍스트 흐름이 작동했다는 결과를 음성면접이나 실제 말하기 능력 개선의 검증으로 표현하지 않는다.

## 7-2. 후속단계 완료조건

선택 문서·도메인·이미지 공고가 각각의 지원 범위에서 원문·출처·적용 조건을 유지하며 기존 문답 흐름에 들어와야 한다. 음성은 녹음부터 확정 답변, 질문 음성 전달과 오류 복구까지 실제로 연결되어야 한다.

음성을 추가해도 질문·평가·Director·기록·리포트의 공통 원칙은 유지한다. 입력 방식 때문에 평가범위가 임의로 바뀌거나, 역할별 음성이 바뀌며 발화자 기록이 어긋나지 않아야 한다.

후속기능 공개 전에 기존 핵심 흐름도 다시 검증한다. 새 기능의 정상 처리뿐 아니라 실패·미지원 상태를 확인하고, 자료가 없을 때 경험이나 요건을 생성하지 않아야 한다.

## 7-3. 기존 스프린트 문서에 반영할 변경

기존 단계 구분을 유지할 경우 W7의 완료조건은 ‘3인 전체 음성면접’이 아니라 **‘3인 텍스트 문답과 기록·종합 및 면접관별 피드백’이라는 적용안**으로 수정한다. 녹음·STT·TTS·음성 매핑·마이크·음성 검증을 핵심 필수 작업에서 후속 작업으로 이동한다.

W8~W9의 기존 문서·도메인·이미지 공고 작업에 음성 연결이 추가되는 만큼 실제 작업량과 인력 배분은 다시 점검해야 한다. 단순히 항목을 옮겼다는 이유로 동일 기간 내 완료를 보장하지 않는다. **W10~W11은 비워 두며 보충 작업을 배정하지 않는다.** 이 기준서는 개별 담당자별 새 일정표까지 확정한 문서는 아니다.

# 8. 근거의 범위와 최종 정의

OPM의 구조화 면접 지침은 직무 관련 질문과 사전 평정기준을 참고할 근거다. 다만 동일 문항·동일 순서의 선발검사와 개인화된 DEVON의 연습면접은 같지 않다. 이 기준만으로 합격 예측이나 사람 간 공정한 순위가 검증됐다고 주장하지 않는다. [외부 7]

QGEval은 질문 품질을 여러 측면으로 구분하여 평가한다. DEVON의 세 질문 기준은 기존 자료가 이를 서비스 목적에 맞게 묶은 내부 설계이며, 그 세 묶음 자체를 논문이 검증했다는 뜻은 아니다. Agent 평가 지침과 LLM Judge 연구도 실제 기록·최종 상태·사람 검수의 필요성을 뒷받침할 뿐, DEVON의 성능 수치를 대신하지 않는다. [자료 4] [외부 8] [외부 5] [외부 6]

**DEVON의 핵심은 자료에 근거하여 묻고, 실제 답변에 맞춰 다음 행동을 바꾸며, 관찰한 내용만 기록과 피드백으로 돌려주는 면접 연습이다.**

이번 개정에서는 그 핵심을 먼저 완성하고 음성 입출력을 후속으로 연결한다. 세 면접관·단일 Director·최소 평가기준·네 종류의 데이터셋은 유지하며, 음성의 개발·검증·보존·운영 의존성만 해당 단계에 맞게 이동한다.

|---|---|---|

| **공고 요구사항–원문 위치 매핑표** | 담당업무·필수·우대 분류와 원문 구절·구획 위치·검수된 해석 | 박현솔의 공고 본문 추출·요구사항 분류·추천 이유 검증 |
| **문서 원문 추출 결과** | 문서 텍스트·주변 구획·페이지/문단 위치·추출상태 | 김진영이 반환하고 박현솔의 문서 주장 추출 기능이 입력으로 사용 |
| **문서 주장–원문 위치 연결 결과** | 원문에 적힌 경험·기여·성과 주장, 주체, 원문 위치, 사용자 확인·제외 상태 | 박현솔이 구조화한 주장을 사용자에게 확인받고 면접에서 조회 |
| **질문별 목적·필수 확인내용 명세** | 질문의 목적, 실제 질문에서 요구한 설명, 적용할 가정 | 송유석의 질문 생성·답변 평가, 구동한의 다음 행동 선택 |
| **원음 대조·검수 완료 전사문** | 동의받은 음성을 직접 듣고 실제 발화에 맞게 확인한 텍스트 | 이건영·송유석이 STT 결과와 의미 변화·인식 오류를 비교 |
| **피드백–문답 근거 연결표** | 피드백 내용과 판단에 사용한 실제 질문·답변, 필요한 추가 자료의 식별정보 | 종합·면접관별 피드백의 근거와 원래 기록 보존 검증 |
| **최초 기능별 평가 결과** | 최초 실행한 기능 버전·검증 데이터·판정·오류 기록 | 이후 변경의 개선·악화 여부를 비교. Baseline의 의미 |
| **개발에 사용하지 않은 최종검증용 데이터** | 프롬프트·정책·코드 수정에 쓰지 않고 남겨둔 검증 입력과 기대 결과 | 최종검증에 사용. Holdout의 의미 |

이 명칭의 ‘표’와 ‘명세’는 정리할 정보를 뜻한다. 각각을 새 DB 테이블이나 별도 화면으로 만들라는 요구가 아니다. 기존 문서·JSON·DB에서 같은 역할을 하는 구조를 재사용할 수 있다.

**근거–위치 매핑표에는 검수 결과를 유지한다.** 이름에서 작성 주체를 빼더라도, 담당자가 원문과 분석의 관계를 확인하고 다른 담당자가 검수하는 과정은 없애지 않는다. AI 분석 출력만 그대로 복사하여 검증 정답으로 쓰지 않는다.

표에 붙인 ‘근거’는 여기서는 검증할 원문을 뜻한다. 면접 전에 준비한 분석은 **Analysis**, 면접 중 실제 문답에 채택된 자료는 **Evidence**라는 기존 구분을 유지한다. 매핑표의 모든 원문을 면접 Evidence로 자동 등록하지 않는다.

## 0-2. 근거–위치 매핑표에 포함할 정보

| 항목 | 작성할 내용 |
|---|---|
| 확인할 항목·내용 | 어떤 분석 내용이나 구현 사실을 원문으로 확인하는가 |
| 원문 출처 | 레포·파일·문서·공고 식별정보 |
| 근거 원문 | 확인한 내용과 관련된 실제 코드·문장. AI 요약과 분리 |
| 원문 위치 | 파일 경로·함수/구획·줄 범위 또는 페이지·문단. 없는 함수·페이지를 생성하지 않음 |
| 확인 가능·미확인 범위 | 원문으로 확인할 수 있는 것과 추가로 검증되지 않은 것 |
| 자료 버전·검수정보 | 읽은 코드/문서 상태·확보 시점, 검수자·검수 상태 |

문서의 주장이 발견됐다는 것은 그 주장이 원문에 존재한다는 뜻이지 실제 성과·개인 기여까지 입증됐다는 뜻이 아니다. 자료를 찾지 못했다면 조회한 범위와 상태를 남기고 근거 원문이나 위치를 만들지 않는다.

검증용 기대 판정·허용 행동·검수자 메모는 실행 모델의 입력·검색 범위에서 분리한다. 반면 실제 서비스가 사용하는 분석 원문·출처와 질문별 목적·필수 확인내용은 해당 기능의 정상 입력으로 제공한다.

## 0-3. 검증 입력·시나리오·실행 결과를 구분한다

| 구분 | 무엇을 작성하는가 |
|---|---|
| **검증 데이터** | 시험할 기능, 입력 자료·요청·질문·답변·면접 상태, 기대 판정·허용 행동, 금지 결과, 판정 근거 |
| **검증 시나리오** | 요청·상태 변화·실패가 발생하는 순서와 각 단계에서 확인할 상태 |
| **검증 실행 결과** | 실제 출력·DB/전달 상태, 기대 결과와 차이, 통과·실패·판단 보류·미실행, 실행 버전 |

단일 결과를 검사하는 자료는 ‘어떤 기능의 검증 데이터’인지, 여러 단계의 흐름은 ‘어떤 전환·종료·복구 시나리오’인지 이름에 적는다. 예상 결과와 실제 실행 결과를 구분하고, 실행하지 않은 기능을 통과로 기록하지 않는다.

# 3. 구동한 — 면접 진행 결정·작업 실행·전체 연결

**입력:** 자료 준비상태, 확정 답변, 답변 평가, 이전 면접 기록.  
**결과:** 다음 행동·질문 목적·면접관, 실제 실행 결과, 확정된 면접 상태.

구동한은 모든 질문과 분석을 직접 만드는 대신, 다른 담당자가 만든 기능을 필요한 순서로 호출한다. Director는 다음 행동을 판단하는 AI이고, Controller는 권한·순서·중복·종료를 통제하는 코드다. Worker는 ARQ·Redis를 통해 전달된 작업을 실행하는 프로그램이다.

## 표를 실제 작업으로 옮기는 방법

**W4~W5: 다른 기능의 결과를 받아 실행 가능한 결정을 만든다.** 송유석의 평가가 ‘부족함’만 반환하면 다음에 무엇을 물을지 알 수 없다. 따라서 확인한 내용과 부족한 항목까지 받는다. Director는 이를 면접 상태와 함께 읽고 다음 행동·목표·면접관을 반환한다. Controller는 그 결정이 현재 권한·상한·종료 상태에서 허용되는지 검사한다. 음성 관련 데이터가 없어도 이 처리가 실행되어야 한다.

**W6~W7: 결정이 실제 질문과 기록이 되도록 연결한다.** 김진영의 근거 조회 결과를 받은 뒤 다시 판단하고, 박현솔의 질문용 자료와 함께 송유석에게 질문 생성을 요청한다. 검증된 질문·질문 기준·면접관을 함께 저장하여 웹에 전달한다. 종료하면 질문 생성을 멈추고 이건영의 리포트를 실행한다. 결과물은 설명 문서만이 아니라 실제 제출 답변부터 다음 질문·종료까지 이어지는 함수와 저장 기록이다.

**W8~W9: 음성 때문에 면접 판단을 다시 만들지 않는다.** 송유석이 만든 확정 전사문을 기존 텍스트 답변 처리에 넘기고, 승인된 질문을 다시 음성 생성에 넘긴다. 문서 분석이 끝나도 사용자 승인·제외는 따로 확인한다. 재녹음이나 공고 변경 전의 결과가 늦게 도착하면 현재 선택을 덮어쓰지 않게 한다. 이 입력 변경 확인은 작업 충돌 방지이며 레포 Snapshot 기능이 아니다.

**W12~W13: 실행 성공 메시지가 아니라 저장·전달 결과를 확인한다.** 이미 저장한 질문을 재실행으로 다시 만들지 않는지, 종료 후 늦은 질문이나 음성을 전달하지 않는지 검사한다. 이후 다른 담당자가 문서만 보고 실행·실패 확인·복구할 수 있도록 배포 절차를 남긴다. ARQ 공식 문서도 작업이 여러 번 실행될 수 있음을 명시하므로, 중복 확정 방지는 서비스에서 확인해야 한다.

**W6~W7: 기존 코드를 찾아 다음 면접 단계가 읽을 수 있게 반환한다.** 선택 레포와 검색 목적을 입력받아 관련 코드의 원문·파일·함수 또는 구획·위치·검색 상태를 반환하는 함수를 만든다. 찾은 구간이 실제 원문에 존재하며 요청과 관련 있는지 대조한다. 못 찾았다면 정상 미발견인지 미분석인지 조회 실패인지 구분한다. 만드는 것은 사용자 프로젝트의 새 코드나 진위 판정이 아니라, 근거를 조회하는 기능이다.

**W8~W9: 문서의 글을 해석하기 전에 정확하게 꺼낸다.** 김진영은 원문과 위치를 반환하고, 박현솔은 그 원문에서 경험·기여·성과 주장을 추출한다. 원문 위치는 잘못 읽었을 때 다시 검수·정정하기 위해 필요하다. 이후 Claim별 관련 코드를 찾되, 구현 존재를 개인 기여와 성과 전체의 검증으로 확대하지 않는다.

**W12~W13: 필요한 부분만 다시 처리할 수 있게 한다.** 수집 누락·분석 누락·검색 후보 누락·잘못된 선택을 구분하여 해당 코드를 수정한다. 지원 범위 밖을 ‘구현 없음’으로 처리하지 않는다. 배포 후에도 실패한 단계만 재시도할 수 있게 하고, 재분석 때문에 과거 면접의 근거를 지우지 않는다.

**W4~W5: 공고를 읽는 것과 추천하는 것을 나눈다.** URL에서 해당 공고의 핵심 본문을 확보한 뒤 담당업무·필수·우대를 원문에 연결한다. 이 JD와 김진영의 기본 분석을 비교하여 추천 이유를 만든다. 제목이나 메뉴만 확보한 상태에서 일반적인 채용조건을 채워 넣지 않는다. 사용자는 추천 이유를 확인한 뒤 면접할 레포를 직접 선택한다.

**W6~W7: 질문에 필요한 정보만 주되 중요한 정정은 유지한다.** 현재 사용자·선택 레포·질문 목적·면접관을 기준으로 자료를 고른다. 면접관별 우선정보는 달라도 이전 답변, 본인 기여 정정, 이미 확인한 내용은 유지한다. 도메인은 이 기간에 원문·핵심 내용·적용 조건을 송유석·이건영과 검수해 두어 W8에 처음부터 조사하지 않도록 한다.

**W8~W9: 세 결과물을 따로 만든 다음 연결한다.** 문서 처리는 김진영의 원문에서 주체·경험·성과를 구조화하고 사용자 확인을 받는 기능이다. 도메인 처리는 검수된 업무 자료에서 요청 목적에 맞는 내용·출처·적용 조건을 반환하는 기능이다. 이미지 처리는 공고 URL에서 확보한 본문 이미지를 읽어 기존 JD 분석기로 넘기는 기능이다. 모두 문장이나 사실을 새로 지어내는 기능이 아니다.

도메인 자료는 질문의 가정과 평가조건에 함께 연결한다. 회사 업종만으로 업무를 강제하거나, 외부 지식을 사용자의 실제 경험으로 바꾸지 않는다. 이미지의 핵심 내용이 불명확하면 그 한계를 남긴다. 파일 업로드 전체의 스캔 문서 해석이나 기업 홈페이지 전체 조사까지 지원 범위를 넓히지 않는다.

**W12~W13: 원문부터 어느 단계에서 의미가 바뀌었는지 찾는다.** 공고 원문·추출문·JD, 문서 원문·추출문·Claim을 각각 대조한다. 실제 URL 접근 실패와 확보된 자료의 해석 실패도 구분한다. 자료를 갱신할 때는 출처·조건을 다시 검수하고 영향받는 질문 전제·도메인 적용 조건·답변 평가 검증 데이터를 다시 실행하는 절차를 남긴다.

## 표를 실제 작업으로 옮기는 방법

**W4~W5: 질문이 요구한 것만 평가하는 함수를 만든다.** 질문·필수내용·확정 답변을 받아, 실제 답변에서 확인한 내용과 부족한 부분을 반환한다. 충분성, 기술적 정확성, 기여·근거의 정합성을 구분하며, 입력·질문 오류를 사용자 부족으로 처리하지 않는다. 질문 생성기는 구동한의 목표를 표현하고, 검증기는 실제 문장이 그 목적·전제·표현 기준을 지키는지 확인한다.

**W6~W7: 텍스트 답변만으로 면접을 완주할 수 있게 한다.** 사용자가 제출한 답변을 그대로 평가하고, 승인된 질문과 기준·면접관을 함께 확정한다. 작성 중인 초안은 평가하지 않는다. 면접관 이름 때문에 기준을 더 엄격하게 바꾸거나, 후속 답변에서 정정한 역할을 다음 면접관이 다시 잘못 전제하지 않는지 확인한다. 이 기간에는 마이크·목소리·STT·TTS 완료를 요구하지 않는다.

**W8: 실제 음성 변환 기능과 목소리 연결을 만든다.** STT는 음성을 텍스트로, TTS는 질문 문장을 음성으로 바꾸는 기능이다. 선택한 공급자의 API를 실제 호출해 한국어 전사와 질문 음성을 만들고, 세 면접관에게 사용할 목소리를 직접 듣고 선정한다. 결과물은 목소리 이름만 적은 표가 아니라 실제 음성 식별값이 있는 설정, 생성 음성, 발음·구분감 확인 기록이다. 또한 문서·도메인 질문의 조건은 박현솔과 나누어 준비한다.

**W9: 음성을 검증된 공통 처리 앞뒤에 연결한다.** 확정 전사문은 W7의 답변 평가로 보내고, 이미 승인된 질문은 해당 Persona의 목소리로 생성한다. 재녹음은 현재 질문의 입력 시도로 구분하며 오래된 결과를 덮어쓰지 않게 한다. 음성 생성·재생 실패 때문에 질문을 새로 만들거나 사용자에게 감점하지 않는다. 실제 브라우저 연결에서는 웹 담당과 마이크 권한·보안 연결·재생을 함께 확인한다.

**W12~W13: 실제로 말한 내용과 기록된 내용을 비교한다.** 원음·원음 대조 및 검수 완료 전사문·STT 결과·답변 판정을 연결하여 오류의 시작점을 찾는다. 배포에서는 모델·프롬프트·Persona·목소리 설정이 평가한 버전과 같고 화면·음성·문답 기록의 질문자가 일치하는지 확인한다. 텍스트 시험 통과를 음성 품질 검증으로 대신하지 않는다.

## 표를 실제 작업으로 옮기는 방법

**W4~W5: 기대 결과를 적는 것과 실제 결과를 확인하는 것을 나눈다.** 김진영의 레포 분석 검증용 근거–위치 매핑표, 박현솔의 공고 요구사항–원문 위치 매핑표, 송유석의 질문별 목적·필수 확인내용, 구동한의 진행 규칙을 받아 기능별 검증 입력·기대 결과·판정 근거를 작성한다. 실행 모델이 받는 입력과 검수된 기대 판정·허용 행동을 분리하고, 담당 함수를 호출하여 실제 결과를 저장하는 실행기를 작성한다. 검수는 각 분야 담당자와 나누고, 판정이 다르면 조건과 근거부터 점검한다. 15~20건은 팀 전체의 초기 검증 데이터 구축·검수·실행 절차를 확인하는 총량이다. 기능마다 15~20건을 배정하거나 모든 검증영역의 최종 표본 수로 확정한 것이 아니다. W5에 실행 가능한 레포 분석·공고 분류·질문·답변·행동 선택부터 검사하고, 연결되지 않은 기능은 미실행으로 남긴다.

**W6~W7: 피드백을 실제 문답에서 만든다.** 처음 부족했던 답변이 후속 질문에서 보완됐는지까지 읽고 관찰을 정리한다. 종합·세 면접관별 피드백에 관련 질문·답변을 연결하며, 관찰하지 못한 영역은 미평가로 남긴다. 전체 시험에서는 실제 수집·분석·텍스트 답변 결과를 이어서 사용하고, 중간 처리의 실제 출력을 검수된 기준 입력으로 교체한 실행은 원인 분리용 검사로 표시하고 전체 서비스 성공으로 보고하지 않는다.

**W8~W9: 추가 기능이 실제로 필요한 경우와 사용하지 않아야 할 경우를 함께 검사한다.** 문서 승인·제외 처리, 도메인 조회 필요성·적용 조건, 이미지 판독·요건 충돌, STT 전사·정정·TTS 재생 실패를 검증할 입력과 기대 결과를 작성한다. 기존 네 분류인 자료 분석·근거 검색, 질문·답변·다음 행동, 면접 시작·전환·종료, 리포트·문답 기록 안에 각각 배치한다. 이전 텍스트 면접도 재실행해 추가 기능이 기존 기능을 깨뜨리지 않았는지 확인한다. 이 반복 검사를 회귀검사라고 한다.

**W12~W13: 개발에 쓰지 않은 자료로 확인하고 실제 배포 상태를 검사한다.** 최종검증용 자료(Holdout)는 프롬프트나 정책 수정에 사용하지 않고 남겨둔 자료다. 같은 프로젝트에서 파생된 문답 검증 데이터와 그 답변을 녹음한 음성은 같은 그룹에 둔다. 평가 전에 버전·기준·실행 조건을 고정하고 실패·보류도 기록한다. 최종검증 결과를 보고 기능 수정에 사용한 검증 데이터는 이후 회귀검사용으로 구분한다. 배포에서는 모델의 설명이 아니라 실제 DB·화면·문답·음성을 보고 통과 여부를 판단한다.

# 8. 담당 간 연결과 웹 작업

| 전달 관계 | 전달할 결과 | 사용하는 이유 |
|---|---|---|
| **김진영 → 박현솔** | 기본·정밀 분석, 문서 원문·위치 | 추천·질문용 자료·문서 Claim을 만들기 위해 |
| **김진영 → 구동한·송유석** | 검색 원문·위치·상태·확인 범위 | 근거를 반영한 행동·질문을 정하기 위해 |
| **박현솔 → 구동한·송유석** | JD·Context·승인 Claim·도메인 조건 | 질문 우선순위·전제·평가조건을 맞추기 위해 |
| **송유석 → 구동한** | 평가·부족 항목·검증 질문, 후속 전사·음성 | 면접을 진행하고 같은 질문을 올바르게 전달하기 위해 |
| **구동한 → 이건영·웹 담당** | 확정 질문·답변·Persona·근거·종료 상태 | 화면·기록·피드백이 같은 사실을 사용하기 위해 |
| **이건영 → 각 담당** | 실패 입력·기대 결과·실제 결과·근거 | 오류를 재현하고 고칠 위치를 확인하기 위해 |

이 연결은 개발자가 매번 수동으로 자료를 넘기는 업무가 아니다. 개발 중에는 반환값과 실행 결과를 공유하고, 서비스에서는 각 함수와 저장·조회 기능이 정보를 주고받게 구현한다.

# 9. 완료 판단과 일정의 현실성

**W7 완료:** 실제 레포·공고로 세 면접관의 텍스트 면접을 끝내고, 원래 문답과 근거에 연결된 종합·개별 피드백을 확인한다. 음성 파일·마이크·STT·TTS는 이 단계의 필수조건이 아니다.

**W9 완료:** 문서·도메인·이미지 공고·음성이 각각 실제 면접과 연결된다. 음성은 확정 답변과 승인 질문의 입출력이며, 사용자의 능력을 목소리로 다시 점수화하지 않는다. 미지원·오류·제외 상태도 정확하게 처리한다.

**W13 완료:** 평가한 버전을 배포하고, 다른 사용자 자료 접근·중복 질문·종료 후 전달·기록 변형 등 필수 오류를 검사한다. 필수 안전 오류가 해결되지 않으면 평균점수가 높더라도 정상 출시로 판정하지 않는다. 검증한 범위와 남은 한계를 기록한다.

이번 변경은 전체 작업량을 줄이기보다 음성 작업을 W8~W9로 이동시킨 것이다. 따라서 그 기간의 실제 처리 가능량을 확인해야 한다. 현재 코드 진척·개인별 투입시간·웹 인력은 확인하지 않았으므로 일정 내 완료를 보장하는 계획은 아니다.

과부하를 줄이기 위해 도메인 원문·출처·적용 조건과 자료 형식은 W4~W7에 준비하고, 김진영은 파일 추출, 박현솔은 Claim·도메인·이미지 본문, 송유석은 음성·질문·평가, 구동한은 실행 연결, 이건영은 평가자료·검증을 맡는다. 지원 사이트·언어·파일형식·도메인·음성 제공 범위를 좁혀 구현한다. 범위를 조정할 때는 팀 승인과 기준 문서 반영이 필요하다.

W8 말에 각 후속 기능의 개별 결과가 나오지 않는다면, 그 자리에서 범위와 일정을 다시 합의해야 한다. W10~W11이나 테스트·배포 기간을 미완성 신규 기능의 숨은 보충 기간으로 사용하지 않는다.

매주 남길 공통 제출물은 **변경한 코드·설정, 실제 입력, 반환값·저장 결과·검사 기록, 다음 담당자의 연결 방법과 미해결 사항**이다. 아직 실행하지 않은 부분은 미실행으로 표시한다. 특정 공통 데이터나 고정 답을 만드는 것이 아니라, 지원 범위의 실제 입력을 처리하는 기능을 완성하는 것이 목적이다.
