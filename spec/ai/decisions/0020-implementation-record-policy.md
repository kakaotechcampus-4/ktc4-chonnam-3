# 0020 AI 구현·검증 기록의 단일화

- 상태: Accepted
- 날짜: 2026-09-27
- 결정자: 현재 사용자
- 관련 PR: [#56](https://github.com/kakaotechcampus-4/ktc4-chonnam-3/pull/56)
- 검토자: 별도 팀 검토자 지정 없음
- 승인 근거: 초기 설계 보존, 구현 기록의 단일화, decisions 기록 요청에 사용자가
  “그럼 다음부턴 이렇게 해서 해결해.”라고 지시했다.

## 맥락

구현 여부와 실행 결과가 설계·task·testing 문서에 중복되어 초기 설계와 현재 구현 상태를
구분하기 어려웠다. 같은 변경을 여러 곳에 반영하면 기록 간 불일치도 생긴다.

## 결정

1. AI 구현·수정 내역, 관련 코드, 실제 검증 결과와 남은 작업은
   [`spec/ai/implementation.md`](../implementation.md)에서 관리한다.
2. 초기 설계는 설계 기준선으로 보존한다. 구현 완료·미완료나 실행 결과를 덧붙이지 않는다.
   설계의 Proposed/Accepted는 승인 상태를 뜻한다.
3. `testing.md`에는 방법·환경·기준을, task 문서에는 목표·선행 조건·완료 조건을 둔다.
   현재 구현·검증 현황이 필요하면 단일 기록을 참조한다.
4. 중요한 설계·정책 변경은 새 ADR에 맥락·결정·이유·영향·대체 관계를 남긴다.
   현행 API·내부 계약은 실제 계약 변경에 맞춰 갱신하되 구현 일지를 섞지 않는다.

## 이유

설계를 구현 일지로 계속 수정하는 방식 대신, 설계의 근거와 실행 결과를 각각 보존한다.
기록 원본을 하나로 정하면 담당자가 서로 다른 문서의 완료 상태를 비교할 필요가 줄어든다.

## 영향

- 이후 AI 작업의 구현·검증 결과는 단일 기록에 반영하고 PR에서 필요한 범위만 요약한다.
- `CLAUDE.md`는 문서 라우팅 규칙을 제공하고, AI README는 구현 기록으로 연결한다.
- 기존 서비스 동작·API·DB·모델 호출 정책은 바꾸지 않는다.
- 과거 문서의 일괄 정리와 이번 develop 통합은 별도 범위다. 초기 설계의 과거 서술을
  현재 실행 상태의 근거로 사용하지 않는다.

## 대체 관계

기존 ADR 0001~0019의 기능·정책 결정은 유지한다. 문서 작성 시 구현 현황과 실행 결과를
설계·testing에 누적하던 관행만 이 기록 원칙으로 대체한다.
