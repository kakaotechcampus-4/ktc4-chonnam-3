# 답변 분석과 평가

상태: Sprint 1 답변 분석은 FIX. 추가 근거 조회·결과 해석은 0003, 세 축 정성 평가·후속 보완은 0004, 질문 후보 복구 선택은 0008에서 Accepted인 AI 정책이다. 출력·저장·사용자 복구 계약은 Proposed이며 공개 점수 산식이 아니다.

원본: [BE 면접](../../backend/features/interview.md), [LLM task 작업](../../../backend/docs/task-14-agents.md), [ForAI 2·4·5](../../../ForAI.md), [context AI 4장](../../../context/AI.md). 계약은 [AnswerAnalysis 제안](../contracts.md)을 따른다.

## 목적과 경계

현재 질문에 사용자가 실제 제출한 답변을 분석하여 확인한 내용·부족한 내용·추가 검증할 주장을 Director에 전달한다. 질문에 없던 기준으로 평가하거나 지원자의 전체 개발 역량·취업 가능성을 판단하지 않는다.

`answer_analysis_v1`은 단발 task다. 입력은 확정 질문·질문 전에 정한 Contract·답변 원문·관련 이전 문답·현재 자료다. 저장·Tool 실행·다음 질문 결정은 task 밖에서 맡는다.

## 평가 가능 여부

[0004 결정](../decisions/0004-answer-assessment-policy.md)에 따라 질문 오류·해석 불가 입력은 평가 가능 여부부터 확인한다. 자료가 부족하면 확인할 수 없는 판단만 보류하고 이유를 남긴다. 코드 근거가 부족하다는 이유만으로 관찰 가능한 충분성까지 모두 평가 불가로 처리하지 않는다.

다른 Turn의 답변, 아직 제출하지 않은 초안, 전송 오류, 해석 불가 입력, 잘못된 질문 전제를 먼저 구분한다. 이런 상태에서 역량 점수를 만들지 않는다.

정상적으로 제출된 “모르겠습니다”나 설명 부족은 전송 실패가 아니다. 사용자가 본인 담당이 아니라고 정정하면 기여 범위를 갱신하고, 답하지 못했다는 이유로 거짓으로 판정하지 않는다.

설명하지 못한 내용은 실제 질문의 충분성 판단에 반영할 수 있지만, “모르겠습니다”를 기술적으로 틀린 주장이나 거짓말로 자동 판정하지 않는다.

초기 조건을 확인할 수 없으면 `needs_clarification` 또는 `not_evaluable` 제안 상태와 이유를 남긴다. [0008 결정](../decisions/0008-ai-candidate-policy.md)의 재작성·재계획·유효 후보 없음 구분은 다음 질문 후보에 적용한다. 사용자 재입력, service 복구·상태 매핑과 실제 저장 enum은 BE·FE와 함께 확정한다.

## 세 가지 판단을 분리

| 판단 | 보는 내용 | 반환 근거 |
| --- | --- | --- |
| 충분성 | 실제 질문에서 요구한 핵심을 충분·부분·불충분 중 어디까지 설명했는가 | Contract key, 확인/부족 항목, 답변 구절 |
| 기술적 정확성 | 주어진 조건·버전에서 설명이 타당한가 | 적용 조건, 검토 자료, 오류 또는 판단 보류 이유 |
| 기여·근거 정합성 | 본인·공동·타인·미확인 중 진술된 범위와 자료가 지원하는 범위를 구분 | 사용자 발언, 원문, 확인 한계 |

충분·부분·불충분의 의미 분류와 세 축 분리는 0004에서 승인했다. `sufficient/partial/insufficient` 등의 실제 enum·필드·저장 채택은 [내부 계약](../contracts.md)의 검토안으로 남긴다. 긴 답변·전문용어 수를 대리 점수로 쓰거나 정성 분류를 임의 숫자로 환산하지 않는다. `specificity`라는 오래된 필드 하나에 세 판단을 합치지 않는다.

사용자가 본인 역할이라고 설명한 것과 외부 자료로 확인된 것은 별개다. 구현·README·commit 수만으로 개인 작성·담당 업무를 확정하지 않는다.

기술적 설명이 길고 구체적이어도 틀릴 수 있으며, 정답에 가까워도 핵심 조건을 설명하지 않았을 수 있다. 유효한 대안을 모델 선호와 다르다는 이유로 오류로 처리하지 않는다.

자료가 기술 주장을 검증할 조건을 제공하지 않으면 해당 판단과 확인할 수 없는 범위를 보류한다. 사용자의 목소리·말투·Persona 이름에 따른 가점은 없다. Sprint 1 텍스트 평가를 실제 말하기 능력 검증으로 표현하지 않는다.

## 검증 가능한 주장과 Evidence

답변의 주장 원문을 보존하고 현재 선택 repo·준비 ref·지원 검색 범위에서 확인 가능한지 판단한다. 조회 대상·목적·확인할 조건을 구조화하여 Controller에 반환한다.

[0003 결정](../decisions/0003-evidence-lookup-policy.md)에 따라 기존 근거 부족, 현재 질문·후속 질문·평가에 대한 영향, 고정 SHA·허용 경로에서의 확인 가능성을 모두 만족하는 주장만 추가 조회 대상으로 제안한다. 조회하지 않은 경우와 정상 조회 후 미발견을 혼동하지 않는다. 이 판단이 service의 권한·범위·실행 상한 검사를 대체하지 않는다.

service는 승인된 Retriever로 근거를 얻고 `evaluation_basis`로 연결한다. 모델이 출력한 확인 표시는 원문·ID·ref 검증을 통과해야 유효하다.

| 자료 상태 | 허용 해석 |
| --- | --- |
| 설명과 일치하는 구현 발견 | 확인한 범위의 구현 존재를 지원; 개인 작성자·운영 성과는 별도 |
| 일부만 확인 | 부분 지원과 남은 한계 |
| 정상 검색 범위에서 미발견 | `unverified`; 코드 부재·거짓 단정 금지 |
| 분석 누락·도구 장애 | 검증 불가 사유; 사용자 감점 금지 |
| 실제 설명과 다른 코드 발견 | `answer_vs_code` 충돌 후보, 버전·조건 확인 후 중립 후속 질문 |

Sprint 1에는 문서 Claim 추출이 없으므로 `document_claims`를 답변 주장 저장소로 사용하지 않는다. answer_vs_code의 `claim_id`는 NULL이며 `verdict='unresolved'`다.

## 후속 답변과 정정

질문 A에서 부족한 내용을 후속 질문 B에서 보완했다면 두 Turn의 연결을 유지하고 이후 질문과 리포트에 반영한다. A의 원문이나 최초 분석을 모범답안으로 덮어쓰지 않는다. 이 보완·보존 원칙은 0004에서 승인했으며 물리 저장 형식까지 승인한 것은 아니다.

본인 기여 정정은 이후 질문 전제와 최종 피드백에 반영한다. 과거 답변 편집 API, 재평가 이력 모델, 리포트 재생성은 합의 없이 추가하지 않는다. 현재 세션의 이후 발언을 반영하는 것과 과거 기록 수정은 별개다.

## 실패와 확인 기준

구조화 출력의 parse/schema/semantic 실패는 [공통 계약](../contracts.md)과 0008을 따라 구분한다. invalid 결과를 부분 JSON·비어 있는 성공·추측한 기본값으로 Director에 넘기지 않는다. 실제 재시도 주체·횟수와 semantic 실패의 재호출 여부는 별도 합의하며, 이미 저장한 답변은 실패해도 보존한다.

필수 대조 사례:

- 같은 질문에 충분·부분·불충분 답변을 넣으면 Contract에 맞는 차이가 나타난다.
- 길고 틀린 답변과 짧고 맞는 답변을 별도 축으로 판단한다.
- 질문하지 않은 항목은 missing_points에 넣지 않는다.
- 팀원 구현을 본인 경험으로 가정하지 않고 정정을 반영한다.
- 유사하지만 무관한 코드와 버전이 다른 코드는 지지 근거로 채택하지 않는다.
- 도구 실패를 허위 주장으로 판단하지 않는다.
- 평가 불가 상태와 실제 설명 부족을 구분한다.
- 후속 보완을 최종 피드백에 연결한다.

품질 목표·오류 심각도 숫자·합격 임계값은 팀이 검수된 사례를 바탕으로 정한다. 샘플 몇 건 통과를 일반적 정확도로 보고하지 않는다.
