# 0011 면접 준비의 단계 재개와 만료 복구

- 상태: Proposed
- 날짜: 2026-10-30
- 관련 PR: #136, 선행 #135, 관찰 연결 #137
- 검토자: PR 리뷰에서 확인

## 맥락

면접 준비는 저장소 분석, Persona 초기화, 평가 기준 초기화, 첫 질문 구성 순서다.
첫 질문만 실패했을 때 성공한 원문 수집과 L2를 반복하면 재시도 계약과 비용 상한을 어긴다.
또한 worker가 DB claim을 남기고 중단되면 큐 재전달만으로 준비 상태를 회수할 수 없다.

## 결정

- 기존 `context_state` JSONB에 완료 단계와 입력·산출물 fingerprint를 저장한다.
  선택 run의 실제 바인딩 L1, 선택 저장소의 고정 SHA, 활성 프롬프트, 공고·기준·프레임을
  비교한다. 관련 없는 다른 SHA의 캐시 추가는 고정 자료 변경으로 보지 않는다.
- 성공한 L2·Evidence·초기화 결과를 DB에서 검증하고 실패한 단계부터 재개한다.
  소유권·고정 SHA·입력 또는 저장 산출물이 달라지면 외부 재조회로 보충하지 않고 거절한다.
- 각 단계의 산출물과 진행 상태를 같은 transaction에서 확정한다. 첫 질문은 #135의
  저장 경계를 사용하며 시작·저장 직전 같은 DB 세션의 비동기 guard로 소유권과 입력을 검사한다.
- 준비 owner의 lease는 90초, heartbeat는 20초다. 실제 배포 worker의 독립 reaper가
  시작 시와 30초 주기로 만료를 확인한다. lease가 없는 이전 claim 및 claim 전 유실 행은
  마지막 수정 이후 600초를 기다려 최근 작업을 보호한다.
- reaper는 첫 Director 기록을 먼저 잠그고 면접 행을 잠근 다음 현재 owner와 만료를
  재검사한다. 정확한 call ID 또는 같은 면접의 첫 Director pending만 닫고 실패 전환한다.
  새 owner가 들어왔으면 회수하지 않는다. 늦은 이전 결과는 첫 질문을 저장할 수 없다.
- 누락 LLM 설정·불완전 proxy 설정은 비재시도 오류로 분류한다. 검증 예외 원문과 비밀값은
  기록하지 않는다. 취소와 예상하지 못한 실행 예외는 상위 worker로 전파한다.

## 이유와 영향

새 테이블·공개 API 상태·자동 재시도 큐를 추가하지 않고 Postgres를 원본으로 사용한다.
전 작업의 무조건 재실행과 수동 claim 삭제는 성공 결과 반복 및 늦은 결과 경합을 막지 못한다.
사용자 REST 재시도는 실패 상태를 검증한 뒤 기존 enqueue 경로를 사용한다.

worker는 기존 세 작업과 분석 reaper를 보존하고 `max_tries=1`, `job_timeout=600`을 유지한다.
준비 시작 전 `2 × source timeout + 4 × LLM timeout + 30초 ≤ 600초`를 검사한다.
수집의 selector와 L2는 같은 두 번 호출 예산을 공유하며, 이는 DB 지연까지 보장하는 SLA가 아니다.
반영·되돌리기는 API와 worker를 같은 버전으로 수행하며 준비 중인 작업을 먼저 배출한다.
lease를 모르는 이전 worker와 혼용하면 오래된 고착 상태가 다시 생길 수 있다.

검증 방법과 실제 실행 결과는 [AI 구현 기록](../../ai/implementation.md)에서 관리한다.
공개 저장소 전용 앱 인증은 별도 공통 구현이며 사용자 토큰을 파일 조회로 확대하지 않는다.
