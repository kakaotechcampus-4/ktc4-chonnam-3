# AI 검증과 완료 기준

작성일: 2026-09-12. 상태: 평가자료 거버넌스는 0007, 합성 로컬 fixture·검수·비교 방법은 0009에서 Accepted. 수치 수용기준·개별 자료 검수는 미정이며 서비스 기능·모델 품질·배포는 아직 검증하지 않았다.

원본: [BE 테스트 전략](../../backend/docs/testing.md), [BE 검증](../backend/verification.md), [공통 통합 기준](../shared/checklist.md), [context AI의 평가 설계](../../context/AI.md). 작업 명령과 순서는 [AI 개발 안내](../../ai/README.md)를 따른다.

## 검증 단계를 구분한다

| 단계 | 검증 대상 | 통과해도 증명하지 못하는 것 |
| --- | --- | --- |
| 문서·정적 계약 | 링크, source/FIX/PENDING, YAML/JSON, 참조, 예시 | 실제 API·DB·모델 실행 |
| 순수 단위 | typed schema, quota, 선택 범위, mock task 출력 | 실제 모델이 해당 출력 생성 |
| BE 통합 | PostgreSQL 저장·제약, Redis 복구, worker·WS·API | FE 화면 완주·모델 품질 |
| 실제 모델 평가 | 검수 사례에서 실제 model/prompt 결과·비용·지연 | 서비스 전체의 정합성·배포 |
| 실제 서비스 흐름 | 실제 수집부터 텍스트 면접·종료·기록·리포트 | 후속 음성 품질 또는 미지원 범위 |

모든 실행 결과는 통과·실패·보류·미실행·범위 밖으로 구분한다. 빈 테스트 수집이나 형식 검사만으로 기능을 통과시켰다고 기록하지 않는다.

## 단계별 인수 조건

| 단계 | 선행 조건 | 검수 가능한 결과 |
| --- | --- | --- |
| 내부 계약 | 해당 [Proposed 계약](contracts.md)의 AI·BE 검토 | schema/version, 정상·실패 fixture, 저장 책임 |
| 개별 분석·판정 | mock client와 명시적 정책 설정 | L1/L2·JD·평가·질문·근거의 재현 가능한 결과 |
| 텍스트 면접 연결 | BE 저장·worker·WS 계약 합의 | 현재 답변부터 다음 질문까지, 9턴·중복·종료 검사 |
| 피드백 연결 | 확정 문답·근거와 생성 상태 | lazy report, Persona 관찰, 후속 보완, 프로필 집계 |
| 공개 리포트 완료 | 승인된 점수 또는 공통 계약 변경 | 유효한 200/202/409와 실제 FE 표시 |
| 실제 모델 검증 | provider/API model ID, budget, 검수 데이터 | model/prompt별 성공·실패·지연·비용 기록 |
| 출시 판단 | 미사용 자료 검증과 배포 환경 | 지원 범위의 전체 경로, 미해결 오류·결정 기록 |

W4~W7 핵심, W8~W9 후속, W12~W13 검증·배포라는 일정은 배경 계획이다. 실제 진척을 검증한 일정 보장은 아니다. W10~W11에 숨은 보충 작업을 배정하지 않는다. 담당 연결은 context의 구동한(진행·연결), 김진영(레포·근거), 박현솔(JD·Context·도메인), 송유석(질문·평가·후속 음성), 이건영(평가자료·리포트)을 참고하되 실제 구현 PR 소유자는 별도로 확인한다.

## 테스트 위치

### Sprint 1 vector 미도입 확인

[0002 결정](decisions/0002-sprint1-vector-search.md)에 따른 추가 확인사항이다. 아래는 구현 후 실행할 검증 조건이며 이번 문서 승인으로 통과한 검사가 아니다.

- embedding provider 호출·vector store 없이 repo 추천, L2 준비, 질문·답변 검증, 리포트·프로필의 해당 경로를 검사한다. 다른 미합의 계약이 막는 경로는 보류로 구분한다.
- 제한 검색 실패가 전체 tree/global search 또는 vector 검색의 자동 활성화로 이어지지 않는지 검사한다. 실패 원인과 확인 범위를 보존한다.
- BE가 Sprint 1 migration에 vector 선설치가 없는지 확인한 기록을 연결한다. 기존 배포 환경의 extension·데이터를 자동 제거하지 않는다.

### 추가 근거 조회 정책 확인

[0003 결정](decisions/0003-evidence-lookup-policy.md)의 AI 판단 정책을 검사한다. 아래는 구현 후 실행할 조건이며, 문서 승인만으로 테스트·모델 품질 통과를 선언하지 않는다.

| 사례 | 기대 결과 |
| --- | --- |
| 기존 근거 부족·판단 영향·허용 범위 내 확인 가능이 모두 충족됨 | 추가 조회 대상으로 제안하되 service의 권한·ref/path·budget 검증을 거침 |
| 세 조건 중 하나가 충족되지 않음 | 해당 조건별 사례에서 추가 조회를 제안하지 않음; 미조회 이유를 보존 |
| 조회하지 않음 | 정상 조회 후 미발견이나 검증 성공으로 기록하지 않음 |
| 정상 조회 후 허용 범위에서 미발견 | `unverified`; 코드 부재·거짓 단정 없음 |
| 분석 부족 또는 도구 장애 | 원인 구분·검증 불가 사유 보존, 사용자 감점 없음 |
| 유효한 코드와 실제 설명이 다름 | 충돌 후보와 버전·조건의 중립 후속 질문; 기존 `unresolved` 유지 |
| ref·위치가 다르거나 무관한 코드 | 지지 근거나 실제 불일치로 확정하지 않음 |

수치 상한·파일 열거·저장 enum은 별도 합의 대상이며 위 사례가 그 계약을 승인하지 않는다.

### 후보 검증·선택 정책 확인

[0008 결정](decisions/0008-ai-candidate-policy.md)이 승인한 다섯 후보 정책을 구현 후
검사한다. 아래 의미 분류는 Accepted이지만 runtime 재호출·상태·schema·quota·budget은
계속 별도 계약 대상이다.

| 후보 사례 | 기대 결과 |
| --- | --- |
| 구조화 후보 실패 | parse/schema/semantic 실패를 구분하고 임의 보충 없이 차단; 유효한 L1 batch 항목은 보존 |
| L2 관찰 | 고정 SHA에서 읽은 source가 뒷받침하는 범위만 사용하고 제한·무효 관찰을 구분 |
| Evidence 후보 | 기존 직접 근거, 정확히 알려진 파일, 사전 검증된 인접 범위 순으로 제안 |
| 질문 후보 복구 | 의미 보존 재작성, 거짓·stale 전제 재계획, 허용 범위 내 후보 없음으로 구분 |
| 도메인 frame 후보 | 검증된 서비스 관련성과 질문 목적 비반복 순으로 선택 |

### 정성 평가와 후속 보완 확인

[0004 결정](decisions/0004-answer-assessment-policy.md)에 따른 의미 정책 검사다. 아래 사례의 기대 판정은 원문·질문 범위에 근거하며 실제 모델 평가와 저장 통합 검사는 따로 실행한다.

| 사례 | 기대 결과 |
| --- | --- |
| 같은 질문의 충분·부분·불충분 답변 | 실제 질문의 핵심과 답변 구절에 연결된 충분성 차이를 기록 |
| 길고 구체적이지만 기술 오류가 있는 답변 | 충분성과 기술 오류를 분리; 길이·전문용어 수로 가점 없음 |
| 정상 제출한 “모르겠습니다”와 전송·처리 실패 | 유효한 답변 내용과 처리 오류를 구분; 거짓·기술 오류 자동 판정 없음 |
| 잘못된 질문 전제 또는 해석 불가 입력 | 평가 가능 여부부터 확인; 질문/입력 오류를 역량 부족으로 변환하지 않음 |
| 코드 근거가 부족하지만 질문의 핵심 설명은 관찰 가능 | 확인할 수 없는 판단만 보류; 모든 축을 자동 평가 불가로 만들지 않음 |
| 코드 존재 또는 README/commit 수만 있는 개인 기여 주장 | 구현 존재와 개인 기여 확인을 분리 |
| 후속 답변에서 설명 보완 또는 기여 정정 | 이후 질문·최종 피드백에 반영하며 원문·최초 분석 보존 |

질문 후보의 재작성·재계획·유효 후보 없음 분류는 [0008](decisions/0008-ai-candidate-policy.md)을 따른다. 실제 저장 enum·JSONB, runtime 재호출·사용자 복구와 상태 매핑, 턴 배분, 공개 점수·수치 통과율은 이 검사표가 확정하지 않는다. 아직 실행하지 않은 모델·DB 검사는 미실행으로 남긴다.

### 도메인 질문 생성 정책 확인

[0005 결정](decisions/0005-domain-question-policy.md)의 AI 생성 정책을 검사한다. 기존 21개는 개발용 후보이며 아래 표가 문구별 운영 품질·독립 검수·seed 설치 완료를 뜻하지 않는다.

| 사례 | 기대 결과 |
| --- | --- |
| 도메인이 없거나 신뢰하기 어려움 | 산업을 추측하지 않고 `etc` 사용 |
| 검증된 도메인 입력이 있음 | 해당 category를 활용하며 이유 없이 `etc`로 대체하거나 새 category를 만들지 않음 |
| 실제 경험·회사·규제·사용자 조건이 확인되지 않음 | 해당 조건은 가정형으로 표현하고 실제 경력·프로젝트 사실로 단정하지 않음 |
| 여러 목적의 질문 또는 기존 기술 질문의 표현만 바꾼 반복 | 하나의 중심 목적과 서비스 운영·사용자 영향·판단 이유에 맞게 생성되는지 확인 |
| JD 자격요건 검사·경력 단정·법률/의료 정답 보증·전용 점수화 후보 | 승인된 생성 정책을 위반하는 후보로 식별 |
| 기존 후보 표 | category별 3개·총 21개와 원문 유지; 운영 승인·설치와 구분 |

후보 복구와 frame 선택 의미는 [0008](decisions/0008-ai-candidate-policy.md)을 따른다. 실제 신뢰도 수치 기준·runtime 재호출과 사용자 상태 복구·턴 배분·활성 version·저장 계약은 별도 합의 대상이다. 문서 검사와 실제 모델 정책 준수 검사를 구분한다.

### 작업별 LLM 사용 정책 확인

[0006 결정](decisions/0006-task-llm-usage-policy.md)에 따른 구현 후 검사다. version 목록의 존재, 실제 LLM 호출, 단계·job 실행을 각각 구분한다.

| 사례 | 기대 결과 |
| --- | --- |
| Wanted 구조화 필드 분류 | 기존 규칙과 원문으로 변환하며 LLM client 미호출 |
| Wanted 입력 누락·수집/추출 실패 | LLM으로 요구사항·태그를 추측해 채우지 않음; 기존 실패와 실제 입력 범위 구분 |
| JD 처리 흐름 | `jd_extract` 단계·검증·저장을 유지하며 외부 7개 step을 삭제·재정렬하지 않음 |
| report 성공 후 프로필 갱신 | `profile_summary` job을 enqueue·실행하되 확정 데이터 집계만 수행하고 LLM 미호출 |
| L1 프로젝트 요약 | 프로젝트 기능·역할과 확인 한계만 설명; README·commit 수로 개인 기여 생성 없음 |
| 기존 LLM task와 prompt version 목록 | L1/L2·답변 평가·Director·리포트의 LLM 방향과 일곱 version 이름 유지 |
| 규칙 변환·집계 metadata | 비호출 작업을 모델 실행 결과로 기록하지 않음; 실제 version·저장 방식은 BE 합의에 따름 |

프로필 집계 단위·중복 제거·필드 매핑·공개 응답이 미합의면 해당 통합 검사를 보류한다. 이 표는 기존 코드의 구현 완료나 실제 모델·worker 테스트 통과 기록이 아니다.

### 테스트 경로

| 영역 | 사용할 위치 | 방법 |
| --- | --- | --- |
| AI 패키지 구조 | `ai/tests/` | 설치된 모듈 import, 타입 표시, 부작용·역의존 검사 |
| Director·도구·내부 계약 | `ai/tests/` | 계약·기능 구현 시 DB 없는 typed fixture와 fake tools 추가 |
| 단발 task·LLM 실패 | `ai/tests/` | 기능 구현 시 fake gateway, timeout/parse/semantic 실패 추가 |
| BE AI 설치·연결 | `backend/tests/agents/`, `backend/tests/llm_tasks/` | 현재 package import smoke; 실제 facade 검사는 기능 구현 시 추가 |
| 저장·큐·WS·리포트 | `backend/tests/features/` | PostgreSQL, Redis, 외부 GitHub/Wanted/LLM mock |
| 공개 직렬화 | `backend/tests/contract/` | camelCase·enum·required/null, 실제 serializer |

현재 작성된 것은 패키지 구조·설치 경계 테스트다. 위 표의 Director·task·저장·공개 직렬화 동작을 모두 구현했다는 뜻이 아니다. 테스트가 실제 작성·수집·실행됐을 때만 해당 결과를 보고한다. SQLite 대체로 PostgreSQL JSONB·배열·CHECK·UNIQUE 검증을 주장하지 않는다. 실행 명령은 [AI 개발 안내](../../ai/README.md)를 따른다.

## 모델 평가 자료 정책

평가는 [0007 결정](decisions/0007-evaluation-design-policy.md)에 따라 기존 네 종류로 구성하고 [0009 결정](decisions/0009-ai-evaluation-method.md)의 로컬 fixture·검수·비교 방법을 적용한다. 이 승인은 실제 데이터셋 구성·검수 완료가 아니며 production DB의 `eval_cases`·`eval_runs` 테이블을 새로 만드는 요구도 아니다.

| 사례 종류 | 실행 입력 | 사람이 확인할 기대 결과 |
| --- | --- | --- |
| 자료·근거 | repo/ref/원문, Wanted 필드, 검색 목적 | 확인 사실·관련 위치·누락·무관한 근거 배제 |
| 질문·답변·다음 행동 (Turn) | 질문·Contract·답변·Context | 허용 판정/목적/Persona, 금지 전제·행동 |
| 면접 흐름 (Session) | 합의된 텍스트 프로토콜과 답변 시나리오 | 시작·9턴·전환·중복·종료·저장 상태 |
| Report | 확정 문답·근거·판정·종료 | 강점/보완/미관찰·출처, 원문 보존 |

### 합성 로컬 fixture 계약

합성 로컬 사례는 `ai/evals/inputs/`와 `ai/evals/expectations/`의 JSON 쌍으로 표현한다.
두 JSON은 같은 `case_id`와 `version`으로 짝을 식별하며 loader는 mismatch, duplicate,
orphan 쌍을 거부한다.

입력 쪽은 사례 식별·분류·`split`·`source_group_id` 같은 loader 제어 정보와 실제 실행
입력 payload를 구분한다. 기대 쪽은 같은 식별자와 버전, 허용 결과, 금지 결과,
검수·control 정보를 표현한다. 모델에는 실행 입력 payload만 전달한다. 기대값, 검수
정보와 모든 loader control metadata는 prompt, retrieval query, tool input에서 제외한다.

이 최소 계약은 AI 로컬 합성 fixture만 대상으로 하며 파일명 규칙, 운영 파일/DB/공개
API schema를 정하지 않는다. 실제 JSON 사례와 loader·harness는 아직 없다. 원문에
확인되지 않는 사실을 기대 정답으로 쓰지 않으며 Question Contract처럼 실제 실행에
필요한 정보는 실행 payload에 유지한다.

## 사례 구성과 판정

같은 질문의 충분/부분/불충분, 구체적이지만 틀린 답변, 기여 정정, 유사하지만 무관한 코드, 잘못된 ref, 미발견, 도구 장애, 종료·중복을 포함한다. 도구를 쓸 때와 쓰지 않아야 할 때를 모두 검사한다.

초기 15~20건은 팀 전체의 구축·검수·실행 절차를 시험하는 제안 규모다. 0007은 이 수나 기능별 할당·최종 표본 수·split 비율을 확정하지 않는다. 같은 원본 프로젝트에서 파생한 모든 사례를 같은 source group으로 묶고, 해당 그룹이 개발용과 최종검증용에 걸쳐 배치되지 않도록 한다. 문답·후속 음성 등 형식이 달라도 같은 원본의 파생 자료라는 관계를 유지한다.

작성자 외 검수자가 원문과 기준을 확인한다. 여러 행동이 타당하면 허용 집합과 목적을 적는다. 정당한 새 질문에 평가 시나리오가 대응하지 못하면 서비스 오답으로 자동 처리하지 않고 사례 한계로 분리한다.

이는 검수 방법의 승인이지 개별 사례가 검수됐다는 뜻이 아니다. 실제 검수자·날짜·결과를 확인 후 기록한다. 검수자 불일치 사례는 양쪽의 출처 근거와 이유를 가진 `pending`으로 보존한다. 후속 검토는 허용 결과 확대, 사례 version 변경·재작성, 사례 무효화 중 하나가 될 수 있지만 모델 출력이나 모델 다수결에 맞춰 기대 결과를 바꾸지 않는다. 실제 담당자 배정, 연락·승인 경로와 실행 확인은 AI-L19에서 별도로 합의한다.

Holdout을 보고 기능을 수정했으면 해당 사례는 이후 회귀검사로 사용한다. 같은 source group의 파생 사례를 복사·이름 변경하여 미사용 최종검증 자료로 취급하지 않는다. 재분류 전 평가 이력·원문은 보존하고 자료 사용 목적의 변화를 남긴다. 결과가 좋았던 시도만 남기거나, 모델 결과에 맞춰 정답을 소급 변경하지 않는다.

grader는 허용 결과, 금지 결과, 의도적으로 모호한 사례, 유효하지 않은 참조, tool 실패 control로 검사한다. false accept와 false reject를 control 종류별로 구분한다. 실제 control 사례와 수치 기준은 AI-L19 합의 전 완성된 것으로 기록하지 않는다.

## 실행 기록과 수용기준

매 실행에 코드 commit, 실제 provider/model ID, prompt/schema/policy/dataset version, 입력 범위, 실행 횟수, 오류/보류, tool trace, 최종 DB 상태, token, latency를 남긴다. 비용은 실제 사용량과 확인한 가격표 버전으로 산정하며 값이 없으면 미수집으로 기록한다.

0007에 따라 통과뿐 아니라 실패·보류·미실행·범위 밖도 함께 기록한다. 실행하지 않은 검사를 성공으로 계산하거나 실패·보류를 결과에서 누락하지 않는다. 이 정책의 승인은 실제 실행 기록·비용 측정이 존재한다는 뜻이 아니다.

품질 수치는 분모·대상·오류 유형과 함께 보고한다. `pending`과 무효 사례는 전체 사례 수와 coverage에서 숨기지 않는다. 품질 지표는 독립 검수가 끝나 판정 가능한 사례를 분모로 별도 표시하고 제외 수와 이유를 함께 적는다. latency 분위수는 표본 수와 실패·timeout 포함 여부를 함께 적는다. 목표 정확도·지연·비용·추가 조회 상한을 문서에서 임의 생성하지 않는다. 최종 평가 전에 팀이 기준을 고정해야 한다.

다른 사용자 자료 노출, 없는 근거 생성, 답변 원문 변형, 종료 후 질문 확정 같은 필수 오류는 평균 품질 수치로 상쇄하지 않는다. 실패 원인이 서비스·자료·정답·채점기·환경 중 어디인지 구분한다.

### 통제된 비교 실험

baseline과 candidate는 같은 사례와 source group에서 비교하고 한 번에 바뀌는 요인을
분리한다. task별 실패, 품질, 비용, 지연을 함께 수집한다. 권한 거부, 잘못된 참조,
parser 실패, tool 실패, 근거 source 부재는 검색 방법의 결함과 별도 원인으로 분류한다.

현재 승인 범위 안의 방법 비교와 더 넓은 기능 범위를 제안하는 실험을 구분한다. 범위
확장이 있어야 풀리는 실패 사례도 버리지 않고 별도 집합으로 보존하지만 실제 확장
실험과 기능 채택은 사전 승인 뒤에만 진행한다. 이 방법은 vector/provider/model/rollout
선택, 측정값이나 합격 임계값을 승인하지 않는다.

### 평가 설계 정책 확인

0007 정책을 실제 평가 체계에 적용할 때 확인할 조건이다. 지금 통과한 데이터셋·모델 검사가 아니다.

| 검사 | 확인할 내용 |
| --- | --- |
| 네 종류의 사례 | 자료·근거, 질문·답변·다음 행동, 면접 흐름, 리포트의 구분 유지 |
| Source group 분리 | 같은 원본의 파생 사례가 개발용과 최종검증용에 걸쳐 배치되지 않음 |
| 로컬 JSON 쌍 | 같은 case ID·version으로 연결; mismatch·duplicate·orphan 거부 |
| 기대 결과·검수 | 기대/금지 결과를 구분하고 작성자 외 실제 검수 기록 확인; 불일치 근거·pending·해결 이력 보존 |
| 입력 격리 | 모델에는 실행 payload만 전달; 기대·검수·loader control metadata 혼입 없음 |
| Grader control | 허용·금지·모호·invalid ref·tool 실패별 false accept/reject 구분 |
| Holdout 사용 이력 | 개발에 사용한 자료는 이후 회귀검사로 구분하며 과거 기록 보존·미사용 자료로 위장하지 않음 |
| 전체 결과 기록 | 실패·보류·미실행 누락 없음; pending 전체 coverage와 품질 분모·제외 이유 구분 |
| 통제 비교 | 같은 사례, 단일 변경 요인, 실패 원인과 승인 범위별 결과 분리 |

수치 목표·표본 수·실행 환경·출시 기준은 계속 실측·팀 합의 대상이다. 자료 접근권한·사용 동의·보존/삭제 정책, 실제 검수자·control 사례와 채점기 실행도 이 표로 완료 처리하지 않는다. 위 검사는 loader·harness 구현 시 추가할 미래 검사다.
