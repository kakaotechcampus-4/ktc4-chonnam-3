# 도메인 질문 프레임

작성일: 2026-09-12. 상태: 생성 정책·개발용 후보 유지는 0005, 후보 선택 선호는 0008에서 **Accepted**. 운영 문구·검수·활성 version·저장은 **Proposed**.

이 문서는 Sprint 1 `domain_lead`의 승인된 질문 생성 정책과 검토할 seed 후보를 구분한다. 도메인 category 7개와 category별 3개 frame이라는 범위는 기존 FIX를 따른다. [0005 결정](../decisions/0005-domain-question-policy.md)에 따라 아래 21개 문구는 개발용 후보로 유지하며, 아직 설치된 seed나 승인된 운영 문구가 아니다.

관련 문서: [AI 아키텍처](../architecture.md), [내부 계약](../contracts.md), [검증](../verification.md), [AI 기준선](../decisions/0001-ai-baseline.md).

원본: [BE 면접 명세](../../../spec/backend/features/interview.md), [도메인 seed 작업](../../../backend/docs/task-03-seed.md), [공통 용어](../../../spec/shared/glossary.md), [DB 명세](../../../backend/docs/db-schema.md).

## 고정 범위와 역할

- category enum은 `finance`, `game`, `travel`, `shopping`, `medical`, `mobility`, `etc` 7개다.
- 각 category는 개인정보·민감정보, 신뢰성·운영, 사용자 경험·서비스 맥락의 세 축을 하나씩 가진다.
- `domain_lead`는 산업과 서비스 사용 맥락에서 판단 과정을 묻는다. JD 요구사항을 다시 읽거나 충족 여부를 추궁하는 Persona가 아니다.
- frame은 질문의 관점과 상황을 제공한다. 사용자에게 해당 산업 경험이 있다고 주장하거나, 특정 프로젝트가 그 도메인에 속한다고 단정하는 근거가 아니다.
- 질문은 가정형으로 제시할 수 있다. 사용자가 실제 경험이 없다고 답하면 그 사실을 감점 근거로 바꾸지 않고, 가정 아래의 판단과 trade-off만 확인한다.
- 법적 적합성, 규제 준수, 의학적 정확성 또는 의료 조언을 모델이 보증하게 하지 않는다. 필요한 경우 적용 법령·조직 정책·전문가 검토가 필요하다는 한계를 명시한다.
- 이 frame 자체는 질문 후보이며 score, 정답, 가중치, 합격 기준을 정의하지 않는다.

## 검토용 seed 후보 21개

각 셀은 하나의 질문 frame이다. 운영 prompt는 현재 Context에 없는 회사·규제·사용자 특성을 끼워 넣지 않고, 필요하면 조건을 가정으로 명시한 뒤 한 번에 한 질문으로 다듬는다.

| category | 개인정보·민감정보 | 신뢰성·운영 | 사용자 경험·서비스 맥락 |
| --- | --- | --- | --- |
| `finance` | 금융 서비스에서 민감한 거래 정보를 다뤄야 하는 상황이라면, 저장·조회·노출 범위를 어떤 기준으로 나누시겠어요? | 결제나 이체 처리 중 일부 시스템만 실패하는 상황이라면, 중복 처리와 상태 불일치를 어떻게 줄이고 운영자가 복구할 수 있게 하시겠어요? | 보안 절차가 사용 흐름을 복잡하게 만드는 상황이라면, 보호 수준과 사용 편의 사이의 결정을 어떤 정보로 내리시겠어요? |
| `game` | 플레이 기록이나 채팅처럼 개인을 식별할 수 있는 데이터가 생긴다면, 수집 목적과 보존 범위를 어떻게 제한하시겠어요? | 실시간 매칭이나 게임 세션에 장애가 생기는 상황이라면, 진행 중인 사용자의 상태를 어떻게 보호하고 복구 순서를 정하시겠어요? | 지연시간과 공정성이 동시에 중요한 기능이라면, 어떤 사용자 신호를 보고 품질 저하를 판단하고 개선 우선순위를 정하시겠어요? |
| `travel` | 여권 정보나 위치 이력처럼 민감할 수 있는 정보를 처리해야 한다면, 꼭 필요한 단계와 접근 권한을 어떻게 구분하시겠어요? | 외부 예약 사업자의 응답이 늦거나 서로 다른 상태를 반환한다면, 예약 확정 여부를 어떻게 관리하고 운영자가 확인할 수 있게 하시겠어요? | 가격이나 좌석 상황이 사용 도중 바뀌는 서비스라면, 사용자가 결정을 되돌리거나 대안을 찾을 수 있도록 어떤 정보를 언제 보여주시겠어요? |
| `shopping` | 배송지와 결제 관련 정보를 함께 다루는 기능이라면, 기능별 최소 데이터와 내부 노출 범위를 어떻게 정하시겠어요? | 주문·결제·재고 중 한 단계가 실패하는 상황이라면, 사용자에게 잘못된 확정을 주지 않으면서 재처리 가능한 흐름을 어떻게 설계하시겠어요? | 추천부터 결제까지 이탈이 많은 상황이라면, 사용자의 의도를 해치지 않으면서 어떤 지점을 먼저 관찰하고 바꾸시겠어요? |
| `medical` | 건강 상태처럼 매우 민감한 정보를 다루는 서비스라면, 사용자 동의·접근 범위·보존 필요성을 어떤 절차로 검토하시겠어요? | 서비스 장애가 사용자 안전이나 업무 연속성에 영향을 줄 수 있는 상황이라면, 시스템 복구와 사람에게 넘기는 절차를 어떻게 구분하시겠어요? | 건강 관련 정보를 보여주는 화면이라면, 시스템이 제공하는 정보와 전문가 판단이 필요한 부분을 사용자가 혼동하지 않도록 어떻게 표현하시겠어요? |
| `mobility` | 실시간 위치와 이동 이력을 사용하는 기능이라면, 서비스 제공에 필요한 범위와 불필요한 추적을 어떻게 구분하시겠어요? | 위치·배차·결제 중 하나가 불안정한 상황이라면, 진행 중인 이동을 보호하고 대체 흐름으로 전환하는 기준을 어떻게 세우시겠어요? | 도착 예상 시간이 계속 바뀌는 상황이라면, 정확도 한계를 숨기지 않으면서 사용자가 다음 행동을 결정할 수 있게 어떻게 안내하시겠어요? |
| `etc` | 도메인이 명확하지 않은 서비스에서 개인 또는 민감 정보가 포함될 가능성을 어떤 질문으로 확인하고, 확인 전에는 수집 범위를 어떻게 제한하시겠어요? | 이 서비스의 핵심 흐름을 아직 모르는 상황이라면, 실패 영향과 복구 우선순위를 정하기 위해 어떤 운영 정보를 먼저 확인하시겠어요? | 대상 사용자와 사용 환경이 충분히 알려지지 않았다면, 핵심 사용 맥락을 확인하고 기능 trade-off를 검증하기 위해 어떤 관찰이나 질문부터 시작하시겠어요? |

## 선택과 질문 생성

0005에서 확정한 것은 `etc` fallback, 하나의 중심 목적, 미확인 경험·조건의 가정형 표현, 기술 질문 중복·JD 검사·경력 단정·법률/의료 정답 보증·점수화 방지 정책이다. [0008 결정](../decisions/0008-ai-candidate-policy.md)은 이 조건을 통과한 후보 중 검증된 서비스 관련성과 이전 질문 목적의 비반복을 순서대로 선호한다. category 근거·신뢰 판단의 실제 입력 계약, 활성 version·저장 구조는 별도 검토 대상이다.

1. service가 검증된 공고·Context의 category를 전달한다. category가 없거나 신뢰할 수 없으면 모델이 산업을 추측하지 않고 `etc`를 사용한다.
2. Director는 남은 Turn 정책과 이전 질문을 확인한 뒤 `domain_lead`가 허용될 때 검증된 서비스 맥락과 더 직접 관련된 frame을 우선하고, 관련성이 같으면 이전 질문의 목적을 덜 반복하는 후보를 고른다.
3. Question Generator는 frame을 그대로 낭독하지 않는다. 확인된 서비스 맥락에서 하나의 중심 목적을 가진 질문으로 구체화하고, 확인되지 않은 경험·조건은 가정형으로 표시한다. 기술 질문을 표현만 바꿔 반복하기보다 서비스 운영·사용자 영향·판단 이유를 묻는다.
4. Controller는 중심 목적·이전 기술 질문과의 중복을 확인하고, JD 자격요건 검사로 변질되지 않았는지, 사용자 경력을 단정하지 않는지, 법률·의료 판단을 보증하지 않는지 검사한다.
5. 질문과 답변은 기존 Turn·AnswerAnalysis·Director 흐름을 사용한다. domain frame 전용 점수나 별도 Agent를 만들지 않는다.

`domain_lead` 질문은 코드 Evidence가 없어도 허용된다. 다만 답변에서 검증 가능한 코드 주장이 생기면 기존 Evidence Retriever 범위와 권한 안에서 `evaluation_basis`를 찾을 수 있다. frame 문구 자체를 사용자 프로젝트의 Evidence로 저장하지 않는다.

이 선호는 frame 축의 고정 순환, 축별 최소 횟수, 숫자 relevance 또는 모든 축 소진 의무가 아니다. 기존 Persona·Turn 정책을 바꾸지 않는다.

## Seed와 변경 관리

개발용 후보 유지와 생성 정책 승인은 운영 seed의 최종 문구 승인·독립 검수 완료를 뜻하지 않는다. 이번 결정에서 기존 21개 문구는 수정하지 않았으며, 검수자나 활성 version을 새로 지정하지 않는다.

`domain_question_frames`는 Sprint 1에 사용하는 운영 데이터다. 질문 문구를 Director 코드나 prompt 문자열에 하드코딩하지 않는다. seed 재실행은 idempotent해야 하며, 팀 검수 후 데이터와 연결된 version을 바꾸어 반영할 수 있어야 한다.

정확한 table column, 활성 version 선택 방식, 검토자 metadata는 이 문서가 새로 확정하지 않는다. [DB 명세](../../../backend/docs/db-schema.md)와 BE migration에서 기존 소유권을 유지하고, [내부 계약](../contracts.md)의 `domain_frames` 입력에는 선택한 category와 검수·version 정보를 전달한다.

위 21개 후보를 실제 seed로 설치하려면 문구별 독립 검수, 중복·유도 질문 검사, 각 category의 세 축 보존, 한국어 표현 검토가 먼저 필요하다. 문서에 존재한다는 이유만으로 운영 seed 설치가 완료됐다고 보고하지 않는다.

## 검증 기준

- category가 FIX 7개 외 값으로 확장되지 않는다.
- 각 category에 세 축이 정확히 하나씩 있으며 후보가 총 21개다.
- `domain_lead` 질문이 JD 요구사항 검사나 사용자 경력 단정으로 바뀌지 않는다.
- 유효한 후보가 여러 개면 검증된 서비스 관련성과 목적 비반복 순으로 선택하며 고정 순환·새 quota를 만들지 않는다.
- 법적·의학적 정답을 생성하거나 전문가 조언으로 표현하지 않는다.
- frame 선택과 문구 변경이 version이 있는 seed 데이터로 재현되며 코드 하드코딩이 없다.
- score, 합격 기준, 새 API·Agent·테이블을 만들지 않는다.
- 실제 모델 평가는 [AI 검증](../verification.md)의 질문 전제·Persona·반복·범위 검사를 함께 통과해야 한다.
