## 결정과 이유

해당 답변 Turn의 `interview_turns` 행에 답변 분석과 다음 행동 판단을 각각 보관한다.

| 컬럼 | 형식 | 책임 |
| --- | --- | --- |
| `interview_turns.analysis` | JSONB | 답변의 충분성·정확성·기여 및 근거에 대한 분석 결과와 해당 분석의 처리 상태·실패 이유 |
| `interview_turns.decision` | JSONB | 최종 다음 행동 판단·중간 조회 요약과 해당 판단의 처리 상태·실패 이유 |

하나의 JSONB 객체 안에 두 결과를 묶는 대안보다 결과별 검증·저장·조회 단위가 명확하다. 답변 분석 후 다음 행동을 판단하는 기존 흐름과도 맞는다. 기존 DB 기준에 따라 `answer_analyses`, `director_decisions` 별도 테이블은 만들지 않는다.

## 중간 조회 요약 포함 — 2026-09-21 추가 결정

`decision`에는 최종 판단·짧은 이유와 함께, 그 판단을 위해 실제 수행한 중간 조회의 요약을 실행 순서대로 보관한다. 어떤 자료를 조회했고 어떤 결과를 얻었는지 확인할 수 있어야 한다. 최종 판단만 보관하는 대안보다 기록은 늘지만, 추가 조회가 판단에 어떤 정보를 제공했는지 추적할 수 있다.

`analysis`는 답변이 무엇을 충족했고 무엇이 부족하거나 미확인인지 다루고, `decision`은 이를 바탕으로 수행한 조회와 정한 다음 행동을 다룬다. 조회 요약을 추가했다는 이유로 최초 분석을 덮어쓰지 않는다.

- 실제 실행 결과를 요약한다. 조회 제안만으로 실행한 것으로 기록하지 않는다. 찾지 못함·분석 한계·도구 오류는 기존 조회 정책에 따라 구분하며, 자료를 찾지 못했다고 답변을 거짓으로 단정하지 않는다.
- 조회 요약은 원문 전체나 모델의 숨은 사고과정이 아니다. 기존 Evidence 원문과 근거 연결, 별도 호출 횟수·오류·지연 기록의 책임을 대체하지 않는다.
- 이 단계는 요약 포함 범위를 확정하며 요약 항목·참조·상태값은 아래 일곱 필드 형식을 따른다. 길이·개수·실행 상한은 AI-L04에서 정한다. 요약을 위한 추가 모델 호출을 승인하지 않는다.
- 최종 판단 생성이 실패해도 수행한 중간 조회 요약을 보존하고, 각 조회가 끝날 때마다 저장한다. 구체적인 범위와 구조는 아래 후속 결정을 따른다. ToolResult 부분 실패 해석은 AI-L02, 저장 충돌·중단 복구는 AI-L12에서 정한다. 미완료·실패를 정상 최종 판단이나 정상 종료로 기록하지 않는다.

## 처리 상태·실패 이유를 각 JSON에 포함 — 2026-09-21 추가 결정

분석의 처리 상태와 실패 이유는 `analysis` 안에, 다음 행동 판단의 처리 상태와 실패 이유는 `decision` 안에 보관한다. 이번 용도로 별도 상태 컬럼을 추가하지 않는다. 별도 컬럼은 상태별 검색에 유리할 수 있지만, 현재 단계에서는 각 결과와 처리 상태를 같은 객체에서 확인하는 방식을 선택한다.

- 두 작업의 처리 상태를 각각 관리한다. 분석이 끝난 뒤 다음 행동 판단이 실패했다는 이유로 분석 결과를 실패로 바꾸거나 지우지 않는다.
- 처리 상태는 BE service가 실제 실행·검증 결과를 바탕으로 확정한다. 답변의 충분성·정확성 평가와 구분하며, 답변이 부족하거나 자료 부족으로 평가를 보류했다는 사실 자체를 시스템의 처리 실패로 기록하지 않는다.
- 이 단계는 상태·실패 이유의 저장 위치를 확정하며, 상태의 종류·공통 저장 형식·조회마다 요약 저장과 실패 시 보존은 아래 후속 결정에 따른다. 최종 판단과 항목별 분석 저장 구성·판단 상태 세 가지는 아래 후속 결정을 따르며 analysis.result 미채택 항목 이름·assessment 상세 내용·내부 null·참조는 AI-L02, 저장 충돌·중단 복구는 AI-L12에 남는다.
- 기존 Turn·면접 상태, 공개 오류 응답, 재시도와 호출 기록의 책임은 유지한다. 내부 결과의 상태를 공개 API에 그대로 노출하거나 자동 재시도를 추가하는 결정이 아니다.

## 네 가지 처리 상태 — 2026-09-21 추가 결정

`analysis`와 `decision` 각각의 일반 처리 흐름을 미시작·처리 중·완료·실패로 구분한다. 미시작과 처리 중을 하나로 묶는 대안보다 시작 시 상태 갱신이 필요하지만, 작업을 아직 시작하지 않았는지 실제로 시작했는지 기록에서 구분할 수 있다.

| 상태의 의미 | 판단 기준 |
| --- | --- |
| 미시작 | 해당 분석 또는 판단 작업을 아직 시작하지 않음 |
| 처리 중 | 해당 작업을 시작했으며 완료나 실패가 아직 확정되지 않음 |
| 완료 | 해당 작업의 유효한 결과를 검증해 확정함 |
| 실패 | 해당 작업을 유효한 결과로 완료하지 못했고 처리 실패가 확정됨 |

- 두 JSON의 상태는 독립적이다. 답변을 기다리는 Turn의 분석·답변 후 판단은 미시작이며, 준비 단계의 첫 질문 생성을 가상의 답변 분석으로 기록하지 않는다.
- 검증된 평가 보류 결과는 분석 완료일 수 있다. 판단 완료는 다음 질문의 전달 완료나 면접 전체 완료와 다르다. 9번째 답변 뒤 허용된 정상 종료 판단도 유효한 판단 결과다.
- 처리 중이라는 기록만으로 프로세스가 현재 살아 있다고 보장하지 않는다. 작업 중단·사용자 종료·재시작 시 상태 정리, 오래 남은 처리 중 상태의 복구와 조회 요약 외 상태 갱신의 정확한 transaction 경계는 AI-L12 및 관련 면접 복구 계약에서 정한다. 사용자 종료나 일시적 연결 끊김을 임의로 처리 실패로 바꾸지 않는다.
- 이 단계는 네 가지 상태의 구분과 의미를 확정하며, 저장 코드·공통 필드명·형식 버전과 result/error의 null 규칙은 아래 공통 저장 형식 v1을 따른다. 새로운 자동 재시도나 완료된 최초 분석의 재실행을 승인하지 않는다.

## 최종 판단 실패 시에도 조회 요약 보존 — 2026-09-21 추가 결정

최종 판단 생성이 실패해도, 그때까지 실제 수행한 조회의 자료·결과 요약을 해당 Turn의 `decision` 안에 실패 상태·실패 이유와 함께 저장한다. 성공했을 때만 새 요약을 저장하는 대안보다 기록은 늘지만, 어느 자료를 확인한 뒤 판단이 실패했는지 추적할 수 있다.

- 서비스가 실패를 감지해 처리할 때 확보한 실제 조회 결과를 남긴다. 결과 없음·분석 한계·도구 오류도 기존 조회 정책에 따라 구분한다. 실행하지 않은 조회나 얻지 못한 결과를 만들어 채우지 않는다.
- 조회 요약이 있어도 최종 판단이 성공한 것은 아니다. 실패를 완료나 정상 종료로 바꾸지 않으며, 이미 저장된 답변·최초 분석·Evidence와 조회 기록을 지우거나 덮어쓰지 않는다.
- 이 단계는 실패 처리에서 남길 내용의 범위를 확정하며, 조회별 저장 시점은 아래 후속 결정을 따른다. 정확한 transaction·중복 방지는 AI-L12에 남는다. 서버·프로세스가 갑자기 종료되거나 DB 쓰기 자체가 실패했을 때의 완전한 보존·복구 보장까지 확정하지 않는다.
- 공통 저장 형식은 아래 v1, 최종 판단과 항목별 분석 저장 구성·판단 상태 세 가지는 아래 후속 결정을 따르며 analysis.result 미채택 항목 이름·assessment 상세 내용·참조·내부 null은 AI-L02, 기록 길이·개수 상한은 AI-L04, 보존기간은 AI-L18에서 정한다. 요약 보존을 위한 추가 모델 호출이나 자동 재실행을 승인하지 않는다.

## 조회가 끝날 때마다 저장 — 2026-09-21 추가 결정

`decision`의 중간 조회 요약은 각 조회가 끝나 실제 결과가 확보될 때마다 DB에 저장한다. 최종 판단의 성공·실패가 정해질 때까지 모아 두는 대안보다 DB 갱신은 늘지만, 이후 작업이 갑자기 중단돼도 이미 저장한 조회 요약을 확인할 수 있다.

- 정상 조회뿐 아니라 찾지 못함·분석 한계·도구 오류가 확정된 조회도 실제 결과에 맞게 요약해 저장한다. 실행 제안만 있거나 응답을 받기 전에 프로세스가 종료된 조회를 완료된 결과로 만들지 않는다.
- 외부 조회가 진행되는 동안 DB transaction을 열어 두지 않는다. 결과를 받은 뒤 BE가 현재 면접·Turn과 결과의 유효성을 확인하고 짧은 transaction으로 요약을 저장한다. 사용자 종료 뒤 늦게 온 결과의 기존 차단 원칙을 유지한다.
- 조회 요약 저장은 해당 조회의 기록이며 최종 판단 완료가 아니다. 최종 성공·실패를 저장할 때 이미 저장한 요약을 잃거나 같은 조회를 중복 기록하지 않아야 한다. seq의 실행 구분은 아래 항목 형식을 따르며 번호 부여·중복 방지·동시 갱신 제약은 AI-L12에서 정한다.

- 근거는 assessment 안의 해당 판단에 연결한다. 같은 내용을 공통 reason·limitations·refs에 중복 저장하지 않으며, 구체적인 근거 참조 형식은 이번 결정에 포함하지 않는다.
- 전체 보류에서도 객체를 유지하고 assessment만 null로 둔다. 평가 대상 제외의 항목 전체 null, 분석 실행 실패의 result 전체 null과 구분한다.
- 공통 세 필드·필수 유지·상태별 조합과 scope/reason 목록을 확정한다. 세 평가 항목의 이름과 assessment 상세 필드·판정값·내부 null·근거 참조 및 나머지 분석 내용은 AI-L02, 길이·개수 상한은 AI-L04에 남는다.

## 충분성의 기존 두 목록 유지 — 2026-09-21 추가 결정

충분성 assessment에 covered_points·missing_points를 유지한다. 사용자의 최소 변경 선호에 따라 기존 설계안으로 요구사항을 충족하고 단일 points 목록으로 교체하지 않는다. 기존 계약·분석 코드는 미구현이므로 운영 데이터의 호환성 때문에 필요한 결정이라는 뜻은 아니다.

- covered_points는 실제 설명한 부분과 답변 근거, missing_points는 설명하지 못한 부분과 판단 이유를 해당 Question Contract의 required_points.key에 연결한다.
- 일부만 설명한 항목은 같은 key가 양쪽에 있을 수 있으나 충족 부분과 부족 부분을 구분한다. 같은 내용을 복사하거나 두 목록 길이를 합산해 확인 항목 수로 사용하지 않는다.
- 판단 불가인 범위는 기존 deferred에 남긴다. 평가 범위 밖 항목을 부족으로 만들거나 답변 인용을 지어내지 않는다.
- assessment가 객체이면 두 목록을 유지하고 해당 내용이 없으면 빈 목록으로 표현한다. 전체 보류의 assessment는 기존대로 null이다.
- 두 목록의 이름·위치·의미를 확정하며 전체 충분성 판정은 아래 후속 결정을 따른다. 목록 항목의 내부 필드·답변 근거 참조는 AI-L02에 남긴다. 이후 결정도 기존안으로 충분하면 유지하고 필요한 규칙만 보완한다.

## 일부 보류 시 전체 충분성 판정은 null — 2026-09-21 추가 결정

충분성 전체 판정은 기존 sufficient·partial·insufficient 세 값을 채택한다. evaluated일 때만 판정값을 기록하고 partially_evaluated이면 assessment 객체와 covered_points·missing_points는 유지하면서 전체 판정값만 null로 둔다. 보류 내용은 기존 deferred에 보존한다.

기존 필드 구성을 유지하면서 상태별 규칙을 보완한다. 보류 부분이 전체 결과에 영향을 주지 않는 경우를 따로 허용하는 대안은 예외 기준과 추가 검증이 필요하므로 채택하지 않는다. not_evaluable의 assessment 전체 null과 평가 대상 제외의 항목 전체 null은 그대로 유지한다.

이 결정은 충분성의 판정값과 상태별 null 규칙에 한한다. 세 축의 종합 평가상태나 공개 점수는 만들지 않으며, 판정 필드명·경로와 목록 항목의 상세 구조·참조 형식은 AI-L02의 나머지 계약에 남는다.

## 적용 경계

- 저장 위치·컬럼명·JSONB 형식과 공통 저장 형식 v1, `decision.retrievals`의 조회마다 저장과 실패 시 보존을 확정한다. 공통 오류 정보·일곱 필드 조회 요약·최종 판단 다섯 항목·대표 intent 하나와 구분 기준, 평가 항목별 상태·내용·이유 저장·판단 상태 세 가지·평가 대상 제외 항목의 null·공통 평가 객체 세 필드 및 종합 평가상태 제외도 확정하며 analysis.result 미채택 항목 이름·assessment 상세 내용·내부 null·참조, ToolResult 전체 계약·부분 실패 해석과 나머지 오류 코드 매핑은 AI-L02 및 해당 실패 계약에서 계속 검토한다.
- 이 컬럼에 저장하는 결과와 모델 원시 출력은 구분한다. 원시 출력·호출 기록의 보관 위치와 권한·보존기간은 AI-L18에서 정한다.
- [0004 결정](0004-answer-assessment-policy.md)의 원문·최초 분석 보존과 후속 보완 원칙을 유지한다. 컬럼을 분리했다는 이유로 후속 답변을 반영해 최초 분석을 덮어쓰지 않는다.
- 최종 상태 확정과 DB 저장은 BE service가 맡는다. 정확한 transaction·동시성·중복 방지는 AI-L12에서 정하며, 두 컬럼을 나누는 결정으로 저장 성공·실패 복구까지 확정하지 않는다.
- 공개 API에 두 객체를 그대로 노출하지 않는다. Question Contract 최종 저장 형식은 [0012 결정](0012-question-contract.md)을 유지하며 다른 내부 객체의 schema를 대신하지 않는다.

## 영향과 확인 기준

내부 계약·아키텍처·답변 평가·면접 흐름·DB 안내와 작업 지침에 컬럼·조회 요약·네 가지 처리 상태·최종 판단 다섯 항목·평가 항목별 상태와 이유·판단 상태 세 가지·평가 대상 제외 항목의 null·공통 평가 객체 세 필드 및 저장 위치를 반영한다. 실제 migration·타입·저장 코드는 구현하지 않았다. 구현 시 미시작과 처리 중이 구별되는지, 같은 Turn에 올바른 결과와 해당 작업의 처리 상태·실패 이유가 연결되는지, 실제 조회 순서·결과와 요약이 일치하는지, 최종 판단 실패 시에도 확보한 조회 요약이 남는지, 한 결과의 저장이 다른 결과나 최초 분석을 덮어쓰지 않는지 검증한다. 답변의 부정적 평가와 실행 실패가 혼동되지 않아야 한다.

## 대체 관계

AI-L02의 analysis/decision 저장 컬럼·공통 바깥 구조 v1·상태 코드·결과/오류의 null 규칙과 실패 시를 포함한 조회 요약 보존, AI-L12의 조회 요약 저장 시점 보류를 해소한다. 최종 판단의 다섯 항목·대표 intent 하나와 구분 기준, 평가 항목별 상태·내용·이유 저장·판단 상태 세 가지·평가 대상 제외 항목의 null·공통 평가 객체 세 필드 및 종합 평가상태 제외도 확정했다. analysis.result 미채택 항목 이름·assessment 상세 내용·내부 null·참조와 다른 계약은 계속 Proposed이며, 저장 충돌·저장 실패 처리·중단 복구는 AI-L12에 남는다.
