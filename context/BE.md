\# 기술 스택



\### FastAPI



Springboot을 쓰기에는 \*\*같은 스키마에 대해서 JavaDTO와 Python dict로 두 번 정의\*\*하게 되고, AI와 일치시킬 때 계약 불일치 생길 수도 있음.



\### PostgreSQL



AI쪽에서 pgvector 활용할 가능성 염두에 두고 있음.

pgvector = 고차원 벡터 임베딩을 직접 저장하고 유사도 검색을 수행할 수 있도록 지원하는 오픈소스 확장(Extension) 프로그램



\### Redis



깃허브 레포 분석 병렬 수행 + 면접 진행 중 DB에 저장과 동시에 작업할 때는 Redis에 저장된 내용을 빠르게 가져와서 사용하는 느낌. (캐시 역할 - 굳이 보조저장장치까지 가지 않게끔.)



\- Redis 함께 보면 좋을 부분 정리

&#x20;   

&#x20;   ## 1. Redis를 언제 쓰는가 — 판단 기준

&#x20;   

&#x20;   Redis를 "빠른 저장소"로 이해하면 계속 오용하게 됩니다. 정확한 정의는 \*\*메모리에 사는 자료구조 서버\*\*입니다. 여기서 성질 세 개가 따라옵니다.

&#x20;   

&#x20;   | 성질 | 결과 |

&#x20;   | --- | --- |

&#x20;   | 메모리에 산다 | \*\*비싸다.\*\* RAM은 디스크의 수십 배 가격. 큰 데이터를 넣으면 안 됨 |

&#x20;   | 메모리에 산다 | \*\*날아간다.\*\* 재시작/장애 시 유실 가능(AOF/RDB로 완화하되 Postgres 수준의 보장은 아님) |

&#x20;   | 프로세스 밖에 있다 | \*\*여러 프로세스가 같은 상태를 공유\*\*할 수 있다 ← 이게 진짜 존재 이유 |

&#x20;   

&#x20;   그래서 쓸 자리와 쓰면 안 되는 자리가 명확합니다.

&#x20;   

&#x20;   \*\*✅ Redis에 맞는 데이터\*\*

&#x20;   

&#x20;   - 날아가도 되는 것 (재계산·재요청으로 복구 가능)

&#x20;   - 만료 시점이 자연스럽게 있는 것 (TTL — 세션, 캐시, 인증 코드, 레이트리밋 카운터)

&#x20;   - \*\*여러 프로세스가 공유해야 하는 것\*\* (작업 큐, 분산 락, 멀티 인스턴스 Pub/Sub)

&#x20;   - 작고, 자주 읽고 쓰는 것

&#x20;   

&#x20;   \*\*❌ Redis에 두면 안 되는 데이터\*\*

&#x20;   

&#x20;   - 나중에 조회·분석해야 하는 것 → 그건 DB의 일

&#x20;   - 유실되면 곤란한 것

&#x20;   - \*\*큰 바이너리\*\* (이미지, 오디오, 파일) → 오브젝트 스토리지(S3)의 일

&#x20;   - 단일 프로세스 안에서만 쓰는 임시 변수 → 그냥 지역 변수면 충분

&#x20;   

&#x20;   한 줄 기준: \*\*"이거 날아가면 어떻게 되지?"에 "다시 만들면 됨"이면 Redis, "큰일 남"이면 PostgreSQL, "용량이 큼"이면 S3.\*\*

&#x20;   

&#x20;   ## 2. 제안하신 음성 흐름 판단 — 멘토님이 맞습니다

&#x20;   

&#x20;   두 흐름 모두 위 기준 세 개를 동시에 위반합니다.

&#x20;   

&#x20;   \*\*질문 생성 흐름 — "꼬리질문을 Redis에 저장"\*\*

&#x20;   

&#x20;   꼬리질문 텍스트는 \*\*날아가면 큰일 나는 데이터\*\*입니다. DEVON\_데이터모델.md에서 `interview\_turns.question\_text`로 영속 저장되고, `turn\_evidences`로 근거와 연결되고, 나중에 리포트 채점 근거(`evidence\_turn\_nos`)로 다시 읽힙니다. 즉 \*\*정답지는 이미 PostgreSQL로 정해져 있습니다.\*\* 여기에 Redis를 더하면 "같은 데이터가 두 곳에 있는데 어느 쪽이 진실인가" 문제만 생깁니다.

&#x20;   

&#x20;   그리고 "저장 + FE에 전달"이 목적이라면 Redis를 경유할 이유가 없습니다. \*\*Redis는 A와 B 사이의 배달 경로가 아닙니다.\*\* 생성 → DB 저장 → TTS → 응답으로 바로 내려주면 끝입니다.

&#x20;   

&#x20;   \*\*답변 분석 흐름 — "사용자 음성을 Redis에 저장"\*\*

&#x20;   

&#x20;   이쪽이 더 위험합니다. 1분짜리 음성은 수백 KB\~수 MB고, 이걸 RAM에 올리는 겁니다. 동시 사용자 10명이면 프리티어 인스턴스 메모리가 바로 압박받습니다. \*\*오디오 바이너리는 Redis가 가장 못 하는 일\*\*입니다.

&#x20;   

&#x20;   게다가 문서상 음성 원본은 1단계 저장 대상이 아닙니다 — `interview\_turns`의 `audio\_uri`는 2단계 확장 항목(932줄)이고, 저장하기로 결정한다 해도 정답은 \*\*S3에 올리고 DB에 URI만\*\* 남기는 형태입니다.

&#x20;   

&#x20;   ## 3. 그럼 음성 흐름은 이렇게 짜면 됩니다

&#x20;   

&#x20;   Redis 없이 이렇게 됩니다.

&#x20;   

&#x20;   ```

&#x20;   \[질문]  Director가 질문 생성

&#x20;             → interview\_turns INSERT (question\_text)   ← 영속

&#x20;             → TTS 호출

&#x20;             → 오디오를 응답 스트림으로 FE에 바로 전달   ← 저장 안 함, 흘려보냄

&#x20;   

&#x20;   \[답변]  FE가 오디오 청크를 WebSocket으로 전송

&#x20;             → 서버 프로세스 메모리에 버퍼링          ← 그냥 지역 변수

&#x20;             → STT 호출

&#x20;             → interview\_turns UPDATE (answer\_text)     ← 영속

&#x20;             → Director에게 텍스트 전달

&#x20;   ```

&#x20;   

&#x20;   \*\*저장이 필요한 건 텍스트뿐이고, 그건 PostgreSQL의 일입니다.\*\* 오디오는 흘려보내면 됩니다.

&#x20;   

&#x20;   WebSocket 연결은 한 프로세스에 붙어 있으므로, 스트리밍 중간 버퍼는 그 프로세스의 메모리로 충분합니다. Redis Pub/Sub이 필요해지는 건 \*\*서버를 2대 이상으로 늘려서 FE의 WS 연결이 어느 인스턴스에 붙을지 모를 때\*\*뿐입니다. 서버 1대면 해당 없습니다.

&#x20;   

&#x20;   ## 4. "그럼 진행률 표시에 쓰면 되나?" — 이것도 아닙니다

&#x20;   

&#x20;   여기가 중요한데, 문서에 이미 답이 나와 있습니다. `analysis\_jobs` (P0) 정의를 보면:

&#x20;   

&#x20;   | 필드 | 타입 |

&#x20;   | --- | --- |

&#x20;   | `steps` | JSONB — 4-2-v2 체크리스트 원천 |

&#x20;   | `current\_step` | VARCHAR(30) |

&#x20;   | `progress` | SMALLINT (0\~100) |

&#x20;   

&#x20;   \*\*진행 상태를 PostgreSQL 컬럼으로 두기로 이미 결정돼 있습니다.\*\* 설계 원칙 4번("비동기 작업은 1급 엔티티다 — Job의 단계별 상태가 저장돼야 한다")이 그 근거고요. 실패 사유(`error\_code`)도 화면 분기에 쓰이니 영속이 필수입니다.

&#x20;   

&#x20;   게다가 4-2-v2의 단계는 4개(`repo\_fetch` → `jd\_extract` → `match\_score` → `prepare\_view`)입니다. \*\*Job 하나당 UPDATE 4번\*\*입니다. 이 정도 쓰기량 때문에 Redis를 도입할 이유는 없습니다. (Redis가 의미 있어지는 건 초당 수십 번씩 progress를 갱신해서 DB에 부담이 갈 때인데, 여긴 그런 상황이 아닙니다.)

&#x20;   

&#x20;   제가 지난 답변에서 "Job 큐 때문에 Redis"라고 말씀드린 걸 "진행률 표시 용도"로 옮겨 이해하신 것 같은데, 그 둘은 다른 얘기입니다. 아래에서 구분하겠습니다.

&#x20;   

&#x20;   ## 5. 이 프로젝트에서 Redis의 자리는 딱 하나입니다 — 워커 브로커

&#x20;   

&#x20;   \*\*진행률 저장(❌)과 작업 큐(✅)는 다릅니다.\*\*

&#x20;   

&#x20;   - \*\*진행률 저장\*\* = "지금 3단계, 60%" 라는 \*상태\*를 어디에 쓸 것인가 → PostgreSQL

&#x20;   - \*\*작업 큐\*\* = "이 Job을 어느 워커가 집어갈 것인가"를 관리하는 \*대기열\* → 여기가 Redis 자리

&#x20;   

&#x20;   레포 분석은 수십 초\~수 분 걸리는 작업이라 API 요청 안에서 처리할 수 없습니다. 별도 워커 프로세스가 필요하고, API 서버와 워커는 \*\*다른 프로세스\*\*입니다. 이 둘이 공유하는 대기열 — 이게 앞서 말한 "프로세스 밖에 있다"는 Redis의 존재 이유에 정확히 들어맞습니다. Celery나 ARQ의 브로커로 쓰는 게 그겁니다.

&#x20;   

&#x20;   한 가지 더 짚어두면, \*\*캐시조차 이 프로젝트에선 Redis가 아닙니다.\*\* `repo\_analyses (P0) — 레포별 AI 분석 캐시`가 이미 PostgreSQL 테이블로 설계돼 있고, 설계 원칙 1번이 "캐시성 데이터와 세션 스냅샷을 분리한다"로 그 구조를 못박아뒀습니다. GitHub API rate limit(`rate\_limited` 에러 코드)도 이 테이블에서 흡수됩니다.

&#x20;   

&#x20;   ## 6. 그래서 내일 회의에서 — 정직하게 말씀드리면

&#x20;   

&#x20;   위를 다 합치면 이렇습니다. \*\*Redis는 이 프로젝트에서 "없으면 안 되는" 컴포넌트가 아닙니다.\*\* 자리가 워커 브로커 하나로 좁혀지고, 그것조차 PostgreSQL로 대체할 수 있습니다(`SELECT ... FOR UPDATE SKIP LOCKED`). 멘토님이 계속 이유를 물으시는 게 이 지점입니다. 약한 근거로 들어가면 또 막힙니다.

&#x20;   

&#x20;   선택지는 둘이고, \*\*저는 A를 추천\*\*합니다.

&#x20;   

&#x20;   \*\*A. Redis 도입 — 근거는 "Celery/ARQ를 쓰기 위해서" 하나\*\*

&#x20;   

&#x20;   이렇게 말하세요: \*"레포 분석이 수 분짜리 작업이라 워커가 따로 필요하고, 재시도·타임아웃·실패 처리를 직접 구현하는 대신 검증된 큐 라이브러리를 쓰려고 합니다. 그 라이브러리의 브로커가 Redis입니다."\*

&#x20;   

&#x20;   - 얻는 것: `retry\_count`, `error\_code`, `llm\_timeout` 같은 필드가 문서에 이미 있는데, 그 재시도/타임아웃 로직을 \*\*직접 안 짜도 됩니다.\*\* LLM 호출이 자주 실패하는 작업이라 이게 실제로 값어치가 있습니다

&#x20;   - 비용: `docker compose`에 5줄, 환경변수 하나. \*\*Redis 자체를 깊게 공부할 필요는 거의 없습니다\*\* — 큐 라이브러리가 감싸주기 때문에 팀이 직접 Redis 명령어를 쓸 일이 사실상 없습니다

&#x20;   

&#x20;   \*\*B. Redis 미도입 — PostgreSQL을 큐로\*\*

&#x20;   

&#x20;   컴포넌트가 하나 줄고 W4 파이프라인 구축 부담도 줄어듭니다. 다만 재시도·백오프·데드레터를 직접 짜야 하고, 그게 W5\~W6에 시간을 먹습니다.

&#x20;   

&#x20;   \*\*"그럼 Postgres로 하면 되잖아요"가 다시 나오면\*\* — 이게 정당한 반박이라는 걸 인정하고 이렇게 답하시면 됩니다: \*"기술적으로 가능합니다. 다만 저희가 직접 짜야 할 재시도/타임아웃 로직을 라이브러리로 대체하는 게 10주 일정에서 낫다고 판단했습니다. Redis를 캐시나 세션 저장소로 쓰려는 건 아니고, 그건 다 Postgres에 둡니다."\*

&#x20;   

&#x20;   \*\*반대로 절대 하지 말아야 할 답변\*\*은 \*"음성 통신에 필요해서요"\* 와 \*"빠르니까요"\* 입니다. 전자는 오늘 확인했듯 사실이 아니고, 후자는 UPDATE 4번짜리 워크로드라 반박당합니다.

&#x20;   

&#x20;   ---

&#x20;   

&#x20;   정리하면 — 제안하신 두 흐름은 접으시고, Redis는 \*\*워커 브로커 단일 목적\*\*으로만 도입 여부를 결정하시면 됩니다. Celery와 ARQ 중 어느 쪽이 나을지, 아니면 B안(Postgres 큐)의 실제 구현 분량이 궁금하시면 그것도 정리해 드리겠습니다.

&#x20;   

\- Celery가 아니라 ARQ로 선정한 이유

&#x20;   

&#x20;   ### 핵심 이유 3개

&#x20;   

&#x20;   \*\*① async 일관성 — 이게 제일 큽니다\*\*

&#x20;   

&#x20;   Celery는 2009년에 \*\*동기 코드 전제로\*\* 설계됐습니다. 워커가 prefork(멀티프로세스) 모델이고, `async def` 태스크를 네이티브로 지원하지 않아서 `asyncio.run()`으로 감싸야 합니다.

&#x20;   

&#x20;   문제는 그다음입니다. FastAPI · `httpx` · SQLAlchemy async를 쓰기로 한 상태에서 워커만 동기로 가면:

&#x20;   

&#x20;   - DB 엔진/세션을 \*\*async용·sync용 두 벌\*\* 만들어야 합니다

&#x20;   - HTTP 클라이언트도 `httpx.AsyncClient`와 `httpx.Client` 두 벌

&#x20;   - 같은 GitHub 호출 로직을 API에서도 워커에서도 쓰고 싶은데, 한쪽은 `await`, 한쪽은 아님 → \*\*코드 공유가 안 됩니다\*\*

&#x20;   

&#x20;   3명이 배워야 할 게 두 배가 되고, 통합 때 "이건 async 버전인가 sync 버전인가" 혼란이 생깁니다.

&#x20;   

&#x20;   \*\*② 워크로드가 I/O 바운드 100%입니다\*\*

&#x20;   

&#x20;   `analysis\_jobs`의 네 종류(`repo\_sync` / `jd\_parse` / `match\_scoring` / `profile\_summary`)가 실제로 하는 일은 \*\*GitHub API 호출과 LLM 호출 대기\*\*입니다. CPU를 쓰는 게 아니라 네트워크 응답을 기다립니다.

&#x20;   

&#x20;   이건 asyncio가 가장 잘하는 워크로드고, Celery의 prefork 모델(프로세스를 여러 개 띄워 CPU 병렬 처리)이 필요한 상황이 아닙니다. \*\*Celery의 강점이 안 쓰이고 무게만 남습니다.\*\*

&#x20;   

&#x20;   \*\*③ Windows 개발 환경\*\*

&#x20;   

&#x20;   Celery는 4.0부터 \*\*Windows 공식 지원이 끊겼습니다.\*\* 돌리려면 `--pool=solo` 같은 우회가 필요합니다. 지금 Windows 11 쓰고 계시고 팀원 중에도 있을 텐데, Docker 안에서 돌리면 되긴 하지만 \*\*로컬에서 워커만 띄워서 디버깅하기가 불편해집니다.\*\* ARQ는 순수 asyncio라 이 문제가 없습니다.

&#x20;   

&#x20;   ### 비교

&#x20;   

&#x20;   |  | Celery | ARQ |

&#x20;   | --- | --- | --- |

&#x20;   | 설계 전제 | 동기 (2009\~) | asyncio 네이티브 |

&#x20;   | FastAPI와의 궁합 | 세션·클라이언트 코드 이원화 | 그대로 재사용 |

&#x20;   | 설정 항목 | broker, backend, serializer, 라우팅, ack, beat… | `WorkerSettings` 클래스 하나 |

&#x20;   | 학습 시간(추정) | +3\~4h | +1h |

&#x20;   | Windows | 공식 지원 없음 | 문제없음 |

&#x20;   | 코드 규모 | 큼 — 막히면 소스를 못 읽음 | 작음 — 막히면 소스를 읽어서 해결 가능 |

&#x20;   | 브로커 선택지 | Redis, RabbitMQ, SQS… | Redis만 |

&#x20;   | \*\*자료·커뮤니티\*\* | \*\*압도적으로 많음 (한국어 포함)\*\* | 적음, 한국어 거의 없음 |

&#x20;   | 고급 기능 | 체인·그룹·beat 스케줄링 | 없음 |

&#x20;   

&#x20;   ### Celery가 나은 점도 있습니다 — 정직하게

&#x20;   

&#x20;   \*\*① 자료가 훨씬 많습니다.\*\* 이게 ARQ의 최대 약점이고, 3명 다 초심자라는 걸 감안하면 무시할 수 없는 리스크입니다. 다만 두 가지가 이걸 상쇄합니다 — ARQ는 코드가 작아서 막히면 소스를 직접 읽을 수 있고, 어차피 검색보다 저에게 물어보는 비중이 클 겁니다.

&#x20;   

&#x20;   \*\*② 채용 공고에 Celery가 훨씬 자주 나옵니다.\*\* 이건 유효한 논점입니다. 다만 면접에서 물어보는 건 \*"왜 비동기 처리가 필요했고 어떻게 설계했나"\*지 라이브러리 이름이 아닙니다. 오히려 \*\*"Celery도 검토했지만 I/O 바운드 워크로드고 FastAPI와 async 생태계를 맞추려고 ARQ를 골랐다"\*\*가 더 좋은 답변입니다. 지금 이 판단 과정 자체가 답변 재료입니다.

&#x20;   

&#x20;   \*\*③ 주기 실행(beat)과 태스크 체인\*\*이 필요하면 Celery입니다. 지금 계획엔 둘 다 없습니다.

&#x20;   

&#x20;   ### 번복 조건

&#x20;   

&#x20;   아래가 생기면 그때 Celery로 옮기세요.

&#x20;   

&#x20;   - CPU 바운드 작업이 생길 때

&#x20;   - \*\*주기 스케줄링\*\*이 필요해질 때 (예: 레포를 매일 자동 재분석)

&#x20;   - \*\*태스크 체인/그룹\*\*이 필요해질 때 (Job A 끝나면 B·C를 병렬로, 둘 다 끝나면 D)

&#x20;   

&#x20;   ### 이 결정을 싸게 만드는 법

&#x20;   

&#x20;   \*\*워커 로직을 큐 라이브러리와 분리해서 짜세요.\*\*

&#x20;   

&#x20;   ```

&#x20;   # ❌ ARQ에 묶임

&#x20;   async def repo\_sync\_task(ctx, job\_id): ...전부 여기에...

&#x20;   

&#x20;   # ✅ 순수 함수 + 얇은 어댑터

&#x20;   async def run\_repo\_sync(job\_id: UUID) -> None:   # 도메인 로직, 라이브러리 무관

&#x20;       ...

&#x20;   

&#x20;   async def repo\_sync\_task(ctx, job\_id):           # ARQ 어댑터, 세 줄

&#x20;       await run\_repo\_sync(UUID(job\_id))

&#x20;   ```

&#x20;   

&#x20;   이러면 나중에 Celery로 갈아타도 \*\*어댑터 몇 줄만\*\* 바뀌고 도메인 로직은 그대로입니다. 이 구조로 짜두면 "잘못 골랐으면 어쩌지" 부담이 사실상 사라집니다.

&#x20;   

&#x20;   ---

&#x20;   

&#x20;   정리하면 — \*\*되돌릴 수 있는 결정이고, 지금 상황(I/O 바운드 · FastAPI async · Windows · 학습 시간 부족)에선 ARQ가 낫습니다.\*\* 다만 "자료가 적다"는 실제 리스크라, 팀에서 그게 더 무겁다고 판단하면 Celery도 틀린 선택은 아닙니다. 내일 회의에서 이 표를 그대로 쓰셔도 됩니다.

&#x20;   



레포 분석 → 면접관이 질문생성 → (DB에 저장 동시에) tts → 취준생이 듣고 답변 → stt → (DB에 저장 동시에) agent에게 넘어가서 → 다음 질문 생성 → tts → 취준생이 듣고 답변 → …

\#### 🆕 비동기 작업 모델 — 이번에 추가된 것



Redis 문법이 아니라 \*\*"프로세스가 둘로 나뉜다"\*\*는 개념입니다. 이걸 모르면 W5부터 코드 구조가 안 읽힙니다.



개념 4개만 잡으세요.



1\. \*\*진입점이 둘입니다.\*\* API 서버(`main.py`)와 워커(`worker.py`)가 \*\*다른 프로세스\*\*로 돕니다. 같은 코드베이스, 같은 DB를 보지만 서로 함수 호출을 못 합니다. `docker compose`에 컨테이너가 2개 뜹니다

2\. \*\*Job에는 객체를 못 넘깁니다.\*\* 인자가 직렬화(JSON)돼서 Redis를 거치므로, ORM 객체나 DB 세션을 통째로 넘길 수 없습니다. → \*\*`job\_id`(UUID)만 넘기고 워커가 DB에서 다시 읽는\*\* 패턴이 표준입니다. 생성 코드가 왜 그렇게 생겼는지 여기서 이해됩니다

3\. \*\*Job은 두 번 실행될 수 있습니다.\*\* 재시도가 걸리면 그렇습니다. "같은 Job이 두 번 돌아도 데이터가 망가지지 않는가"(멱등성)를 항상 확인해야 합니다

4\. \*\*`analysis\_jobs` 테이블이 유일한 진실입니다.\*\* Redis는 "누가 이 일을 집어갈지" 대기열일 뿐, 상태(`status`/`steps`/`progress`)는 전부 PostgreSQL에 씁니다



\*\*Redis 본체는 이 정도만\*\* — `SET`/`GET`/`EXPIRE`/`TTL`이 뭔지, `redis-cli`로 큐 안을 들여다보는 법(디버깅용). 30분.
