# 0014 기존 설계를 유지하는 최소 변경 재결정

- 상태: Partially Superseded — 최소 변경 기준은 유지하며 공고 TTL·역할별 배분은 후속 공통 0002로 대체
- 날짜: 2026-09-21
- 결정자: 현재 사용자
- 관련 PR: 없음
- 결정 근거: “지금까지 정한 의사결정 사항들을 기존 그대로 두고 유지되도록 변경되어도 최소한으로 변경되도록 다시 정해.”
- 추가 확인: 2026-09-21, 중간 조회 요약을 기존 판단 근거에 짧게 포함하고 기존 판단 저장 시점에 함께 저장하는 최소 변경 방식을 사용자의 “그럼 이건 이렇게 정해.” 지시로 확정했다.
- 적용 범위 확인: 2026-09-22, “남은 의사결정 사항들도 이렇게 기존을 그대로 유지하고 최소한으로 변경되도록 정하자.” 지시에 따라 아래 기준을 남은 결정에도 적용한다. 개별 미정 사항의 선택까지 자동 승인한 것은 아니다.
- 진행 방식 추가 지시: 2026-09-22, “기존안으로 해서 정할 수 있는 건 그대로 하고 질문이 필요한 것들만 질문해.”에 따라 기존안으로 요구사항을 충족한다고 확인한 부분은 재질문 없이 채택·기록한다. 기존안이 없거나 충돌·실질적인 선택 차이가 있는 사항만 묶어 질문한다.

후속 결정(2026-09-22): [공통 0002](../../shared/decisions/0002-local-policy-baseline.md)에 따라 아래 24시간 TTL과 HR·domain 개별 배분 비고정 부분은 각각 7일과 정상 9턴의 기술/도메인/HR 6/2/1로 대체됐다. 해당 본문은 당시 이력으로 남기며, 변경 자료의 새 ID·기존 참조 보존 등 나머지 결정은 유지한다.

## 목적과 기준

기존 설계로 요구사항을 충족하면 필드·이름·값·저장 순서·처리 책임을 유지한다. 보기 좋은 통일, 상세한 추적이나 장래 확장만을 이유로 DB 저장 형식과 생산자·소비자 코드를 바꾸지 않는다. 테이블·컬럼뿐 아니라 JSON 내용, 검증·읽기·쓰기, 추가 저장 횟수와 복구 의무까지 변경 비용에 포함한다.

남은 결정은 관련 내용을 기능 단위로 묶어 검토한다. 기존안으로 충족되는 필드·값·처리 책임과 그 안에서 정할 수 있는 통상적인 세부 사항은 근거를 확인해 그대로 채택하고 결과를 기록한다. 기존안과 충돌하거나 실제 동작·비용·저장·복구에 실질적인 선택이 필요한 경우에만 목적·추천 이유·변경 영향을 제시해 질문한다. 단순 필드 명명과 반복적인 형식 선택은 별도 질문으로 늘리지 않는다. 실측·자료 검수·계정 확인이 필요한 항목은 설계 선택만으로 완료 처리하지 않는다.

비교 기준은 0011~0013 반영 전 저장소의 기존 계약·기능 명세와 0001~0010의 유효한 정책이다. 실제 계약·ORM·Turn service는 미구현이므로 기존 설계와 이미 동작하는 코드를 혼동하지 않는다. 기존에 미정이던 내용은 기존 구조에 맞춰 필요한 범위만 확정한다. 모든 미정을 새 구조로 채우거나 새 구조 때문에 생긴 세부 질문을 계속 늘리지 않는다.

## 질문 기준과 당시 자료

Question Contract는 기존 `purpose`, `required_points`, `assumptions`, `basis_refs`, `evaluation_scope`를 유지한다. 확인내용의 고유 key·설명, 질문 범위를 넘지 않는 평가, 빈 가정·근거 목록의 의미, 실제 자료 ID·권한·ref 검증은 그대로 필요하다. 채택한 저장 형식은 [내부 계약](../contracts.md#question-contract-저장-형식)에 둔다. 호출의 schema/version metadata 기록 책임은 기존 Gateway에 남기며 JSON마다 같은 버전 필드를 중복 요구하지 않는다.

공고는 normalized Wanted URL과 24시간 TTL로 재사용한다. 동일 내용은 기존 ID를 쓰고 변경 내용은 기존 `job_postings`·`jd_requirements`의 새 행으로 저장하여 확정 run·질문의 참조를 유지한다. 같은 ID의 내용을 덮어쓰면서 당시 자료를 연결만으로 보존할 수는 없으므로 이 보완은 남긴다. 별도 공고 이력 테이블·질문별 본문 복사본은 추가하지 않는다.

이 결정은 DB 영향이 전혀 없다는 뜻이 아니다. 미정이던 저장 컬럼을 정하고 변경 자료를 새 행에 남기는 동작은 실제 구현 시 필요하다. 내용 비교·동시 수집·저장 제약과 보존기간은 기존 AI-L02·AI-L03·AI-L12·AI-L18 범위에서 함께 정한다.

## 기존 평가와 판단 구조

AnswerAnalysis는 기존 `evaluation_status`, `sufficiency`, `covered_points`, `missing_points`, `technical_assessment`, `contribution_scope`, `claim_checks`, `needs_verification`, `verification_requests`, `limitations`를 유지한다. 종합 평가상태는 기존 evaluated·needs_clarification·not_evaluable를 쓰되 세 축을 하나의 점수로 합치지 않는다. 판단 가능한 내용과 보류한 범위·이유를 각각 기존 필드에 남긴다. 별도 평가 객체나 부분 평가 상태는 만들지 않는다.

충분성은 기존 sufficient·partial·insufficient를 유지하고 충분성 자체가 판단 불가이거나 평가 범위 밖일 때 null로 둔다. 모르는 내용을 부족으로 단정하지 않으며 이미 확인한 충족·부족 부분은 보존한다. 전체 판정이 null이거나 다른 축에 한계가 있어도 확인 가능한 내용을 삭제하지 않는다.

DirectorDecision은 기존 next_step·intent·persona·target·tool_requests·reason_summary를 유지한다. ask/retrieve/finish를 사용하고, retrieve는 질문 Turn을 늘리지 않는다. 실제 질문/정상 종료 실행은 검증된 ask 또는 Controller가 허용한 finish로만 한다. intent는 보완·심화·전환·확인의 중심 목적 하나를 기록하되 새 영문 코드 enum을 강제하지 않는다. 목적을 둘 이상 수행할 수 있다는 이유로 배열·별도 우선순위 규칙을 추가하지 않는다.

## 저장과 실패 경계

기존 Turn service 설계의 T1 질문, T2 답변, T3 분석, T4 판단·Context 갱신 순서를 따른다. 분석·판단을 별도 JSONB에 직접 저장하며 유효한 결과가 없으면 해당 컬럼은 SQL NULL이다. 이를 네 실행 상태로 해석하지 않는다. 기존 답변 원문·최초 분석·유효한 Evidence는 이후 실패나 보완으로 덮어쓰지 않는다.

조회 요약은 실제 조회 여부·범위·결과·한계를 기존 ToolResult 의미에 맞춰 짧게 정리하고 성공한 판단의 reason_summary에 포함하여 기존 T4 판단 저장 시점에 함께 저장한다. 기존 조회 결과 전달·작성 지침·검증을 필요한 범위에서 보완하며, 이 요약을 위한 새 저장 필드나 별도 모델 호출은 추가하지 않는다. 확인 근거는 기존 Evidence 관계를 쓴다. 미조회·미발견·자료 부족·도구 오류를 구분하며 제안만 한 조회를 실제 결과로 기록하지 않는다. 별도 조회 요약 DTO나 도구 결과 사본을 만들지 않는다.

감지된 실패·중단에서는 0003의 조회 기록 보존 의무를 기존 실패 기록 책임 안에서 충족해야 한다. 실패 기록의 정확한 영구 저장 위치·형식은 아직 구현·확정되지 않았으며 AI-L02·AI-L18에서 함께 정한다. 이를 일반 로그나 성공 decision으로 대체하거나 새 events 종류를 추가하지 않는다. 이 저장 경계가 정해지기 전에는 조회 보존을 포함한 연결 구현 완료를 선언하지 않는다.

조회마다 DB에 쓰는 요구는 없앤다. 외부 호출 뒤 기존 단계의 성공 확정 또는 감지된 실패 정리 시점에 저장한다. 이에 따라 프로세스 강제 종료·DB 쓰기 실패 직전의 모든 중간 조회까지 보존하는 보장은 하지 않는다. 동시성·중복 방지·저장 실패·중단 복구는 원래 AI-L12 범위이며, 이전 확장 구조만을 위한 실행 일련번호·상태 정리 설계는 요구하지 않는다.

## 영향과 확인 기준

2026-09-22 기존안 추가 점검: [0010](0010-sprint1-interface-runtime-decisions.md)의 Sprint 1 상세 limitations 비공개와 [BE Turn 정책](../../backend/features/interview.md#turn-정책)의 HR·domain 개별 배분 비고정을 그대로 유지한다. 이 항목을 미정으로 다시 묻지 않는다. 변환·L1 요약의 상세 저장 매핑과 명시적 종료 wire는 기존 의미·사용자 동작 안에서 구현 시 구체화하며, 새 컬럼·공개 의미·복구 동작이 실제로 필요한 경우에만 그 차이를 검토한다. 구현·연동 완료를 뜻하지 않는다.

진행 중 질문 생성 실패도 기존 오류 안내·기록 보존·명시적 나가기 흐름을 유지하며 요청되지 않은 새 수동 이어가기를 추가하지 않는다. 오류·연결 종료만으로 DB 종료 상태를 확정하거나 재연결로 실패한 LLM 호출을 자동 반복하지 않는다. 실제 오류·종료·실패 보존 연결은 기존 구현 검토에 남기고, 0010의 재시도 소유권·상한·semantic 실패 재호출 금지를 유지한다.

- 기존 서비스 구성·레이어·API/WS·9턴·Persona·공개 점수·Worker/queue·재시도 정책은 유지한다. 새 서비스·테이블·상태 API·추가 모델 호출은 만들지 않는다.
- 현행 계약·기능 명세·DB 안내·작업 가이드·검증 조건과 [결정 상태·후속 작업 안내](README.md#결정-상태와-후속-작업)를 함께 맞춘다. 형식 전체를 여러 문서에 반복하지 않고 내부 계약으로 연결한다.
- 기존 0003 조회 보존과 0004 최초 분석·축별 한계 보존을 약화하지 않는지 확인한다. 질문에 없는 기준·조회 실패·미확인을 사용자 감점으로 바꾸지 않는다.
- 질문 기준의 다섯 필드, 분석·판단의 기존 필드·값과 저장 순서, 미채택 상세 객체·실패 저장 경계의 구분을 검토한다.
- 이번 변경은 문서 재결정이다. DB migration·runtime 코드·실제 모델 호출·운영 데이터 변경은 수행하지 않는다. 문서·참조 검사는 구현 테스트를 대신하지 않는다.

## 대체 관계와 남은 범위

0011 모델 선택은 유지한다. 0012의 질문 동시 저장·다섯 내용 항목·근거 연결·자료 보존은 유지하되 버전 필드와 부가 필드 일괄 거부 정책을 이 결정으로 대체한다. 0013은 두 JSONB 위치와 기존 의미·보존 목적만 유지하고 위 표의 추가 구조·조회별 저장 요구를 대체한다. 과거 결정 원문은 삭제하지 않으며 충돌 시 현재 결정인 0014와 갱신한 내부 계약을 따른다.

AI-L02에는 Context·Question 전체·Evidence/ToolResult·feedback, 기존 분석 필드의 상세 객체·참조·null과 Director의 행동별 상세 형식·공개 변환이 남는다. 복구·영구 실패 기록·자료 운영처럼 원래 미정이던 내용도 해당 항목에 남긴다. 철회한 공통 객체·상태·조회 사본을 다시 설계할 의무는 없다.
