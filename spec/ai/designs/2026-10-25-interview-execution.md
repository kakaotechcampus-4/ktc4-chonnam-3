# 면접 준비·답변·전송의 실행 경계

- 상태: Proposed — 실행 연결의 설계 검토 대상이며 구현·검증 완료를 뜻하지 않는다.
- 날짜: 2026-10-25
- 선행 입력 설계: [Director 질문 결정과 AI·BE 입력 계약 PR #124](https://github.com/kakaotechcampus-4/ktc4-chonnam-3/pull/124)
- 정책 참조: [고정 배분 PR #97](https://github.com/kakaotechcampus-4/ktc4-chonnam-3/pull/97), [세션 인증 0003](../../shared/decisions/0003-sprint1-session-auth.md)
- 공개 계약 원본: [공통 계약 안내](../../shared/contracts/README.md), [WS #18](../../../frontend/docs/api-spec.md)

## 범위와 책임

이 문서는 #124가 별도 연결로 남긴 준비·턴 저장·상태 전이·worker·WS의 실행 경계를 정의한다.
목적·Question Contract 생성, 독립 검토와 입력 구조는 #124를 참조하며 다시 정의하지 않는다.
기존 REST·WS 필드, flat `analysis`/`decision`, 첫 HR·기술 6/도메인 2/HR 1 정책을 유지한다.
선행 정책·구현의 develop 병합 여부와 이 설계의 검토 상태는 별개다.

Controller는 권한·상태·현재 턴·고정 입력·예산과 DB 확정을 책임진다.
AI 결과는 저장 전에 다시 검증하며 모델이 상태 전이나 정상 종료를 자율 확정하지 않는다.
PostgreSQL은 원문·질문·답변·분석·호출 기록의 원본이고 Redis는 연결 소유권·작업 인계·snapshot을 맡는다.
외부 모델·GitHub 호출 동안 DB transaction을 유지하지 않고, 호출 후 입력과 상태를 재확인한다.

## 준비 실행

1. 본인 소유의 `preparing` 면접에 준비 claim을 기록해 같은 작업의 중복 실행을 막는다.
   현재 claim 소유자만 결과를 확정하며, 오래된 실행 결과가 이후 준비 상태를 덮어쓰지 못하게 한다.
2. 분석 run과 선택 레포에 연결된 성공 L1을 읽고 분석 당시 SHA를 고정한다.
   현재 default branch HEAD로 대체하지 않는다. 선택 순서의 앞 최대 2개를 primary로 쓰는 것은
   이 실행 설계의 Proposed 구현 선택이며, 별도의 레포 우선순위 정책을 확정하는 근거는 아니다.
3. 필요한 활성 prompt·도메인 프레임·평가 기준을 확인한다. 자료 부재를 일반 질문이나
   임의 기준으로 채우지 않으며, 비활성 seed를 실행 과정에서 자동 활성화하지 않는다.
4. 같은 레포·SHA·prompt의 유효 L2를 재사용하되 질문 근거에 필요한 실제 원문을 다시 확보한다.
   새 L2가 필요하면 #124의 실제 tree 기반 선정·유한 수집 경계를 따르고 미확인 범위를 전달한다.
5. 검증한 원문·레포·SHA·위치를 Evidence에 저장한다. AI 요약을 읽은 원문으로 대체하지 않는다.
   준비 중 확보한 근거와 답변 후 Tool로 조회한 근거의 출처를 구분한다.
6. 첫 HR 질문의 생성·검토·저장이 끝난 뒤에만 `in_progress`로 전이한다.
   확정 직전에 claim·권한·상태·선택 레포·SHA·준비 입력이 여전히 일치하는지 확인한다.

준비 실패는 `preparing_failed`로 기록하고 기존 `prepareSteps`·`lastError` 계약으로 복구할 수 있어야 한다.
이 설계는 실패 단계부터 재개해야 한다는 기존 요구를 전체 단계 재실행으로 바꾸지 않는다.

## 답변 확정과 다음 턴

1. 현재 면접과 답변 대상 턴을 확인하고 잠근다. 현재 `asked` 질문의 답변만 한 번 확정한다.
   오래된 턴·중복 답변은 원문을 덮어쓰거나 모델 작업을 새로 시작하는 근거가 되지 않는다.
2. 답변 원문·답변 시각과 해당 분석 실행의 claim을 commit한 뒤 `answerReceived`, `thinking`을 보낸다.
   ACK 전송 실패는 이미 저장한 답변을 취소하지 않으며, 소켓 교체가 수락한 분석을 재실행시키지 않는다.
3. 현재 질문·계약은 과거 문답과 분리해 T3에 전달한다. 질문하지 않은 항목을 누락으로 평가하지 않는다.
   최초 분석 원형과 실제 호출 metadata를 보존하고 성공한 결과만 다음 단계에 사용한다.
4. 검증한 분석에 조회 필요가 있고 허용 레포·SHA·위치가 확인될 때 제한 Tool 조회를 수행한다.
   유효한 근거를 commit한 뒤에만 `evidenceCheck`를 보낸다. 부분 성공의 원문과 실패 한계를 함께 보존한다.
5. 보강 T3가 성공하면 당시 입력과 근거에 다시 대조한 결과를 후속 판단에 사용한다.
   최초 답변·분석을 덮어쓰지 않는다. 조회 장애 자체를 거짓 답변·감점의 증거로 삼지 않는다.
6. 1~8번째 답변 분석 후 다음 질문을 생성·검토·저장하고 확정한 `question`만 전송한다.
   저장 직전에 권한·상태·현재 턴·원문 Context를 재검사해 종료 후 결과나 stale 결과를 차단한다.
7. 9번째 답변의 필요한 분석이 성공한 뒤에만 `completed`와 완료 시각을 확정하고 `interviewEnd`를 보낸다.
   10번째 질문·Context를 만들지 않는다. 남은 시간 표시가 0이 된 것을 정상 완료의 대체 조건으로 삼지 않는다.

## 예산과 실패 확정

#124의 논리 작업별 예산을 서비스 호출 전 구분하고 하위 호출까지 같은 객체로 전달한다.

| 작업 | 공유 범위 | 소진·실패 시 실행 경계 |
| --- | --- | --- |
| L2 | 파일 선정과 분석이 같은 총 2회 예산을 사용 | 검증한 분석 없이 준비 성공으로 확정하지 않는다 |
| T3 | 최초 분석과 보강 분석이 같은 총 2회 예산을 사용 | 필요한 분석 실패 후 다음 질문·정상 완료를 실행하지 않는다 |
| T4 | 질문 생성과 독립 검토가 별도 총 2회 예산을 사용 | 거절·소진 후 무검토 질문이나 추가 생성을 실행하지 않는다 |

전송 재시도·재연결·worker 재전달은 위 예산을 초기화해 같은 모델 작업을 재시작하는 사유가 아니다.
오류·취소·입력 변경을 정상 결과와 구분해 저장하고, 확정하지 못한 결과를 질문 횟수에 더하지 않는다.
실패한 호출의 원문·metadata와 이미 검증한 부분 근거는 보존한다. 공개 로그로 원문 보존을 대신하지 않는다.
`question_failed`의 `recoverable: true`는 진행 중 면접의 수동 이어가기나 모델 재호출 권한이 아니다.

## WS 인증·인계·복구

로그인 쿠키·Origin은 handshake에서 한 번 검증하며, 면접 `sessionId`의 사용자 소유권을 별도로 확인한다.
열린 연결에서 로그인 세션 만료만으로 끊거나 답변마다 로그인 재인증하지 않는다. 재접속은 다시 인증한다.
답변 수용·전송·snapshot 갱신 시에는 면접 실시간 매핑·연결 소유권·DB 권한과 상태를 계속 확인한다.

중복 연결은 기존 소켓을 실제 종료한 뒤 신규 연결을 허용한다. Redis Pub/Sub로 현재 nonce 소유자에게
교체를 알리고, 소유권이 같은 잠금만 해제한 뒤 신규 연결이 NX로 획득하는 방식을 제안한다.
알림 유실은 유한 획득 대기 안에서 재발행하며 이전 연결의 정리가 신규 잠금을 지우지 못하게 한다.

이미 수락한 답변의 T3→Tool→T4 수명과 소켓 수명을 분리한다. 전체 작업을 감싼 유한 인계 표식이
있는 동안 새 연결은 완료된 DB 결과를 기다린다. 동일 답변 분석을 다시 호출하지 않는다.
Redis snapshot이 없으면 DB에서 재구성하고 저장된 현재 `asked` 질문을 재전송한다.
이미 답변된 턴의 실패·미완료 분석은 재접속만으로 다시 실행하지 않는다.
종료된 면접의 신규 handshake는 거절하고, 완료 이벤트 유실은 기존 GET의 상태 조회로 확인한다.
연결 종료·로그인 만료만으로 `completed`나 `abandoned`를 기록하지 않는다.

## 기존 요구를 대체하지 않는 한계

- 준비 화면의 `prepareStep`·`prepareCompleted` 전달과 preparing 상태의 WS 연결 유지 요구는 남는다.
  질문 복구 경계만으로 준비부터 진행까지 전체 연결이 충족됐다고 보지 않는다.
- 정확히 실패한 준비 단계부터 재개하고 성공 단계의 유효 결과를 보존하는 조건은 별도 검증 대상이다.
- 명시적 나가기·레포 재선택의 abandoned 정책을 유지한다. 종료 통지 wire와 처리 연결은
  [공통 계약의 보류 항목](../../shared/contracts/migration.md)을 따르며 이 문서에서 새 메시지를 만들지 않는다.
- 유한 인계 표식은 일반 실행 lease·reaper나 프로세스 강제 종료 후 복구를 대신하지 않는다.
  DB 정지를 포함한 전체 작업 deadline을 보장하지 않으며, 실행 중단 확인 없는 자동 재실행을 허용하지 않는다.
- 여러 탭의 자동 재접속이 서로 연결을 교체하는 문제를 해소한 것으로 간주하지 않는다.
- Report 생성·음성·평가 품질 검증은 별도 범위다. 이 설계는 공개 오류 필드나 복구 API를 추가하지 않는다.

실제 적용 범위·선행 의존성·검증 결과는 관련 구현 PR과 단일 구현 기록에서 관리한다.
