# 0049. 통합 PR 리뷰의 최신 기반·실행 복구·배포 일치

- 상태: Accepted for local implementation and publication scope
- 결정일: 2026-11-10
- 관련 PR: #233, 병합된 #185·#234·#235
- 대체 관계: [0047](0047-integrated-publication-without-voice-input.md)의 음성 기반 미병합 제외 조건을 현재 게시 범위에서 부분 대체한다. 원래 결정과 당시 검증 기록은 보존한다.

## 맥락

#233의 기준 이후 음성 입력·STT와 FE 오류 처리가 develop에 병합되었다.
기존 17개 PR을 보존하며 같은 #233 번호로 최신 기반에 맞춰 리뷰 지적을 해결한다.
단독 PR의 과거 검증과 최신 develop 통합 검증은 별도로 기록한다.

## 결정

1. 최신 develop의 음성 기본값·STT 설정·오류 분류·질문 위치를 보존한다.
   #234의 STT 복구 불가 안내와 명시적 abandon, 오디오 초과의 같은 턴 재답변 및 #235의 AI 안내도 유지한다.
   소켓을 유지하는 기존 `stt_unavailable` 동작을 임의의 연결 종료 정책으로 바꾸지 않는다.
   저장 모드와 반대인 입력은 STT·모델 호출·저장 전에 기존 오류로 거절한다.
2. 실제 병합된 선행 구현에 자체 대기 보완을 연결하고, 적용이 끝난 패치는 게시본에서 제거한다.
   새 공개 계약과 기존 계약 준수 수정을 구분하며 실제 실행 스키마·FE·공통 명세를 일치시킨다.
   질문 복구 결정은 공통 STT 0011과 구분해 [공통 0012](../../shared/decisions/0012-bounded-question-recovery.md)로 참조한다.
3. 이미 적용된 migration은 재작성하지 않는다. 0015는 실제 0006과 0014를 합류한다.
   0016은 기존 세 CHECK의 이름만 정렬하며 식·행·제약 OID를 유지한다.
   0017은 전달 중인 검증된 프로필 결과, 0018은 문서 예약 작성자의 절대 만료 시각을 보존한다.
   보호 대상인 생성 결과·진행 중 예약이 있으면 해당 컬럼의 downgrade를 거절한다.
4. 프로필 작업의 실행 상한은 600초, running 전달 lease는 630초로 공통 관리한다.
   면접 준비의 1800초 상수를 프로필 복구 대기에 사용하지 않는다. 전달은 기존 5회·24시간 상한을 따른다.
5. 프로필의 모델 입력·근거 면접·프롬프트·모델·생성 설정이 같으면 재평가 회차만 바뀌어도 성공 요약을 재사용한다.
   보고서별 revision 전달 기록은 outbox에 남기며 모델 입력 지문과 구분한다.
6. 영속 프로필 전달에서 생성한 검증된 짧은 역할 요약은 원래 입력 지문·모델·프롬프트 버전·실행 설정과 함께 보관한다.
   본문 원문·키·프롬프트를 넣지 않으며 16KiB 이하로 제한한다. 생성 뒤 Redis 장애는 종결 모델 실패와 구분해 유한 재전달한다.
   재사용은 입력 지문이 같을 때만 허용하고 공개 요약 저장 전에는 Redis·DB 소유권과 현재 입력을 다시 검사한다.
   성공·종결·만료 시 임시 결과를 지운다. 입력이 바뀌면 예전 결과를 새 요약으로 저장하지 않는다.
7. 배포는 같은 릴리스 이미지를 준비하고 구 API·worker를 중지한 뒤 migration → 실행 recipe 11종 프롬프트 등록 → API·worker 순으로 진행한다.
   소비 모듈·지원 버전·기존 같은 버전의 모델과 본문을 검사하고 등록 실패 시 새 소비자를 시작하지 않는다.
   등록은 DB 작업이며 유료 모델 호출이 아니다. health 성공은 활성 프롬프트·서비스 품질 검증을 대신하지 않는다.
8. 이미지 다운로드별 30초와 이미지·Vision 전체 360초를 분리한다. 기본 이미지 4개에 각각 다운로드 30초·Vision 60초를 배정할 수 있는 유한 상한이다.
   같은 원문의 부분 인식 재시도는 외부 처리 전에 URL별 DB 예약을 확정한다. HTTP 중 DB 잠금은 유지하지 않는다.
   실패·취소도 시간당 최대 3회에 포함하고 첫·둘째 시도 뒤 60·120초, 셋째 뒤 해당 1시간 주기의 끝까지 기다린다.
   실행 lease와 실제 outer deadline을 연결하며, 다른 요청은 기존 성공본을 사용한다. 원문이 바뀌면 새 주기로 구분한다.
9. Report·Score v3는 입력 자료의 명령을 실행 지시로 취급하지 않는다. 특히 OCR/JD와 코드 근거를 구분한다.
   채점은 각 턴이 실제 참조한 코드·도구·문서·JD 자료만 사용하고 배포 접미사가 있는 v3도 같은 경계를 따른다.
   과거 v2는 불변으로 보존하며 현재 runtime manifest는 새 버전을 명시한다.
10. 평가 지문은 portable UTF-8 LF와 원시 바이트를 함께 기록하고 과거 무표시 지문의 raw 의미를 보존한다.
    결과 경로를 독점 예약하고 중간 상태를 영속화하며, 기술 오류는 실패 종료 코드로 반환한다. 사람 검수 상태는 별도로 표시한다.
    평가 원문·정답은 이미지에 넣지 않고 필요한 참조 구조를 읽기 전용 마운트한다.

## 영향과 한계

- 기존 17개 PR과 원격 #233 원본 HEAD를 보존한다. 번호 유지 재게시가 필요하면 확인한 원격 HEAD의 명시적 lease로 갱신한다.
  다른 사람의 변경이 있으면 덮어쓰지 않는다. 신규 커밋의 추가·삭제 합계는 각각 300줄 이하로 유지한다.
- 임시 생성 결과는 이미 성공 응답을 받아 검증·DB 보존한 작업의 재과금을 줄인다.
  공급자 응답 전 연결 유실이나 DB까지 사용할 수 없는 장애에서 과금된 결과를 복구했다고 주장하지 않는다.
  영속 전달 ID가 없는 이전 user-only job은 기존 실패 분리를 유지하며 이 임시 결과 복구 범위와 구분한다.
- 출력 검증·모델 semantic 실패는 영구 실패로 남기며 인프라 복구가 모델 실패의 우회 재시도 경로가 되지 않게 한다.
- 초기 설계·과거 ADR은 당시 기준으로 보존한다. 실제 실행 결과는 [AI 구현 기록](../implementation.md)과 PR에 통과·실패·미실행으로 구분한다.

## 검증 기준

- 실제 PostgreSQL에서 선행 두 분기의 합류·왕복, CHECK 이름과 정의·OID 보존, 새 복구 컬럼과 downgrade 보호를 확인한다.
- 같은 입력의 revision 재사용, 입력 변경 시 캐시 거절, 생성 직후 Redis 장애의 모델 1회·재전달 성공, 오래된 소유자의 저장 거절을 확인한다.
- 배포 순서는 실제 스크립트의 명령 대역으로 검사하며 migration·프롬프트 등록 실패 뒤 소비자가 시작하지 않는지 확인한다.
- 최신 FE·BE 계약과 자동 테스트, 원격 base·Draft·HEAD·파일·커밋별 줄 수 및 원본 PR 보존을 다시 확인한다.
  이 검증을 실제 공급자 호출이나 사람의 품질 검수로 확대 보고하지 않는다.
