# 0002 로컬 기준의 업로드 용량·공고 재사용·면접 배분 채택

- 상태: Partially Superseded — 면접 배분은 0004로 대체, 업로드 용량·공고 재사용은 유지
- 날짜: 2026-09-22
- 결정자·검토자: 현재 사용자
- 관련 PR: #40 설정 구현과 대조함. 이 결정으로 원격 PR을 수정하거나 병합하지 않음.
- 결정 근거: 세 항목의 문서·로컬 차이를 확인한 뒤 사용자가 “이 사항은 현재 로컬 상태를 따르게 정하자.”라고 지시함.

후속 결정: [0004](0004-flexible-persona-allocation-restoration.md)에서 면접 배분만 기술 목표 6턴·최소 5턴, 도메인·HR 합산 최소 3턴과 개별 배분 비고정으로 복원했다. 아래 6/2/1 설명은 당시 결정 이력이며 포트폴리오 20MB·공고 재사용 7일은 계속 유효하다.

## 맥락과 이유

기존 문서는 포트폴리오 10MB, 공고 재사용 24시간, 기술 질문 목표 6·최소 5턴과 HR·도메인 합산 최소 3턴을 요구했다. 로컬 화면과 설정 예시에는 포트폴리오 20MB, 공고 7일, 역할별 6/2/1이 남아 있었다. 사용자는 이번 세 항목에 한해 로컬 값을 기준으로 삼아 변경을 최소화하기로 했다.

## 결정

| 항목 | 채택 기준 | 반영 전 확인한 로컬 상태 |
| --- | --- | --- |
| 포트폴리오 용량 | 최대 20MB = 20 × 1024 × 1024 bytes. 상한과 같은 크기는 허용하고 초과하면 거절 | 화면 검사와 BE 설정 예시는 20MB. 개발용 모의 서버는 10MB여서 20MB로 맞춤 |
| 공고 재사용 | 기존 `fetched_at` 기준 7일. `JD_REUSE_TTL_DAYS=7` 유지 | 설정 예시·수집 모듈 설명에 7일. 로컬의 실제 재사용 판단 로직은 미구현 |
| 면접 역할별 횟수 | 정상 완료 9턴에서 `tech_lead:6`, `domain_lead:2`, `hr_manager:1` | `PERSONA_TURN_QUOTA` 설정 예시는 6/2/1. 로컬의 실제 횟수 제한 로직은 미구현 |

첫 질문은 기존대로 HR이며 위 1턴에 포함한다. 2턴부터 Director가 각 역할의 남은 횟수 안에서 선택한다. 별도의 고정 질문 순서는 추가하지 않는다. 사용자 종료·실패로 중단된 면접에 정상 완료 횟수를 강제하지 않는다.

공고는 기존 normalized Wanted URL·성공본 재사용 조건을 유지한다. 재조회한 내용이 같으면 기존 ID를 쓰고, 바뀌면 새 공고·요구사항 ID를 부여하여 이전 run·질문의 참조를 보존한다. 이번 결정은 과거 수집 주석의 요구사항 삭제 후 재삽입 방식을 채택하지 않는다.

지원 파일 형식, 자기소개서 설정 예시의 10MB, 9턴 종료, 첫 질문 HR, API 필드·DB 구조·모델·저장 정책은 이번 세 값 변경의 대상이 아니다.

## 영향과 검증

- FE·BE·AI의 관련 명세, OpenAPI의 파일 크기 설명, 구현 안내와 검증 기준을 위 값에 맞춘다.
- 포트폴리오 화면의 기존 20MB 검사는 유지한다. 개발용 모의 서버의 상한과 오류 안내만 20MB로 맞추고 경계값을 검증한다.
- BE 설정 예시의 값은 유지한다. 공고 재사용·역할 배분·실제 BE 업로드 검사는 기존 구현 작업에서 연결·검증한다. 문서 확정을 구현 완료로 표시하지 않는다.
- DB migration이나 API 요청·응답 구조 변경은 없다. 실제 배포·모델 호출·원격 PR 수정은 수행하지 않는다.

## 대체 관계

[AI 0014](../../ai/decisions/0014-minimal-change-revision.md)의 24시간 TTL과 HR·도메인 개별 배분 비고정 부분, 그리고 관련 문서의 포트폴리오 10MB 기준만 이 결정으로 대체한다. [AI 0012](../../ai/decisions/0012-question-contract.md)의 당시 24시간 표기도 현행 기준이 아니다. 이전 결정 원문은 이력으로 남기고 나머지 승인 내용은 유지한다.
