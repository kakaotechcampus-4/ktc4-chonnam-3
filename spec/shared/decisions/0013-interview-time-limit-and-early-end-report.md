# 0013 면접 제한 시간 — 질문 생성 중 정지와 시간 종료 면접의 완료·리포트

## 맥락

면접 잔여 시간(`remainingSeconds`)은 `총 시간 - (지금 - started_at)`으로 계산되어, 답변 분석과 다음 질문 생성(`thinking`)을 기다리는 동안에도 줄었다. 사용자는 기다리기만 했는데 답변 시간이 줄어든다. 또 잔여 시간이 0이 되어도 면접을 끝내는 곳이 없어, 0:00 이후에도 답변이 이어지고 9번째 답변에서만 `completed`가 되었다.

관련해 현재 문서에는 서로 어긋난 부분이 있다.

- FE spec 타이머 절은 `planned_duration_sec - elapsed_sec`라고 쓰지만 `elapsed_sec` 컬럼은 없고 구현은 벽시계 계산이다.
- 공통 0009는 abandon된 면접의 부분 리포트를 범위 밖으로 두었다. 시간 종료로 끝난 면접(`completed`)의 부분 리포트는 정해진 바가 없다.
- 리포트 생성 조건은 "`completed`이고 답변 완료 턴이 1개 이상"이지만, 실제로 `completed`가 되는 길은 9턴 완료뿐이라 부분 진행은 한 번도 리포트 대상이 되지 않았다.

## 결정

### 1. 잔여 시간에서 질문 생성 대기를 뺀다

`remainingSeconds = 총 시간 - (경과 - 질문 생성 대기)`.

| 항목 | 값 |
| --- | --- |
| 정지 구간 | 답변 저장 시각(`answered_at`)부터 다음 질문 저장 시각(다음 턴 `asked_at`)까지 (`thinking` 전체: 답변 분석 + 다음 질문 생성) |
| 다음 질문이 아직 없는 구간 | 종료 시각(`completed_at`/`abandoned_at`), 진행 중이면 지금까지 |
| 중단·완료된 면접 | 열린 구간을 종료 시각에서 잘라 조회마다 값이 변하지 않는다 |
| 질문 음성(TTS) 재생 | 정지하지 않는다. 면접관의 발화 시간도 면접 시간에 포함된다 |
| 첫 질문 생성 | 이미 제외된다. `started_at`이 첫 질문 저장 뒤에 찍힌다 |

### 2. 제한 시간이 다 되면 서버가 면접을 `completed`로 끝낸다

- 조건: 면접이 `in_progress`이고, 마지막 턴이 `asked`(답변 대기 중)이며, 잔여 시간이 0 이하.
- 판정 시점: `GET /interviews/{id}`, WS 연결, WS 답변 수신. 새 엔드포인트는 만들지 않는다. 화면을 닫고 떠난 면접의 자동 종료는 하지 않는다(heartbeat 판정은 Sprint 2).
- 질문 생성·답변 분석 중에는 시간이 멈춰 있어 만료되지 않는다.
- 만료 뒤 도착한 답변은 저장하지 않는다. WS는 `interviewEnd`를 보내고 닫는다. 작성·녹음 중이던 답변은 버린다(진행 중 답변의 유예 제출은 하지 않는다).
- 새 status를 만들지 않고 `completed`를 쓴다. 정상 완료와 시간 종료는 "답변 완료 턴 수 < `total_turns`"로 구분한다.
- 이벤트는 새 이름 없이 기존 `interview_completed`에 `payload {"reason": "time_expired"}`를 남긴다. 이벤트 이름은 task-17의 10종 고정(DB CHECK)을 따른다. 9턴 정상 완료의 이벤트는 그대로다.

### 3. 시간 종료로 끝난 면접의 리포트

- 생성 조건: `completed`이고, tech_lead와 domain_lead 답변 완료 턴이 각각 1개 이상. 미달이면 `409 report_unavailable`. 9턴 정상 완료는 6/2/1 배분이라 항상 충족한다.
- AI 입력과 리포트 응답의 턴 목록은 답변 완료 턴만 쓴다. 지원자가 답할 기회가 없었던 마지막 턴은 빼며, 빈 답변으로 0단계 판정하지 않는다.
- 점수 계약(6개 key, nullable 금지)은 바꾸지 않는다.

### 4. 마이페이지

- `averageScore`는 모든 턴(`total_turns`)에 답한 면접의 리포트 점수만으로 계산한다. 시간 종료 면접은 완료 횟수·목록에는 남고 평균에서만 빠진다.
- `GET /me/interviews` 각 행에 `answeredTurns`(답변 완료 턴 수)와 `reportAvailable`(리포트가 있거나, 열면 만들어지는 면접이면 true)을 더한다. 리포트가 지연 생성이라 `totalScore`가 null인 것만으로는 "아직 안 열어 봄"과 "만들 수 없음"을 구분할 수 없기 때문이다.
- 프로필 요약(언어·유형·역할)은 시간 종료 면접을 계속 포함한다.

## 이유와 대안

- 정지 범위를 `thinking` 전체로 한 이유: 실제 면접에서 면접관은 질문을 어느 정도 정리해 온다. 질문 준비 시간은 지원자의 시간이 아니다. 질문 생성 호출만으로 좁히면 답변 분석 대기가 지원자 시간에서 빠지지 않는다.
- TTS를 정지하지 않은 이유: 실제 면접에서도 면접관이 말하는 시간은 면접 시간에 포함된다.
- 만료 트리거를 서버 이벤트 검사로 한 이유: 서버에 타이머·워커가 없고 정지 구간 때문에 만료 시각이 계속 움직여 예약 job이 맞지 않는다. FE가 종료를 요청하는 안은 새 엔드포인트가 필요하고 클라이언트 말을 서버가 다시 검증해야 한다. 이벤트 검사는 새 계약 없이 서버가 판정한다.
- `completed`를 재사용한 이유: 새 status는 DB CHECK, migration, openapi enum, FE 타입과 `status == 'completed'`로 거르는 모든 곳을 바꿔야 한다. 정상 완료와의 구분은 턴 수로 계산할 수 있다.
- 답변 작성 중 만료를 즉시 끊기로 한 이유: 만료 뒤 답변을 받으려면 면접 종료 판정을 9번째 답변이 아닌 곳에서도 허용해야 해서 AI Director 종료 계약까지 건드린다. 후속으로 미룬다.
- 점수 없음(null) 허용 대신 최소 진행 조건을 택한 이유: nullable score는 AI 점수 계약, BE의 6개 key 검증, openapi, FE 리포트 화면을 모두 바꾸고 Sprint 1 점수 결정을 뒤집는다. 최소 조건은 BE 조건과 FE 안내만 바뀐다. 진행이 짧은 사용자는 리포트를 받지 못한다는 비용이 있다.
- 평균에서 시간 종료 면접을 뺀 이유: 질문 수와 구성이 달라 9턴 면접과 같은 기준의 점수가 아니다.

## 영향

- BE: 잔여 시간 계산, 만료 전환(`GET`·WS), 리포트 생성 조건과 입력, `/me/interviews`(`averageScore`, `answeredTurns`, `reportAvailable`). 최소 진행 조건은 `REPORT_REQUIRED_PERSONAS` 한 곳에 둔다.
- FE: `thinking` 동안 카운트다운 정지, 0 도달 시 입력 잠금·안내·서버 확인, 리포트의 "N/9턴" 표시와 짧은 진행 안내, 마이페이지 행 표시.
- 계약(`openapi.yaml`): `remainingSeconds`의 의미(질문 생성 대기 제외), `InterviewSummary`의 `answeredTurns`·`reportAvailable`. 필드 이름과 타입은 새로 생기는 두 개 외에 바뀌지 않는다.
- spec 수정 대상: FE `interview.md` 타이머 절과 "정상 완료는 9번째 답변 처리 완료" 문구, BE `report.md` 생성 조건, `openapi.yaml`.
- AI 확인 필요:
  1. 최소 진행 조건(tech 1회, domain 1회 답변)을 채워도 질문 범위에 따라 판정이 `not_applicable`로 나오면 한 key가 전부 NA가 되어 `unscorable key`로 생성이 실패한다. 이 조건으로 6개 key가 충분히 판정되는지, 조건을 더 좁혀야 하는지 확인한다.
  2. 답하지 못한 마지막 턴을 입력에서 빼도 점수·서술 계약에 문제가 없는지 확인한다.
- 되돌리기: 최소 진행 조건은 상수 한 곳, 평균 조건은 쿼리 한 곳, 만료 전환은 `expire_if_due` 호출 지점 세 곳을 되돌리면 된다. 새 컬럼·migration은 없다.
- 알려진 한계: 잔여 1초를 남기고 답변을 제출하면 다음 질문이 온 뒤 1초 뒤 종료된다. 화면을 닫고 떠난 면접은 자동 종료되지 않는다.

## 대체 관계
