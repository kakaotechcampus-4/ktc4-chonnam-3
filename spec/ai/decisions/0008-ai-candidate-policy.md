- 날짜: 2026-09-12
- 관련 PR: 없음
- 검토자: 현재 사용자 승인
- 연결 항목: [later.md의 AI-L04·AI-L06·AI-L08·AI-L09·AI-L10](../../../later.md)

## 맥락

기존 결정은 추가 근거 조회와 결과 해석, 답변 정성 평가, 도메인 질문 생성 원칙을 승인했지만 모델 후보가 실패하거나 여러 후보가 유효할 때의 일부 AI 정책은 남겨 두었다. 반면 재시도 실행, 준비 상태, Tool I/O와 운영 seed는 AI 단독 책임이 아니다.

사용자는 AI가 독립적으로 확정할 수 있는 후보 수준 정책만 아래와 같이 승인했다. 이 결정은 기존 [0003 근거 조회](0003-evidence-lookup-policy.md), [0004 답변 평가](0004-answer-assessment-policy.md), [0005 도메인 질문](0005-domain-question-policy.md)의 승인 내용을 유지한다.

## 구조화 후보 실패

구조화 결과 실패는 다음 의미를 구분한다.

- parse 실패: 구조화 문서로 읽을 수 없다.
- schema 실패: 읽을 수 있지만 채택된 구조 계약을 만족하지 않는다.
- semantic 실패: 구조는 맞지만 허용하지 않은 참조·Persona·근거·범위처럼 task 의미 정책을 위반한다.

어느 실패든 빈 성공, 추측한 기본값, 누락값의 임의 보충 또는 ad hoc repair로 성공 처리하지 않는다. 유효한 L1 batch 항목은 보존하고 잘못된 항목만 실패 후보로 분리한다. 실패는 현재 task 범위 밖의 원문이나 이미 검증된 결과를 지우지 않는다.

이 정책은 semantic 실패 뒤 실제 모델을 다시 호출할지, 어느 계층이 attempt를 관리할지, 호출 횟수·timeout·budget을 정하지 않는다. parse 실패에 관한 기존 FIX 재시도도 그대로 두며 실행 책임은 AI·BE가 별도로 합의한다.

## L2 관찰의 근거 범위

L2 관찰은 분석 대상의 고정 SHA에서 실제 source를 확인하고, 읽은 내용이 해당 주장까지 뒷받침할 때만 사용 가능하다. source는 유효하지만 언어·도구 기능이나 읽은 범위가 해석에 충분하지 않으면 확인 가능한 관찰과 한계를 함께 남긴다. 잘못된 ref/path, 확인하지 않은 source 또는 읽은 내용을 넘어 추론한 언어 동작·아키텍처 주장은 사용 가능한 관찰이나 Evidence 출발점으로 취급하지 않는다.

AI 결과는 사용 가능한 관찰과 제한되거나 무효인 관찰을 구분한다. 이 결정은 지원 언어·parser 목록, 읽기 방식·범위, 정확한 반환 필드, 유효한 일부 결과로 면접 준비를 성공시킬지와 repo/`preparing_failed` 상태 매핑을 정하지 않는다.

## Evidence 후보 우선순위

추가 조회가 [0003 결정](0003-evidence-lookup-policy.md)의 세 조건을 만족하면 BE가 공급하고 검증할 수 있는 범위 안에서 다음 순서로 후보를 제안한다.

1. 현재 주장·질문 목적과 관련된 기존 Evidence와 이미 수집한 원문
2. 현재 주장에 직접 연결된 정확히 알려진 파일
3. 사전에 검증된 인접 범위의 후보

같은 단계에서는 구현 주장은 실제 코드, 프로젝트 목적은 README, 언어·저장소 사실은 해당 metadata처럼 주장 종류에 직접 맞는 source를 우선한다. 직접성이 같으면 확인 범위가 더 좁고 명확한 후보를 먼저 둔다. 검색하지 않은 위치를 근거처럼 만들지 않는다.

이는 후보 순위 정책일 뿐 디렉터리 파일 열거, 인접 범위 생성, Tool transport, 권한 검사, 호출·파일·byte/token/time 상한 또는 중단 처리를 승인하지 않는다.

## 질문 후보 복구 선택

질문 후보의 처리 기준은 다음과 같다.

- 전제·목적·필수 확인내용은 유효하고 한 질문 표현만 복합적이거나 유도적이면 의미를 바꾸지 않고 재작성 후보로 분류한다.
- 전제나 목적이 거짓·stale이거나 이미 확인한 내용을 반복하여 현재 맥락에 맞지 않으면 새로운 목적·근거의 재계획 후보로 분류한다.
- 공급된 허용 Persona·맥락·근거·범위 안에서 안전하고 유효한 질문 후보를 만들 수 없으면 검증되지 않은 fallback 질문을 내보내지 않고 유효 후보 없음으로 반환한다.

이 분류는 임의의 새 enum, 정상 종료, 사용자 입력 복구, BE·FE 상태 매핑, 추가 모델 호출, attempt/budget 또는 Persona·Turn quota 변경을 승인하지 않는다. service/Controller가 최종 상태와 공개 동작을 결정한다.

## 도메인 frame 후보 선택

[0005 결정](0005-domain-question-policy.md)을 통과한 frame 중 검증된 서비스 맥락과 질문 목적에 더 직접 관련된 후보를 우선한다. 관련성이 같은 후보 사이에서는 이전 질문의 목적을 덜 반복하는 후보를 선호한다.

이 선호는 세 축의 고정 순환, 축별 최소 횟수, 숫자 relevance 점수 또는 모든 축 소진 의무가 아니다. 기존 21개는 계속 개발용 후보이며 최종 운영 문구 채택, 독립·도메인·한국어 검수, 활성 version, 저장·migration과 seed 설치는 별도다.

## 수용 사례

- 깨진 JSON, 구조 누락, 구조는 맞지만 다른 repo/ref를 인용한 결과를 parse/schema/semantic 실패로 구분하고 모두 성공으로 전달하지 않는다.
- L1 batch의 유효한 항목과 semantic 오류 항목이 함께 있으면 유효 항목을 보존하되 오류 항목을 기본값으로 채우지 않는다.
- 고정 SHA의 실제 파일을 읽은 L2 관찰은 사용 가능하지만, 읽지 않은 코드 경로의 동작 설명은 제한 또는 무효로 남긴다.
- 지원 기능이 확인되지 않은 언어 source는 파일 존재만으로 실행 동작·아키텍처를 추정하지 않고 확인 범위를 명시한다.
- 이미 수집한 직접 근거가 있으면 새 조회를 제안하지 않고, 필요할 때만 정확한 파일과 사전 검증된 인접 후보 순으로 제안한다.
- 목적이 유효한 복합 질문은 재작성 후보, 거짓 전제나 반복 목적은 재계획 후보, 허용 범위에 안전한 질문이 없으면 유효 후보 없음으로 구분한다.
- 도메인 frame 후보가 여러 개면 검증된 서비스 관련성과 목적 비반복 순으로 고르되 고정 순환이나 새 quota를 만들지 않는다.

## 이유와 대안

- invalid 후보를 부분 JSON·기본값으로 살리면 모델 오류가 검증된 사실처럼 downstream에 전달된다. 실패를 구분하고 fail closed하는 편이 원인을 보존한다.
- L2 하나의 오류로 모든 관찰을 버리면 실제로 확인한 자료도 잃고, 반대로 일부 path만 맞는 결과를 전체 준비 성공으로 보면 근거 범위를 과장한다. 관찰의 사용 가능성과 서비스 readiness를 분리한다.
- source 종류를 고정 서열로 두면 주장과 맞지 않는 자료를 우선할 수 있다. 주장 적합성, 기존 자료, 좁은 범위를 순서대로 적용한다.
- 모든 질문 오류를 표현 재작성으로 처리하면 거짓 전제가 남고, 모두 차단하면 고칠 수 있는 문구도 버린다. 의미 보존 여부로 재작성과 재계획을 나눈다.
- 도메인 frame 고정 순환은 맥락과 무관한 질문을 강제하고, 완전 자유 선택은 같은 목적을 반복할 수 있다. 검증된 관련성과 비반복 선호만 둔다.

## 승인하지 않은 범위

- Context·Question·AnswerAnalysis·DirectorDecision·Evidence/ToolResult의 정확한 필드·enum·null·schema version과 저장/API 계약
- 실제 provider/model, SDK/client/task/worker 중 retry 주체, semantic 실패 재호출, timeout·호출·token·동시성·Tool budget
- 지원 언어·parser 목록, L2 일부 결과의 준비 성공 여부와 repo/면접 상태 매핑
- 디렉터리 열거·인접 후보 생성·Tool I/O, 권한과 실행 상한, Evidence 저장 형식
- 사용자 복구·정상 종료·공개 메시지·Persona 배분 변경과 새 retry/replan 횟수
- 운영 domain seed의 최종 문구·독립 검수·활성 version·검토 metadata·DB/migration/설치

## 구현과 검증 인계

위 수용 사례는 이후 fixture와 모델 평가의 요구사항이며, 이 문서 작성으로 코드·fixture·실제 모델·DB·Tool·worker·seed 검증을 수행한 것은 아니다. 정확한 계약과 운영값을 채택하기 전에는 순수 후보 분류·우선순위 검토만 진행한다.
