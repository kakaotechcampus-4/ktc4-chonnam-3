# 0062 응답 계측의 정밀 시계 분리

상태: 2026-11-11 로컬 구현·평가 채택. 0061의 계측 필드·보존 원칙은 유지하며 시계 선택만 후속 보완한다.

## 맥락

해당 Windows/Python 실행 환경의 get_clock_info에서 monotonic은 약15.6ms 해상도이고,
실행 장부·비교 실행기의 perf_counter는 더 높은 해상도를 제공한다. 서로 다른 시계로
측정한 세부 구간과 전체 시간을 빼면 잔차가 왜곡될 수 있다. 0ms를 실제 작업이 없다는
뜻으로 해석할 수도 없다. 이 환경 관찰을 다른 OS·Python 버전의 일반 사실로 확대하지 않는다.

## 결정

- 사적 응답 구간 계측 version2는 별도의 perf_counter 시작점을 잡고 mark·SSE 수신·
  duration 모두 같은 시계로 측정한다. 단위·9개 필드·원문 보호·관측 상한은 0061과 같다.
- 기존 AttemptMetadata.latency_ms·timeout·대기·재시도·호출 budget의 시계와 의미는
  바꾸지 않는다. 새로운 세부 계측의 시계 선택으로 공개 호출 계약을 변경하지 않는다.
- 장부는 version1·2를 모두 읽는다. 실행 환경의 clock info를 평가 identity에 기록한다.
  ms 정수로 반올림한 0은 표시 정밀도 이하의 관측이며 정확한 0이나 미관측의 뜻이 아니다.
- 이미 실행한 version1 원문·장부·통계와 당시 코드를 보존한다. 세부 시간은 해당 시계의
  해상도 한계를 함께 해석하고, 실제보다 정밀한 값으로 사후 보정하지 않는다.
- 기존 비교의 전체 경과 시간은 처음부터 perf_counter였으므로 그 짝 비교와 판정은
  보존한다. 새 시계의 단일 실호출 확인은 별도 예산·동결 자료로 기록하며, 이전 비교의
  새 표본이나 정책 속도 개선으로 합산하지 않는다.

## 이유와 영향

모델·추론 강도·토큰 상한을 바꾸지 않고 측정의 해석 문제를 해결한다. 높은 시계 정밀도도
공급자 내부의 대기·추론·네트워크를 완전히 분해해 주지는 않는다. 실제 검증·수치·남은
범위는 [구현 기록](../implementation.md)에 둔다.
